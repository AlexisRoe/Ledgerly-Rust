# Learning log

One section per milestone, written by the implementing agent when the milestone is done, before it stops for review. This is **raw material for the lessons**, which another agent writes after M11. Write for that reader: they will have this file, the code and the vendored Java, but none of the conversation.

## Entry format

```md
## M<N> · <title>

- **Java → Rust:** one bullet per construct that changed shape. Name the Java file and the Rust file, and say what moved from runtime or tests into the type system (or the other way round).
  - e.g. `ExpenseStatus` + guard methods (`https://github.com/AlexisRoe/Ledgerly-Java/blob/e2a13909634808b347d30b3dec4c3ffee6741c02/src/main/java/com/ledgerly/expenses/internal/domain/Expense.java`) → `ExpenseStatus` enum with an exhaustive `match` in `Expense::apply` (`crates/expenses/src/domain/expense.rs`): adding a status no longer compiles until every transition decides what to do with it.
- **Rust features that carried the weight:** ownership, traits, lifetimes, async, macros…, with the file where each shows best.
- **Surprises and dead ends:** what did not work first and why, with links to the fixing commit.
- **Parity traps:** behaviour that had to be copied from Java exactly although the contract does not say so.
- **Decisions:** anything decided during the milestone that is not worth an ADR.
- **Open questions:** things the reviewer should look at or explain.
```

## M0 · Domain core

`J/` is Ledgerly-Java's `src/main/java/com/ledgerly/` and `JT/` its `src/test/java/com/ledgerly/`, both at the commit in `vendor/ledgerly-java/SOURCE`.

- **Java → Rust:**
  - `Money` record implementing `Comparable<Money>`, which throws `CurrencyMismatch` (`J/shared/money/Money.java`) → `Money` with **no `Ord` and no `Add`** (`crates/shared/src/money/mod.rs`). `Ord::cmp` must return an `Ordering` for every pair of values, and there is none for 1 EUR against 1 USD. Implementing `Ord` would mean panicking or inventing an order, and would let `sort()`, `max()` and `BTreeMap` accept mixed currencies silently. So `Money::cmp` and `Money::checked_add` return `Result<_, MoneyError>`: a failure Java raises at runtime is now part of the signature, and the caller cannot forget it.
  - `java.util.Currency` plus the `getDefaultFractionDigits() < 0` check in `Money` → `Currency` (`crates/shared/src/money/currency.rs`) over a generated table (`currencies.rs`). A code without minor units (XAU, XTS, XXX) never becomes a `Currency`, so `minor_units()` is a plain `u8` and `Money` needs no check for it.
  - Six transition methods, each calling `requireClaimant`/`requireDecider` and `requireStatus` (`J/expenses/internal/domain/Expense.java`) → one function, `Action::target_from(status)` (`crates/expenses/src/domain/action.rs`), written as two nested `match`es **without a `_` arm**, and `Expense::authorize` (`crates/expenses/src/domain/expense.rs`), which matches on the action the same way. What the exhaustive `match` guarantees: a new `ExpenseStatus` or `Action` does not compile until every one of its (status, action) pairs is decided and until someone has said who may perform the action. Java notices a forgotten pair only through the 30-case test in `JT/expenses/internal/domain/ExpenseTest.java`. The test is ported anyway (`legal_pairs_succeed_and_the_rest_are_invalid_transitions`): the compiler proves that every pair has an answer, the test proves that it is the right one.
  - Sealed `ExpenseException` with six subclasses → `ExpenseError` enum (`crates/expenses/src/domain/error.rs`). Java's `NotAllowed(String)` became `Forbidden`, an enum of the five reasons, so tests match on a variant and not on message text. The messages are Java's, through `thiserror`.
  - `validMerchant`, `validNote` and the reason check inside `reject` (private static methods re-run on a `String` every time) → `Merchant`, `Note`, `RejectionReason` (`crates/expenses/src/domain/text.rs`): the check runs once, in the constructor, and the aggregate's fields have these types.
  - `ReceiptSummary(int, int)`, which throws on negative counts (`J/expenses/ReceiptSummary.java`) → `ReceiptSummary { accepted: u32, pending_scan: u32 }` (`crates/expenses/src/receipt_checks.rs`): a negative count cannot be written.
  - `Collections.unmodifiableList(rejections)` and the test `rejectionsListIsReadOnly` → `rejections(&self) -> &[Rejection]`. A shared slice has no mutating method, so the test has no counterpart.
  - `UserId`, `TeamId`, `ExpenseId` records, and bare `UUID`s for everything else (`J/shared/id/`) → seven newtypes generated by one `macro_rules!` (`crates/shared/src/id.rs`). Each has only the constructor for the UUID version Java stores (`ImportId::new_v4`, the rest `new_v7`). A `compile_fail` doc-test shows the mix-up that no longer compiles.
  - `Role.includes` via `compareTo` (`J/shared/role/Role.java`) → `Role::includes` via a private `rank()` with an exhaustive `match`, and no `Ord` on `Role`, so `role >= Role::Approver` cannot be written the wrong way round.
  - Injected `java.time.Clock` → `Clock` trait with `SystemClock` and `FixedClock` (`crates/shared/src/clock.rs`). `FixedClock` exists only under `cfg(test)` or the `testing` feature.
  - `Objects.requireNonNull` in every constructor → nothing. A value that may be missing is an `Option` (`Expense::note`).
- **Rust features that carried the weight:**
  - Exhaustive `match` on enums: `crates/expenses/src/domain/action.rs`.
  - Newtypes with private fields and a fallible constructor ("parse, don't validate"): `crates/shared/src/money/mod.rs`, `crates/expenses/src/domain/text.rs`.
  - `Result` and `?` with `#[from]` conversions (`InvalidInput` → `ExpenseError`, `CurrencyError` → `MoneyError`): `Expense::reject`, `Money::parse`.
  - Ownership and borrowing: transitions take `&mut self`, queries `&self`; `Money`, `Actor` and the ids are `Copy`; `rejections()` lends a slice. A refused operation returns before it assigns anything, so there is no half-changed expense (test `a_refused_edit_changes_nothing`).
  - Traits and trait objects: `&dyn Clock`, `Box<dyn ReceiptChecks>`; the `Send + Sync` bounds are there for the `Arc<dyn Clock>` to come.
  - `macro_rules!`: `typed_id!` in `crates/shared/src/id.rs`.
  - Lints as design rules: `[workspace.lints]` in `Cargo.toml`; `#[expect(..., reason = "...")]` for the two exceptions (`Money::cmp`, `mod domain`).
  - `proptest`: the `Money` properties at the end of `crates/shared/src/money/mod.rs`.
- **Surprises and dead ends:**
  - `rust_decimal` cannot stand in for `BigDecimal` when parsing: it accepts `1_000`, rejects `1E+2`, holds no negative scale and never prints an exponent, while Java's messages contain `BigDecimal.toString()` (`Amount must be positive: 0E-7`). `crates/shared/src/money/decimal_text.rs` therefore parses Java's grammar itself and reproduces `toString()`; `rust_decimal` only stores the validated amount (5515d7e).
  - `str::trim()` is not `String.strip()`. Rust treats U+00A0, U+2007, U+202F and U+0085 as whitespace and U+001C–U+001F not; Java does the opposite. A merchant of one non-breaking space is valid in Java. `crates/shared/src/text.rs` holds Java's definitions, and Java's `length()` (UTF-16 units), which is what the 200/2000/1000 caps count (9de7c1b).
  - `"10.000".stripTrailingZeros().scale()` is -1, not 0. My first test expected 0; Java's rule ("scale after stripping ≤ minor units") only works because negative scales pass.
  - The first plan for `Merchant`/`Note` was to build them at the HTTP edge and hand `Expense::edit` typed values. That validates the fields before the claimant and status checks, so a non-claimant sending a blank merchant would get 400 where Java answers 403. `NewExpense` now carries the two texts raw and the aggregate converts them after its other checks (de705be).
  - Module-level `#![deny(clippy::arithmetic_side_effects)]` also hit the test modules; it is now `cfg_attr(not(test), deny(...))`.
  - The plan's source for the currency data (`make/data/currency/currency.properties` at tag `jdk-25`) does not exist. The file is `src/java.base/share/data/currency/CurrencyData.properties` and the tag `jdk-25-ga` (325bb3a).
  - `vendor/ledgerly-java/SOURCE` is not in the checksum manifest, so a strict "no unlisted file" check failed on a clean checkout. The script allows exactly that file and requires it to exist (fd84722).
  - A zsh trap worth knowing: a loop variable named `path` replaces `PATH`.
- **Parity traps:**
  - Currency messages are the JDK's, not Ledgerly's: `The input currency code: "ABC" is not a valid ISO 4217 code`, `… must have a length of 3 characters`, and for a lower-case code `The country code: "eu" is not a valid ISO 3166 code`. Java passes `e.getMessage()` to the client (`J/expenses/internal/web/ExpenseMapper.java`, `safeMessage`).
  - Withdrawn currencies (DEM, ITL, …) are accepted, because `java.util.Currency` has no "active" flag.
  - Java evaluates `new BigDecimal(amount)` before `Currency.getInstance(code)`: with both wrong, the answer is `Not a valid decimal number`.
  - Check order inside the aggregate: who is acting (403 or self-dealing 409) → status (409) → field rules (400) → receipt rules (422). `reject` checks the reason last. `draft` and `edit` report the first broken field in the order merchant, note, date.
  - `submit` reports a missing accepted receipt before a pending scan.
  - A claimant with the MEMBER role who tries to reimburse their own expense gets "Role MEMBER may not REIMBURSE", not self-dealing: the role check comes first.
  - A note is neither stripped nor rejected when empty or blank; only the merchant and the rejection reason are stripped.
  - Enum names in messages are Java's constants in upper case (`Expense is DRAFT and cannot APPROVE`).
- **Decisions:**
  - `indexing_slicing` and `arithmetic_side_effects` are denied in `expenses::domain` and `shared::money` (non-test code), not workspace-wide. M0.1's text can be read either way; CONCEPT §4 says "in `domain/`".
  - chrono for dates and instants. CONCEPT §2 names no date crate. Reasons: sqlx maps it natively, and openapi-generator's `rust-axum` output uses it for `date`/`date-time`. The second reason is from memory and must be confirmed in M3.1.
  - `Money` must fit `numeric(19,4)`, as the plan says. Java has no such rule. The error (`MoneyError::TooLarge`) has a message of my own.
  - `Money::cmp` keeps the plan's name with `#[expect(clippy::should_implement_trait)]`.
  - `Expense::draft` creates its id with `ExpenseId::new_v7()`, which reads the system time, not the `Clock`. Java does the same (`UuidV7` uses `System.currentTimeMillis()`).
  - `Uuid::now_v7()` also orders ids created within one millisecond; Java's `UuidV7` does not. Rust is stricter, nothing depends on Java's weaker order.
  - `Expense` has no `version`, `created_at` or `updated_at` yet. In Java they are JPA concerns; they come with persistence in M2.
  - `Expense` has no `PartialEq`: two expenses with equal fields are still two expenses.
  - `ReceiptChecks::summary_for` takes a `TeamId` as well (CLAUDE.md: every read of team data takes the team id). It is synchronous and infallible in M0 and will have to change when a database stands behind it.
  - `mise.toml` also pins `cargo-binstall`, so that `cargo-nextest` installs as a binary. `sqlx-cli` has no prebuilt binary and is compiled on the first `mise install` (several minutes).
  - `just verify` is, for now: vendor check, `cargo fmt --check`, clippy `-D warnings`, nextest, doc-tests. `just gen-currencies` is not part of it, because it needs the network.
- **Open questions:**
  1. **`RejectionId` (plan M0.3) was not created.** Rejections have no id in Java (`Rejection(rejectedBy, reason)`) or in the schema (`expense_rejections`, key `(expense_id, position)`). Should the type exist anyway?
  2. **Which JDK's currency data is the reference?** The table comes from `jdk-25-ga`. A later 25.0.x that Java actually runs on may ship a newer ISO 4217 amendment. Is `jdk-25-ga` the right pin?
  3. **Amounts written with non-ASCII digits** (`١٢`) are accepted by Java's `BigDecimal` and rejected here (test `non_ascii_digits_are_not_accepted_although_java_accepts_them`). Over HTTP the spec's pattern `^[0-9]{1,15}(\.[0-9]{1,4})?$` should stop them first; the CSV import (M8) reaches `new BigDecimal` directly. Port the Unicode digit table, or accept the difference?
  4. **Amounts beyond `numeric(19,4)`.** Java's `Money` accepts `1E+20`; what Java then answers (presumably a database error during import) is unknown to me. Rust rejects it as `TooLarge`. To be settled in M8 against Java's behaviour.
  5. **`NewExpense` carries `merchant` and `note` as plain text**, so the aggregate, not the HTTP edge, turns them into `Merchant` and `Note`. This keeps Java's check order but bends CONCEPT §4 "request DTOs are converted into domain types at the edge" for these two fields. Is that the right trade?
  6. **Id parsing.** `FromStr` on the ids accepts every form the `uuid` crate accepts (also without hyphens, braced, `urn:uuid:`). Java's `UUID.fromString` accepts other odd forms (`1-1-1-1-1`). Which strings a path parameter accepts has to be pinned in M3 from Java's behaviour.
  7. **`vendor/ledgerly-java/SOURCE` has no checksum.** The drift check allows it by name. Should it be added to the manifest upstream?
