# Learning log

One section per milestone, written by the implementing agent when the milestone is done, before it stops for review. This is **raw material for the lessons**, which another agent writes after M11. Write for that reader: they will have this file, the code and the vendored Java, but none of the conversation.

## Entry format

```md
## M<N> · <title>

- **Java → Rust:** one bullet per construct that changed shape. Name the Java file and the Rust file, and say what moved from runtime or tests into the type system (or the other way round).
  - e.g. `ExpenseStatus` + guard methods (`https://github.com/AlexisRoe/Ledgerly-Java/blob/e2a13909634808b347d30b3dec4c3ffee6741c02/src/main/java/com/ledgerly/expenses/internal/domain/Expense.java`) → `ExpenseStatus` enum with an exhaustive `match` in `Expense::apply` (`crates/expenses/src/domain/expense.rs`): adding a status no longer compiles until every transition decides what to do with it.
- **Rust features that carried the weight:** ownership, traits, lifetimes, async, macros…, with the file where each shows best.
- **Surprises and dead ends:** what did not work first and why, with links to the fixing commit.
- **Parity traps:** behaviour that had to be copied from Java exactly although the contract does not say so.
- **Decisions:** anything decided during the milestone that is not worth an ADR.
- **Open questions:** things the reviewer should look at or explain.
```

## M0 · Domain core

`J/` is Ledgerly-Java's `src/main/java/com/ledgerly/` and `JT/` its `src/test/java/com/ledgerly/`, both at the commit in `vendor/ledgerly-java/SOURCE`.

- **Java → Rust:**
  - `Money` record implementing `Comparable<Money>`, which throws `CurrencyMismatch` (`J/shared/money/Money.java`) → `Money` with **no `Ord` and no `Add`** (`crates/shared/src/money/mod.rs`). `Ord::cmp` must return an `Ordering` for every pair of values, and there is none for 1 EUR against 1 USD. Implementing `Ord` would mean panicking or inventing an order, and would let `sort()`, `max()` and `BTreeMap` accept mixed currencies silently. So `Money::cmp` and `Money::checked_add` return `Result<_, MoneyError>`: a failure Java raises at runtime is now part of the signature, and the caller cannot forget it.
  - `java.util.Currency` plus the `getDefaultFractionDigits() < 0` check in `Money` → `Currency` (`crates/shared/src/money/currency.rs`) over a generated table (`currencies.rs`). A code without minor units (XAU, XTS, XXX) never becomes a `Currency`, so `minor_units()` is a plain `u8` and `Money` needs no check for it.
  - Six transition methods, each calling `requireClaimant`/`requireDecider` and `requireStatus` (`J/expenses/internal/domain/Expense.java`) → one function, `Action::target_from(status)` (`crates/expenses/src/domain/action.rs`), written as two nested `match`es **without a `_` arm**, and `Expense::authorize` (`crates/expenses/src/domain/expense.rs`), which matches on the action the same way. What the exhaustive `match` guarantees: a new `ExpenseStatus` or `Action` does not compile until every one of its (status, action) pairs is decided and until someone has said who may perform the action. Java notices a forgotten pair only through the 30-case test in `JT/expenses/internal/domain/ExpenseTest.java`. The test is ported anyway (`legal_pairs_succeed_and_the_rest_are_invalid_transitions`): the compiler proves that every pair has an answer, the test proves that it is the right one.
  - Sealed `ExpenseException` with six subclasses → `ExpenseError` enum (`crates/expenses/src/domain/error.rs`). Java's `NotAllowed(String)` became `Forbidden`, an enum of the five reasons, so tests match on a variant and not on message text. The messages are Java's, through `thiserror`.
  - `validMerchant`, `validNote` and the reason check inside `reject` (private static methods re-run on a `String` every time) → `Merchant`, `Note`, `RejectionReason` (`crates/expenses/src/domain/text.rs`): the check runs once, in the constructor, and the aggregate's fields have these types.
  - `ReceiptSummary(int, int)`, which throws on negative counts (`J/expenses/ReceiptSummary.java`) → `ReceiptSummary { accepted: u32, pending_scan: u32 }` (`crates/expenses/src/receipt_checks.rs`): a negative count cannot be written.
  - `Collections.unmodifiableList(rejections)` and the test `rejectionsListIsReadOnly` → `rejections(&self) -> &[Rejection]`. A shared slice has no mutating method, so the test has no counterpart.
  - `UserId`, `TeamId`, `ExpenseId` records, and bare `UUID`s for everything else (`J/shared/id/`) → seven newtypes generated by one `macro_rules!` (`crates/shared/src/id.rs`). Each has only the constructor for the UUID version Java stores (`ImportId::new_v4`, the rest `new_v7`). A `compile_fail` doc-test shows the mix-up that no longer compiles.
  - `Role.includes` via `compareTo` (`J/shared/role/Role.java`) → `Role::includes` via a private `rank()` with an exhaustive `match`, and no `Ord` on `Role`, so `role >= Role::Approver` cannot be written the wrong way round.
  - Injected `java.time.Clock` → `Clock` trait with `SystemClock` and `FixedClock` (`crates/shared/src/clock.rs`). `FixedClock` exists only under `cfg(test)` or the `testing` feature.
  - `Objects.requireNonNull` in every constructor → nothing. A value that may be missing is an `Option` (`Expense::note`).
- **Rust features that carried the weight:**
  - Exhaustive `match` on enums: `crates/expenses/src/domain/action.rs`.
  - Newtypes with private fields and a fallible constructor ("parse, don't validate"): `crates/shared/src/money/mod.rs`, `crates/expenses/src/domain/text.rs`.
  - `Result` and `?` with `#[from]` conversions (`InvalidInput` → `ExpenseError`, `CurrencyError` → `MoneyError`): `Expense::reject`, `Money::parse`.
  - Ownership and borrowing: transitions take `&mut self`, queries `&self`; `Money`, `Actor` and the ids are `Copy`; `rejections()` lends a slice. A refused operation returns before it assigns anything, so there is no half-changed expense (test `a_refused_edit_changes_nothing`).
  - Traits and trait objects: `&dyn Clock`, `Box<dyn ReceiptChecks>`; the `Send + Sync` bounds are there for the `Arc<dyn Clock>` to come.
  - `macro_rules!`: `typed_id!` in `crates/shared/src/id.rs`.
  - Lints as design rules: `[workspace.lints]` in `Cargo.toml`; `#[expect(..., reason = "...")]` for the two exceptions (`Money::cmp`, `mod domain`).
  - `proptest`: the `Money` properties at the end of `crates/shared/src/money/mod.rs`.
- **Surprises and dead ends:**
  - `rust_decimal` cannot stand in for `BigDecimal` when parsing: it accepts `1_000`, rejects `1E+2`, holds no negative scale and never prints an exponent, while Java's messages contain `BigDecimal.toString()` (`Amount must be positive: 0E-7`). `crates/shared/src/money/decimal_text.rs` therefore parses Java's grammar itself and reproduces `toString()`; `rust_decimal` only stores the validated amount (5515d7e).
  - `str::trim()` is not `String.strip()`. Rust treats U+00A0, U+2007, U+202F and U+0085 as whitespace and U+001C–U+001F not; Java does the opposite. A merchant of one non-breaking space is valid in Java. `crates/shared/src/text.rs` holds Java's definitions, and Java's `length()` (UTF-16 units), which is what the 200/2000/1000 caps count (9de7c1b).
  - `"10.000".stripTrailingZeros().scale()` is -1, not 0. My first test expected 0; Java's rule ("scale after stripping ≤ minor units") only works because negative scales pass.
  - The first plan for `Merchant`/`Note` was to build them at the HTTP edge and hand `Expense::edit` typed values. That validates the fields before the claimant and status checks, so a non-claimant sending a blank merchant would get 400 where Java answers 403. `NewExpense` now carries the two texts raw and the aggregate converts them after its other checks (de705be).
  - Module-level `#![deny(clippy::arithmetic_side_effects)]` also hit the test modules; it is now `cfg_attr(not(test), deny(...))`.
  - The plan's source for the currency data (`make/data/currency/currency.properties` at tag `jdk-25`) does not exist. The file is `src/java.base/share/data/currency/CurrencyData.properties` and the tag `jdk-25-ga` (325bb3a).
  - `vendor/ledgerly-java/SOURCE` is not in the checksum manifest, so a strict "no unlisted file" check failed on a clean checkout. The script allows exactly that file and requires it to exist (fd84722).
  - A zsh trap worth knowing: a loop variable named `path` replaces `PATH`.
- **Parity traps:**
  - Currency messages are the JDK's, not Ledgerly's: `The input currency code: "ABC" is not a valid ISO 4217 code`, `… must have a length of 3 characters`, and for a lower-case code `The country code: "eu" is not a valid ISO 3166 code`. Java passes `e.getMessage()` to the client (`J/expenses/internal/web/ExpenseMapper.java`, `safeMessage`).
  - Withdrawn currencies (DEM, ITL, …) are accepted, because `java.util.Currency` has no "active" flag.
  - Java evaluates `new BigDecimal(amount)` before `Currency.getInstance(code)`: with both wrong, the answer is `Not a valid decimal number`.
  - Check order inside the aggregate: who is acting (403 or self-dealing 409) → status (409) → field rules (400) → receipt rules (422). `reject` checks the reason last. `draft` and `edit` report the first broken field in the order merchant, note, date.
  - `submit` reports a missing accepted receipt before a pending scan.
  - A claimant with the MEMBER role who tries to reimburse their own expense gets "Role MEMBER may not REIMBURSE", not self-dealing: the role check comes first.
  - A note is neither stripped nor rejected when empty or blank; only the merchant and the rejection reason are stripped.
  - Enum names in messages are Java's constants in upper case (`Expense is DRAFT and cannot APPROVE`).
- **Decisions:**
  - `indexing_slicing` and `arithmetic_side_effects` are denied in `expenses::domain` and `shared::money` (non-test code), not workspace-wide. M0.1's text can be read either way; CONCEPT §4 says "in `domain/`".
  - chrono for dates and instants. CONCEPT §2 names no date crate. Reasons: sqlx maps it natively, and openapi-generator's `rust-axum` output uses it for `date`/`date-time`. The second reason is from memory and must be confirmed in M3.1.
  - `Money` must fit `numeric(19,4)`, as the plan says. Java has no such rule. The error (`MoneyError::TooLarge`) has a message of my own.
  - `Money::cmp` keeps the plan's name with `#[expect(clippy::should_implement_trait)]`.
  - `Expense::draft` creates its id with `ExpenseId::new_v7()`, which reads the system time, not the `Clock`. Java does the same (`UuidV7` uses `System.currentTimeMillis()`).
  - `Uuid::now_v7()` also orders ids created within one millisecond; Java's `UuidV7` does not. Rust is stricter, nothing depends on Java's weaker order.
  - `Expense` has no `version`, `created_at` or `updated_at` yet. In Java they are JPA concerns; they come with persistence in M2.
  - `Expense` has no `PartialEq`: two expenses with equal fields are still two expenses.
  - `ReceiptChecks::summary_for` takes a `TeamId` as well (CLAUDE.md: every read of team data takes the team id). It is synchronous and infallible in M0 and will have to change when a database stands behind it.
  - `mise.toml` also pins `cargo-binstall`, so that `cargo-nextest` installs as a binary. `sqlx-cli` has no prebuilt binary and is compiled on the first `mise install` (several minutes).
  - `just verify` is, for now: vendor check, `cargo fmt --check`, clippy `-D warnings`, nextest, doc-tests. `just gen-currencies` is not part of it, because it needs the network.
- **Open questions:**
  1. *Decided after M1: leave it out; plan M0.3 updated.* **`RejectionId` (plan M0.3) was not created.** Rejections have no id in Java (`Rejection(rejectedBy, reason)`) or in the schema (`expense_rejections`, key `(expense_id, position)`). Should the type exist anyway?
  2. *Decided after M1: keep `jdk-25-ga`; plan M0.4 updated with the real path and tag.* **Which JDK's currency data is the reference?** The table comes from `jdk-25-ga`. A later 25.0.x that Java actually runs on may ship a newer ISO 4217 amendment. Is `jdk-25-ga` the right pin?
  3. *Decided after M1: port Java's behaviour (112d6fb, `scripts/gen-unicode-digits.sh`).* **Amounts written with non-ASCII digits** (`١٢`) are accepted by Java's `BigDecimal` and rejected here (test `non_ascii_digits_are_not_accepted_although_java_accepts_them`). Over HTTP the spec's pattern `^[0-9]{1,15}(\.[0-9]{1,4})?$` should stop them first; the CSV import (M8) reaches `new BigDecimal` directly. Port the Unicode digit table, or accept the difference?
  4. *Decided after M1: keep the bound now, settle against Java in M8 (plan M8.4).* **Amounts beyond `numeric(19,4)`.** Java's `Money` accepts `1E+20`; what Java then answers (presumably a database error during import) is unknown to me. Rust rejects it as `TooLarge`. To be settled in M8 against Java's behaviour.
  5. *Decided after M1: keep Java's order; CONCEPT §4 names the exception.* **`NewExpense` carries `merchant` and `note` as plain text**, so the aggregate, not the HTTP edge, turns them into `Merchant` and `Note`. This keeps Java's check order but bends CONCEPT §4 "request DTOs are converted into domain types at the edge" for these two fields. Is that the right trade?
  6. *Decided after M1: canonical form only (ae67c36).* **Id parsing.** `FromStr` on the ids accepts every form the `uuid` crate accepts (also without hyphens, braced, `urn:uuid:`). Java's `UUID.fromString` accepts other odd forms (`1-1-1-1-1`). Which strings a path parameter accepts has to be pinned in M3 from Java's behaviour.
  7. *Decided after M1: keep the exemption.* **`vendor/ledgerly-java/SOURCE` has no checksum.** The drift check allows it by name. Should it be added to the manifest upstream?

## M1 · First axum app

`J/` is Ledgerly-Java's `src/main/java/com/ledgerly/`, `JT/` its `src/test/java/com/ledgerly/`, `R/` its `src/main/resources/` (vendored under `vendor/ledgerly-java/`).

- **Java → Rust:**
  - Spring Modulith's `ApplicationModules.verify()` (`JT/ModularityTest.java`) → one crate per module and `crates/app/tests/architecture.rs`, which reads `cargo metadata` and compares the graph with CONCEPT §3. A cycle no longer needs a test: cargo refuses `teams → expenses` before anything compiles. The test still catches a wrong arrow that is not a cycle (`receipts → identity`), with the edge named.
  - `@ConfigurationProperties` records with `@DefaultValue`, `application*.yaml` and `ProductionEnvironmentCheck` (`J/shared/config/`) → plain structs in `crates/shared/src/config/` and one reader in `crates/app/src/config.rs`. Spring binds by reflection and fails on the first bad value; the reader collects every missing or unusable setting and reports them together, under Java's names (`SPRING_DATASOURCE_URL`, `LEDGERLY_LIMITS_*`). Secrets are `SecretString` from the moment they are read, so `Debug` of the whole config prints `[REDACTED]` (test `debug_of_the_config_shows_no_secret`).
  - Spring Boot's `DurationStyle` and `DataSize` → `parse_duration` and `parse_data_size` (`crates/shared/src/config/`), with the same units and the same binary megabytes.
  - Tomcat with `server.shutdown: graceful` and Actuator on `management.server.port` → two axum listeners (`crates/app/src/lib.rs`, `server.rs`, `management.rs`). Spring's lifecycle phases become one `tokio::join!`: on SIGTERM readiness turns `OUT_OF_SERVICE`, the API drains for up to 30 s, then the management listener stops.
  - Logback's ECS encoder plus the MDC → a `tracing_subscriber::Layer` (`crates/app/src/logging.rs`) that writes Spring Boot 4.2's member list in its order, and span fields in place of the MDC. A field is attached to the span of a request instead of being put into and removed from a thread-local, so it cannot leak into the next request on the same thread.
  - Micrometer Tracing with the OTel bridge → the OpenTelemetry SDK used directly in a middleware (`crates/app/src/telemetry.rs`); the ids are also stored in the request's extensions for the problem bodies of M3.
  - Paketo buildpacks → a hand-written multi-stage `Dockerfile` (ADR 0012): 39 MB, user 65532, no shell.
  - JUnit with `@SpringBootTest`, `MutableClock`, `CapturedVerificationTokens` and seeders → `crates/parity-tests`, a black box (ADR 0011). Where Java mints a token, the suite logs in; where Java reads its mailbox, the suite writes a verification with a token it knows; where Java flips `FakeMalwareScanner.unavailable`, the suite stops the ClamAV container; where Java gives a test class its own properties, the suite starts the app once per run group.
- **Rust features that carried the weight:**
  - Traits as seams: `config::Environment` (the process environment or a `HashMap` in tests), `tracing_subscriber::Layer`.
  - `tokio::sync::watch` for the shutdown switch (`server.rs`): any number of waiters, and a waiter that arrives late still sees that shutdown has started.
  - `tokio::select!` and `tokio::join!` for "drain, but not longer than 30 s" and "stop the listeners in order".
  - `secrecy::SecretString` and the type system for the redaction rule.
  - Integration tests that start the real binary (`crates/app/tests/startup.rs`) and send it SIGTERM.
- **Surprises and dead ends:**
  - The first drain test assumed that `serve` returning means the cut-off request has failed. It does not: the connection task belongs to the runtime and lives until the runtime stops, which the binary does right after. The test now checks that `serve` returns on time and that the request never got an answer (53897d0).
  - `docs/reference/java-port-spec.md` §3.8 listed ECS fields as dotted keys (`log.level`). Spring Boot 4.2 writes nested objects (`"log":{"level":…}`). Corrected from Boot's source at `v4.2.0-RC2` (c6af184).
  - `redgate/flyway` publishes no arm64 image; `flyway/flyway` at the same version does (b8f4803).
  - Docker Desktop was not running when the image was first built; nothing in the repository was at fault.
  - `docs/reference/java-test-inventory.md` §1 had no `Api10UnsafeConsumptionOfApisTest`, although the class exists at the pinned commit. The inventory check (`crates/parity-tests/tests/inventory.rs`) found it because a parity test named a class the inventory did not know (d355e99).
  - nextest has no global timeout by default, and a test that waits for a server that never stops waits forever. `.config/nextest.toml` now ends a test after two minutes.
  - sqlx 0.9 wants `&'static str` (or `SqlStr`) for a query, not any `&str`.
- **Parity traps:**
  - Spring Boot's health body with probes enabled is `{"groups":["liveness","readiness"],"status":"UP"}`; Java's test greps for `"status":"UP"` without a space, so the JSON must be compact.
  - Actuator answers with `application/vnd.spring-boot.actuator.v3+json`, not `application/json`.
  - `application-keycloak.yaml` gives the issuer a default (`${KEYCLOAK_ISSUER_URI:http://localhost:8180/realms/ledgerly}`) that also applies in `prod`. Implemented as Java does (open question 3).
  - The `prod` failure text is Spring's failure analyzer's: a "needs these settings, which are not set" block and the "Set them in the environment…" action.
  - Java's tests run with `requests-per-minute=100000` (`application-test.yaml`); the parity groups do the same, and override it where Java's test classes do.
  - Java's ID in an `Idempotency-Key` test is a literal (`key-12345678`). Against a database that is never cleaned, a literal key would replay an earlier run, so the parity tests use fresh keys.
- **Decisions:**
  - Required settings are checked in every profile, not only `prod`. Java fails there too, through `@NotBlank`, one setting at a time.
  - A database URL with a user or password in it is refused, so the URL is never a secret and can be named in errors.
  - Negative durations are refused.
  - The management listener answers 404 in Spring's error shape for every path it does not serve. M1.3 asks for 404; whether Java answers 401 there is open question 1.
  - `/actuator/info` reports a `build` block with `group: com.ledgerly`, the Cargo version and, when the image build passes it, the build time.
  - `just verify` ends with `just parity`, as `docs/local-setup.md` §4 lists, so it needs Docker. `just test` runs everything else, including the inventory check.
  - The parity suite reads the milestone of a test from its `m<N>` module and also marks it `#[ignore = "M<N>"]`, so `cargo nextest list` and the report agree.
  - Fixture users share one Argon2id hash in Spring's parameters, computed once per test process (Argon2 with 16 MiB is too slow per user).
  - In the `api4` group every test claims its own client address in `X-Forwarded-For`, and the app is started with `SERVER_FORWARD_HEADERS_STRATEGY=native` (a variable Java's `.env.example` names). Without that, the logins the fixtures need would use up the 12-per-minute allowance that the test is about.
  - The EICAR string is assembled from two halves in `crates/parity-tests/src/fixtures.rs`, so that a virus scanner on a developer machine leaves the checkout alone.
  - New dependencies, each named in its commit: secrecy, tokio, axum, tracing, tracing-subscriber, opentelemetry (+ sdk, otlp), and for the suite sqlx, reqwest, jsonschema, argon2, sha2, p256, serde-saphyr. `deny.toml` allows MIT-0 for one transitive crate of jsonschema.
- **Open questions:**
  1. *Decided: keep 404.* **Unknown paths on the management port.** Rust answers 404 (the plan's wording). Java's actuator security chain denies non-exposed endpoints, which may make the answer 401 or 403. Only "≠ 200" is asserted by Java. Which status should Rust pin?
  2. *Decided: keep the body as it is.* **`/actuator/health` body.** The `groups` member is from memory of Spring Boot with `probes.enabled`; the inventory only quotes `{"status":"UP"}`. Worth checking against a running Java once.
  3. *Decided: copy Java, raise it upstream in Ledgerly-Java.* **Keycloak issuer in `prod`.** Java's YAML default applies in `prod`, which contradicts ADR 0013's "nothing in prod has a default". Rust copies Java. Fix upstream?
  4. *Decided: settle in M11.* **Keycloak issuer in the parity suite (M11).** The app reaches Keycloak as `keycloak:8080`, the tests as `127.0.0.1:8180`; Keycloak puts the requested host into `iss`, so the two will not match without `KC_HOSTNAME` or a shared hostname. To be settled in M11; the `keycloak` run group is a placeholder until then.
  5. *Decided: follow the link and check the store's headers (cd65a6c).* **Presigned links.** Java's tests read the download name and lifetime from a fake store. The parity test reads them from the link's `response-content-disposition` and `X-Amz-Expires` parameters, which is how the AWS SDK encodes them; the inventory notes that Java's encoding was never checked. M7 will show whether both agree.
  6. *Decided: parity runs as its own CI job (228543f).* **CI runs `just verify`, and with it the parity suite**, which builds the image and starts ClamAV (amd64 only). It is not known yet how long that takes on GitHub's runners; the reviewer will see it on the first push.
  7. ~~**The prometheus test asserts `jvm_memory_used_bytes` and `http_server_requests`**~~ Decided by the reviewer: that part of `MetricsTest.prometheusExposesThemOnTheManagementPortOnly` is Java-only. `crates/parity-tests/tests/owasp_metrics.rs` asserts the Rust equivalents, `process_resident_memory_bytes` and `http_server_request_duration_seconds`; plan M10.3 and inventory §4.6 say so. Pointed at Java, this one assertion fails by design.

## M2 · Persist expenses

`J/` is Ledgerly-Java's `src/main/java/com/ledgerly/`, `R/` its `src/main/resources/` (vendored under `vendor/ledgerly-java/`).

- **Java → Rust:**
  - Flyway running inside Spring Boot at startup (migrate, then `validate`) → `ledgerly_shared::database::verify` (`crates/shared/src/database/schema.rs`), which only reads `flyway_schema_history` and refuses to start on any missing, failed, changed or unknown version, naming each one. The migrations are embedded in the binary by `crates/shared/build.rs`, which lists `R/db/migration/` at build time, so a re-vendored V11 is demanded by the next build without anyone editing a list. Flyway's checksum is reimplemented (`migrations.rs`, `flyway_checksum`): CRC-32 over each line's UTF-8 bytes without the line break, BOM removed, read as a signed `int`. The test pins the ten values Flyway 12 wrote.
  - HikariCP via Spring Boot's `DataSource` auto-configuration → `sqlx::PgPool` (`crates/shared/src/database/mod.rs`) with Hikari's defaults (10 connections, 30 s acquire, 10 min idle, 30 min lifetime). Hikari's `initializationFailTimeout=1` (one attempt, fail at once) is copied by trying one plain `PgConnection` before creating a lazy pool; `PgPoolOptions::connect_with` alone retried for 30 s.
  - `ExpenseRepository extends Repository` (no inherited `findById`) and the JPA mapping on `Expense` (`J/expenses/internal/infrastructure/ExpenseRepository.java`, `J/expenses/internal/domain/Expense.java`) → free `pub(crate)` functions in `crates/expenses/src/persistence/mod.rs`. Java keeps the unscoped lookup out by choosing a base interface; Rust keeps the whole module out of the crate's public API, so nothing outside `expenses` can call any of it, and inside it every read takes a `TeamId`.
  - `@Version long version` inside the entity → `ledgerly_shared::version::{Version, Versioned<T>}`. The aggregate stays free of persistence fields; `find` returns `Versioned<Expense>` and `update`/`delete` take the expected `Version` explicitly. Java's optimistic lock is implicit (Hibernate adds `and version=?` at flush); here it is one visible `where … and version = $n` and a `Conflict` when no row matches.
  - Hibernate filling fields through the protected no-arg constructor → `TryFrom<ExpenseRow> for Versioned<Expense>`, which sends every column through the domain's own constructors (`Money::new`, `Merchant::new`, `Category::from_str`, …) and then `Expense::restore(StoredExpense)` (`pub(crate)`). A row the domain could not have written becomes `PersistenceError::Corrupt` naming the column, never a half-valid aggregate.
  - `@ElementCollection` + `@OrderColumn(name = "position")` for rejections → one `array_agg(… order by position)` in the same statement as the expense (one snapshot, no lazy loading), and appending rows from the stored count on `update`.
  - `@Transactional` on the use case + `ObjectOptimisticLockingFailureException` → `pool.begin()` … `commit()` in `crates/expenses/src/application/`, with persistence functions taking `&mut PgConnection` so the caller decides the transaction. A `Transaction` that is dropped without `commit` rolls back: the "rollback on exception" rule of `@Transactional` falls out of `?` and `Drop`.
  - `@Transactional(readOnly = true)` on `GetExpense` → `set transaction read only` as the first statement.
  - `@CreationTimestamp`/`@UpdateTimestamp` → `now` passed into `insert`/`update` by the use case, from the injected `Clock`.
  - Testcontainers' `@ServiceConnection` Postgres in Java's tests → `TestDatabase` (`crates/shared/src/database/testing.rs`, feature `testing`): one Postgres container shared by all test processes of a run (it removes itself when idle; see the M2 follow-up commit), a template database migrated once by the pinned Flyway image, and `CREATE DATABASE … TEMPLATE` per test (≈ 0.3 s warm). Images are read from `compose.yaml`, so Renovate updates tests and dev loop together.

- **Parity traps:**
  - Spring's conversion rules, each with a test in `query.rs` or `list_tests.rs`:
    - `+` is a space.
    - A `String` parameter given twice is joined with `,` (`sort=incurredOn&sort=asc` sorts ascending); other types take the first value.
    - `""` means the default (`size=` is 20).
    - Enums are trimmed with `String.trim()` and `""` is no filter.
    - Blank UUIDs and dates are no filter.
    - Integers go through `NumberUtils.parseNumber`: all whitespace removed, a sign, `0x`/`#` hex, Unicode digits.
    - A date may carry an offset (`incurredTo=2026-01-31Z`), because the generated interface uses `@DateTimeFormat(iso = DATE)`, which is `ISO_DATE`, not `ISO_LOCAL_DATE`.
  - Order of checks:
    1. 401.
    2. The first parameter that does not convert, in declaration order (`page, size, sort, status, category, claimantId, currency, incurredFrom, incurredTo`): Spring's type mismatch 400 `REQUEST_REJECTED` "Failed to convert 'size' with value: 'abc'".
    3. All constraint violations together: 400 `VALIDATION_FAILED` with Hibernate Validator's default messages: `must be greater than or equal to 0`, `must be less than or equal to 100`, `must match "^(incurredOn|createdAt|amount)(,(asc|desc))?$"`, `must match "^[A-Z]{3}$"`.
    4. Teammate, else 404.
    5. Then the use case: size against `ledgerly.limits.max-page-size` ("size must be between 1 and N"), currency ("Unknown currency code"), sort ("Sorting by amount needs a currency filter"), then the date range ("incurredFrom must not be after incurredTo").

    So a stranger gets 400 for `size=101` but 404 for `currency=ZZZ` or `sort=amount`.
  - Both the spec's `maximum: 100` and the configured limit apply, as Java's learning log says.
  - `page.size` and `page.number` echo the request. A page past the end is 200 with `content: []` and the real totals.
  - The tie-breaker is the id in the *same* direction as the sort field. The default is `incurredOn,desc` with size 20.
  - A MEMBER's `claimantId` is silently replaced by their own id, and `totalElements` counts only their rows.
  - Cursor:
    - JSON `{"t": Instant.toString(), "id": uuid}`, with `Instant.toString()` trimming the fraction to 0/3/6/9 digits (chrono's `SecondsFormat::AutoSi`).
    - Java's `Map.of` key order changes between JVM starts, so decoding accepts both orders.
    - `Instant.parse` takes an offset and any case, and the cursor decoder accepts both too.
- **Decisions:**
  - The page and the count run in one `REPEATABLE READ, READ ONLY` transaction, so the totals always match the page. Java uses the default `READ COMMITTED` (read-only); the difference only shows under concurrent writes.
  - Constraint violations are listed in parameter order. Java's come from a `ConstraintViolationException`'s `HashSet`, in no defined order.
  - UUIDs in query parameters and cursors: canonical 8-4-4-4-12 only, as for path parameters (M1 decision 6). Java's `UUID.fromString` also takes forms like `1-1-1-1-1`.
  - An invalid `%` escape in the query stays literal, as in path parameters. Tomcat 11's handling (drop the parameter, or 400) was not checked.
  - A type mismatch on a repeated parameter quotes the first value. Java would quote the array's `toString()`.
