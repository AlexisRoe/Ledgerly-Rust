Traits in depth

Typestate: states as types

Ledgerly checks expense transitions at run time with an enum and a table. A different design moves the states into the type system, so approve on a draft doesn't compile. Knowing both helps you choose.

By the end of this lesson

You can build a typestate API with marker types and PhantomData, and say when it fits better than an enum.

The run-time design (Ledgerly)

In Ledgerly

One Expense type with a status field. approve exists on every expense and returns an error if the status is wrong. That's the right choice here: the status comes from the database at run time, the API must answer "you can't approve a draft" with a 409, and the parity suite checks exactly that response.

The compile-time design

  • Each state is a type; methods exist only on the states where they're legal.
  • Transitions take self by value, so the old state is consumed: you can't keep using the draft after submitting it.
  • PhantomData<S> tells the compiler the struct is "about" an S without storing one. It has size zero; so do the marker structs. All of it disappears after compiling.

TS can approximate it with branded types or a discriminant generic (Claim<"draft">), but nothing stops code from keeping the old object around and calling methods on it. Rust's moves make the old state unusable.

You can't put a Claim<Draft> and a Claim<Approved> in one Vec: they're different types. That alone rules typestate out for Ledgerly's expenses.

Where the comparison breaks

In TS, a "state machine in types" is usually a discriminated union, which is Ledgerly's design (an enum), not typestate. Typestate relies on moves and on methods existing per concrete generic instantiation (impl Claim<Draft>), which TS's structural types can't express cleanly.

Check yourself

Why do the transition methods take self by value?

  • Because &self methods can't return a new value
  • So the old state is consumed, never reused
  • Because PhantomData values can't be borrowed at all
  • To copy the claim into the new state
After let s = draft.submit();, draft is moved: E0382 if you touch it.

What does size_of::<Claim<Approved>>() include for the state?

  • One byte for the state's discriminant
  • Nothing; PhantomData and the markers are zero-sized
  • A pointer to the state's marker type
  • A copy of each previous state's data
Typestate is free at run time.

Why doesn't Ledgerly use typestate for expenses?

  • Typestate needs unsafe code, which Ledgerly's lints forbid
  • The status comes from the database at runtime
  • Typestate doesn't work with async functions or methods
  • Java has no typestate, so parity would fail
A loaded row could be in any state, and wrong transitions must become 409 responses.
