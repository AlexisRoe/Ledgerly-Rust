Traits in depth

dyn compatibility and async in traits

Not every trait can be used as dyn Trait. Knowing why explains a pattern you've seen in Ledgerly's ports: methods returning BoxFuture instead of being async fn.

By the end of this lesson

You can predict whether a trait is dyn-compatible, fix it with where Self: Sized, and read and write a boxed-future port like MembershipLookup.

Static vs dynamic dispatch?

What a dyn Trait is

A &dyn Store is two pointers: one to the data, one to a vtable, a table with one function pointer per method. So every method must be callable through that table without knowing the concrete type. That rules out (Reference: dyn compatibility):

  • generic methods, fn put_all<I: IntoIterator>(…): one entry per possible I would be infinitely many;
  • methods returning Self or taking it by value (its size is unknown), such as fn new() -> Self or Clone;
  • async fn and -> impl Trait methods: each impl returns a different, unnamed type, so there's no single signature to put in the table.

Add where Self: Sized to such a method and it's excluded from the vtable: the trait becomes dyn-compatible, and the method is just unavailable on dyn Store. Otherwise: E0038.

Async methods behind dyn

Rust supports async fn in traits, but such traits can't be used as dyn. Ledgerly's ports must be (they're passed as Arc<dyn …> so tests can swap them), so they return one nameable type instead: a boxed future.

In Ledgerly

Read the alias inside out: a future (dyn Future<Output = T>) that may move between threads (Send), may borrow for 'a, stored on the heap (Box) and pinned there (Pin, lesson 102). The impl calls an async fn and boxes its future with Box::pin. The cost is one allocation per call, which is nothing next to a database round trip. The futures crate has the same alias, as futures::future::BoxFuture.

Where the comparison breaks

In TS, interface Lookup { roleOf(...): Promise<Role | undefined> } just works: every async function returns the same Promise type. In Rust each async fn returns its own anonymous future type, sized to hold exactly its local state. That's what makes Rust's futures allocation-free, and it's also why erasing them behind dyn needs a Box.

Check yourself

Which method makes a trait unusable as dyn unless marked where Self: Sized?

  • fn get(&self, key: &str) -> Option<String>
  • fn len(&self) -> usize
  • fn merge<T: Store>(&mut self, other: T)
  • fn clear(&mut self)
A generic method would need one vtable entry per T.

Why don't Ledgerly's ports use async fn role_of(…) directly?

  • async fn is not allowed inside traits at all
  • Traits with async fn can't be used as dyn
  • Boxed futures run faster than async fn futures
  • async fn cannot take a database connection argument
They're used as Arc<dyn MembershipLookup>, so they need one nameable return type.

What does Box::pin(fut) do in the impl?

  • Runs the future right away on a new task
  • Moves the future to the heap, pinned there
  • Copies the future so it can be awaited twice
  • Converts the future into a plain blocking function
It turns a concrete future into a Pin<Box<dyn Future…>>; still lazy.
