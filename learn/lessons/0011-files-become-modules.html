Basic syntax and code organisation

Files become modules

In TypeScript every file is a module the moment it exists. In Rust a file is only part of the program once a parent says mod name;.

By the end of this lesson

Given any .rs file in Ledgerly, you can find the mod line that pulls it in, and given a mod x; line, you can find the file it refers to.

Warm-up
What does //! document, compared with ///?
//! documents the enclosing module or crate. /// documents the next item.
What's the entry file of a library crate, and of a binary crate?
src/lib.rs and src/main.rs.

The module tree is declared, not discovered

A crate is compiled from one root file: lib.rs or main.rs. The compiler doesn't scan the folder. It follows mod declarations, and each one says "there's a child module called this; go find its code":

For mod events; written in src/lib.rs, the compiler looks for either (Book 7.5):

Declared inDeclarationFile (option A)File (option B)
src/lib.rsmod events;src/events.rssrc/events/mod.rs
src/lib.rsmod domain;src/domain.rssrc/domain/mod.rs ← Ledgerly
src/domain/mod.rsmod action;src/domain/action.rssrc/domain/action/mod.rs

Ledgerly uses a plain file for a module without children (events.rs, facade.rs) and a folder with mod.rs for one with children (domain/, web/). Think of mod.rs as a folder's index.ts.

In Ledgerly: one level down

So crates/expenses/src/domain/action.rs has the module path crate::domain::action. The tree mirrors the folders, but only because each level declares its children.

Modules that exist only sometimes

#[cfg(test)] is an attribute that means "only compile the next item when building tests". The test files are real modules, but they don't exist in the production binary at all. (pub(crate) is visibility; that's lesson 13.)

Where the comparison breaks
  • A file nobody declares is ignored. Create src/domain/new_rule.rs and forget mod new_rule;: it isn't compiled, not even checked. No error, no warning. rust-analyzer shows a hint that the file isn't part of the crate.
  • Modules aren't imports. In TS, import both loads a file and brings names into scope. In Rust, mod adds a file to the tree (once, in its parent), and use creates shortcuts to names (anywhere, any number of times). Next lesson.
Try it
  1. Open crates/shared/src/lib.rs and list its mod lines. For each, predict whether the code lives in x.rs or x/mod.rs, then check in the file explorer.
  2. What is the module path of crates/shared/src/money/currency.rs? Which line makes it part of the crate?
Answer to 2
crate::money::currency. Two lines put it in the tree: pub mod money; in crates/shared/src/lib.rs and mod currency; in crates/shared/src/money/mod.rs. Because that second line has no pub, other crates can't name ledgerly_shared::money::currency. You'll see how they reach Currency anyway in lesson 13.

Check yourself

You add crates/expenses/src/domain/limits.rs with a function, but nothing else. What happens on cargo build?

  • It's compiled and can be used everywhere
  • The build fails with an orphan-file error
  • The file is silently ignored by the compiler
  • It becomes a new crate in the workspace
Only files reached through mod declarations are compiled. Add mod limits; to domain/mod.rs.

Where is the code for mod web; declared in crates/expenses/src/lib.rs?

  • src/lib/web.rs
  • src/web.rs or src/web/mod.rs
  • src/web/index.rs
  • web.rs anywhere in the crate
A child of the crate root lives next to it: src/web.rs, or src/web/mod.rs when it has children of its own. Ledgerly uses the latter.

What does #[cfg(test)] mod tests; achieve?

  • Marks the module as deprecated outside tests
  • Compiles the module only for test builds
  • Runs the module's code before every test
  • Hides the module from rust-analyzer's index
cfg is conditional compilation. Under cargo build the module doesn't exist. Under cargo test it does.
