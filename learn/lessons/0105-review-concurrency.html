Recall

Answer out loud, then open
Send vs Sync?
Send: may be moved to another thread. Sync: &T may be shared between threads. (98)
The four Tokio channels and one use for each?
mpsc job queue, oneshot a reply, watch current state (shutdown flag), broadcast events to every listener. (100)
What two things must poll do when it returns Pending?
Not block, and arrange for the waker to be called when progress is possible. (101)
Why are compiler-generated futures pinned?
They may hold references into themselves, so they must not move once polled. (102)

Mixed questions

A handler keeps a RefCell in its state. What does the compiler say?

  • Nothing, as long as only one request uses it
  • An error: RefCell isn't Sync, so it can't be shared
  • A warning that suggests replacing it with a Cell
  • Nothing, but every request panics on its first use
axum shares state across worker threads, so it must be Send + Sync. (84, 98)

You need to cache keys fetched over HTTP, fetching at most once at a time. Which lock?

  • std::sync::Mutex
  • tokio::sync::Mutex
  • std::cell::RefCell
  • AtomicBool
The lock is held across the fetch's .await, like Ledgerly's Issuer. (99)

(Ownership) In a for loop you spawn a Tokio task per id, using a shared Arc<Pool>. What goes inside the loop?

  • Nothing special; the task simply borrows the pool
  • let pool = Arc::clone(&pool); then async move
  • pool.lock().await, then spawn the task with the guard
  • Box::pin(pool), then spawn with the pinned pool
Each task owns its own Arc: 'static and cheap. (82, 97)

A select! loop reads a socket with read_exact in one branch and a tick in the other. What can go wrong?

  • Nothing; every Tokio method is cancel-safe anyway
  • A tick cancels a half-done read, losing bytes
  • The tick branch never runs while it's reading
  • The socket closes after every loop iteration
read_exact isn't cancel-safe. (103)

(Errors) spawn_blocking(f).await returns Result<T, JoinError>. When is it Err?

  • When f returned a Result that was Err
  • When f panicked, or the task was cancelled
  • When the blocking pool has no free threads
  • When f took longer than the default timeout
The outer Result is about the task; f's own result is inside T. (25, 104)
