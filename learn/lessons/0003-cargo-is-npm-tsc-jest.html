Setting up and the toolbox

Cargo is npm + tsc + jest

One tool installs dependencies, compiles, runs, tests and documents. Its manifest is Cargo.toml.

By the end of this lesson

You can create, build, check, run and test a Rust project with cargo, and read a crate's Cargo.toml line by line.

Warm-up
Which file decides the Rust version inside Ledgerly, and what's its Node equivalent?
rust-toolchain.toml (channel = "1.99.1"), like .nvmrc.
What is an edition?
An opt-in language dialect per crate (2024 in Ledgerly). Editions mix freely between crates.

Note what's missing: there's no cargo install step for dependencies. cargo build downloads what Cargo.lock lists from crates.io (the npm registry of Rust) and compiles them from source into target/. target/ is node_modules and dist in one folder, and it gets big: delete it any time, and the next build recreates it.

Reading a manifest

  • [package] is the top of package.json. x.workspace = true means "take this from the root Cargo.toml" (next lesson).
  • [dependencies] and [dev-dependencies] mean what they do in npm: dev-dependencies are only for tests, examples and benchmarks.
  • features = ["macros"] has no npm equivalent. A feature switches on an optional, compile-time part of a crate. Code behind a disabled feature isn't compiled at all (Cargo book: features). Ledgerly's testing feature exposes test helpers such as a fixed clock, and only the dev-dependencies turn it on.
  • Version strings default to caret rules: "1.0.229" means ^1.0.229 (specifying dependencies).

Cargo.lock

The same job as package-lock.json: exact versions of the whole dependency tree, committed for applications. Ledgerly's lock lists 418 packages. --locked (used in the justfile) is npm ci: fail if the lock would have to change (Cargo.toml vs Cargo.lock).

Where the comparison breaks
  • One copy per compatible version range. npm happily nests five copies of a package. Cargo unifies semver-compatible requirements into one version, and only builds a second copy when the requirements are incompatible (a different major, or a different minor below 1.0, such as 0.4 vs 0.5).
  • Packages vs crates. A package (one Cargo.toml) contains one or more crates, the unit of compilation: a library crate (src/lib.rs) and/or binary crates (src/main.rs, src/bin/*.rs). Ledgerly's crates/app package has both: the library ledgerly_app and the binary ledgerly.
  • Hyphens become underscores. The package ledgerly-expenses is written ledgerly_expenses in Rust code, because - isn't allowed in identifiers.

Check yourself

You only want to know whether your change type-checks. What's the fastest command?

  • cargo check
  • cargo build
  • cargo test
  • cargo run
cargo check runs every analysis (types, borrow checker) but skips code generation. It's the tsc --noEmit of Rust.

What does sqlx = { workspace = true, features = ["macros"] } turn on?

  • A newer sqlx version taken from the workspace
  • An optional compile-time part of the sqlx crate
  • A runtime flag read from the environment variable
  • A plugin installed separately from crates.io later
Features are compile-time switches the crate author defines. Here they enable sqlx's query!/query_as! macros, which expenses uses for checked SQL.

How do you refer to the package ledgerly-shared in Rust code?

  • ledgerly-shared
  • ledgerly_shared
  • LedgerlyShared
  • @ledgerly/shared
Hyphens aren't valid in identifiers, so cargo exposes the crate as ledgerly_shared, e.g. use ledgerly_shared::clock::Clock;.

Where do compiled dependencies end up?

  • In a global cache shared by projects
  • Inside a node_modules-like folder for each crate
  • Inside target/, built from their source code
  • They're downloaded as prebuilt binaries per platform
Sources are cached in ~/.cargo/registry, but compiled output lives in each project's (or workspace's) target/. That's why the first build is slow and later ones are incremental.
