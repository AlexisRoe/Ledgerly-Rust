Module and crate boundaries

Where you draw module and crate lines decides what the compiler can enforce for you, how fast you build, and what you promise other code. Ledgerly is a worked example of drawing them on purpose.

By the end of this lesson

You can decide between a module and a separate crate, use features for optional code, and know what semver means for a Rust library's public API.

Split into crates when you want a boundary the compiler enforces, or when build times suffer. Inside a crate, modules plus pub(crate) are enough.

Java needs a test (ArchUnit) to catch expenses reaching into receipts' internals. In Rust, the internals are simply not visible, and a dependency cycle can't even be declared. The architecture test in crates/app/tests/architecture.rs (lesson 72) checks the remaining rule: which arrows exist.

Features: optional code

In Ledgerly

Code under #[cfg(any(test, feature = "testing"))] (like FixedClock, lesson 84) only exists when a crate asks for it, here in expenses' [dev-dependencies]. Features are additive: Cargo builds one copy of each crate with the union of all features requested anywhere in the build, so a feature must only add things, never change or remove behaviour (Cargo: features).

Semver for public APIs

For a published library, every pub item is a promise. Breaking changes need a new major version (for 0.x crates: a new minor). Some are less obvious than in TS: adding a variant to a public enum breaks other crates' exhaustive matches (unless it's #[non_exhaustive]), adding a public field breaks struct literals, and adding a trait impl can make method calls ambiguous. The Cargo semver reference lists them all; the cargo-semver-checks tool checks them. Ledgerly publishes nothing (publish = false), so its crates can change freely together.

Where the comparison breaks

In a TS monorepo, package boundaries are enforced by convention and lint rules (exports maps, eslint-plugin-boundaries), and deep imports can sneak past them. A Rust crate boundary can't be bypassed: there is no path to a private item. That makes "one crate per module" a cheap, strong architecture tool.

Check yourself

Why does Ledgerly use a crate, not a module, per business module?

  • Because Cargo can't compile very large single crates
  • Crate walls turn boundary violations into compile errors
  • Because modules can't contain async functions or traits
  • Because each crate is deployed as a service
What Java checks with ArchUnit, Rust's compiler checks for free.

Why must Cargo features be additive?

  • Because features can only add dependencies, nothing more
  • One build gets the union of all requested features
  • Because removing code with features is a syntax error
  • Because cargo-deny rejects any features that remove things
If crate A turns a feature on, crate B gets it too. It must not break B.

In a published library, which change is breaking?

  • Adding a new public function to a module
  • Adding a variant to an exhaustive public enum
  • Adding a private field to a private struct
  • Fixing a typo in a doc comment's example
Callers' exhaustive matches stop compiling.
