Functions, closures and iterators

Function signatures in depth

A Rust signature tells you more than a TS one: who owns each argument, whether the call can fail, whether it's async, and whether the result may be ignored. Learn to read it like a contract.

By the end of this lesson

You can read any function header in Ledgerly, including pub(crate) async fn, const fn, #[must_use], impl Into<String> and &dyn Clock parameters, and summarise its contract in one sentence.

Flexible parameters: impl Trait

message: impl Into<String> means "any type that can be converted into a String". Callers can pass a literal "Merchant is required" or a format!(…) result, and .into() does the conversion. It's like accepting string | String without overloads. You'll meet traits properly in section 7. For now, read impl X in a parameter as "anything that implements X".

In Ledgerly: no default parameters, no overloads

Rust has neither optional parameters (f(a, b = 1)) nor overloading. Ledgerly uses the usual substitutes:

  • Different names: Merchant::new (validates) vs Merchant::stored (trusts the database); Money::new vs Money::parse.
  • Option parameters: reason: Option<&str> in TransitionExpense::execute, because only reject has a reason.
  • A struct of arguments: NewExpense and the …Command structs bundle many fields, as you'd pass an options object in TS.
Where the comparison breaks

In TS the signature says nothing about mutation, ownership or failure, so you read the body (or hope for good JSDoc). In Rust most of that is in the types, which is why Ledgerly's doc comments can be short. Return types are never inferred, so the signature is always complete.

Check yourself

What can a caller pass for message: impl Into<String>?

  • Only a String value that the caller owns already
  • A &str literal, a String, or other convertible types
  • Any value at all, converted with a toString call
  • Only a reference to a String, never a literal
Anything implementing Into<String>, which includes &str and String. The function calls .into() to get a String.

Rust has no default parameter values. How does Ledgerly handle "reason only for reject"?

  • Two overloads of execute, with and without reason
  • An Option<&str> parameter that is None for others
  • A global variable that holds the current reason
  • A default value written as reason = "" inline
reason: Option<&str>, and the reject branch uses reason.unwrap_or_default().

What does #[must_use] on fn status(&self) -> ExpenseStatus do?

  • Forces callers to handle an error the function returns
  • Warns when a caller calls it and ignores the result
  • Makes the function run at compile time if possible
  • Prevents the function from being called more than once
Calling a getter and throwing the result away is almost always a bug, and the lint catches it.
