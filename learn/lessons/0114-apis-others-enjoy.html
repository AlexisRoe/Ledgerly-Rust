Designing Rust code

APIs others enjoy

Rust has strong naming and design conventions, written down in the official API Guidelines. Following them makes your types feel like std's: readers guess correctly what a method costs and returns before opening it.

By the end of this lesson

You can name conversion methods by their cost, choose which traits a public type should implement, and use #[must_use] and #[non_exhaustive] where they help. Then you review a small API.

(API Guidelines: naming.) Also: getters have no get_ prefix (expense.status()), iterators are iter / iter_mut / into_iter, constructors are new, with_…, from_…, and conversions that can fail are try_… or parse.

Traits a public type should have

Derive eagerly what makes sense: Debug always (even for types holding secrets, with a hand-written redacting impl), Clone, PartialEq/Eq, Hash, Default where meaningful, Display for anything users see, serde behind a feature in libraries. Callers can't add these themselves later: the orphan rule (lesson 91).

Two attributes

  • #[must_use] on functions whose only point is their result. Ledgerly marks pure getters like Money::amount with it: calling one and ignoring the value is certainly a bug.
  • #[non_exhaustive] on a public enum or struct in a library means "I may add variants or fields". Other crates must then write a _ arm and can't build the struct literally. That's the opposite of Ledgerly's choice: inside one workspace, it wants every match to break when a variant is added (lesson 77).

Where the comparison breaks

TS naming conventions are mostly about style. Rust's encode facts the type system also checks: an into_ method takes self, so the compiler will stop you using the value afterwards, and as_ returns a borrow. When names and signatures agree, readers can trust the name.

Why doesn't Ledgerly put #[non_exhaustive] on ExpenseError?

  • Because the attribute only works on struct types
  • It wants matches to break on new variants
  • Because thiserror cannot derive non_exhaustive enum types
  • Because the enum is private to its crate
Inside one workspace, exhaustive matches are the safety net.
