if is an expression

Rust has no ternary operator because it doesn't need one: if … else … itself produces a value.

By the end of this lesson

You can write and read let x = if … { a } else { b };, know why both branches must have the same type, and recognise the guard-clause style Ledgerly uses for validation.

Ternary → if expression

Each branch is a block, and its last expression (no semicolon) is the branch's value (Book 3.5). The reject endpoint is the only transition with a JSON body (the reason), so this decides how the router reads the request.

Rules that follow from "if is an expression":

  • Both branches must have the same type. if ok { 1 } else { "no" } is error E0308. TS would infer number | string.
  • An if used as a value needs an else, because otherwise there's nothing to produce when the condition is false. (An if without else has type (), fine as a statement.)
  • No parentheses around the condition. rustfmt removes them and the compiler warns. Braces are always required, even for one line.

Guard clauses: if + early return

The same guard style you'd use in TS: check, bail out, continue. Here, though, the bail-out is a return Err(…) rather than a throw. The order of checks is deliberate: it decides which error a client sees first.

Where the comparison breaks

No truthiness, no &&/|| returning operands, no ternary. That sounds like less, but one construct does the job of three. Also, if let (lesson 33) and match (lesson 31) are expressions too, so you'll often see let x = match … { … }; where TS needs a let plus a switch that assigns in every case.

Check yourself

Does this compile? let size = if large { 100 } else { "small" };

  • Yes, size becomes a union of both types
  • Yes, the number is converted to text automatically
  • No, both branches must produce the same type
  • No, if can never be used as a value
The branches are an integer and a &str, which gives E0308 (mismatched types). Rust has no ad-hoc unions; you'd need an enum.

What's wrong with let fee = if premium { 0 };?

  • The condition needs parentheses around it
  • Without else there's no value for false
  • Integer literals can't appear inside an if
  • Nothing; fee is zero or uninitialised then
An if without else has type (), so the then branch's 0 doesn't match. Add else { 5 }.

In Merchant::new, why does the blank check come before the length check?

  • Rust evaluates if statements in reverse order
  • The order decides which message a client sees
  • Length checks need the text trimmed in place
  • It doesn't matter; the compiler reorders them
Guards run top to bottom and the first failure returns. Ledgerly keeps Java's order so the same input gets the same error.
