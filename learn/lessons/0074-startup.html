Reading Ledgerly end to end

Startup: from main to a listening server

Lesson 1 showed you main and asked you not to read every token. Now read all of it, plus run, and you'll know the life of the process from docker run to SIGTERM.

By the end of this lesson

You can list the startup steps in order, say what makes each one fail and how that failure is reported, and explain graceful shutdown.

Warm-up
Why isn't main async?
Some setup (telemetry's blocking client) must happen before the runtime exists. (62)
What do tokio::join! and select! do in serve?
join! runs both listeners and the shutdown trigger to completion; select! races a server against its drain deadline. (63)

Part 1: synchronous setup in main

  1. Config from environment variables, with Java's names (SPRING_DATASOURCE_URL, …). &ProcessEnvironment is a &dyn Environment [49, 53]. All problems are collected and reported at once, and secrets are already SecretStrings [71].
  2. Logging: JSON lines in Spring's ECS format [71]. if let Err [33].
  3. Panic hook: logs the panic's location, not its message [57].
  4. Telemetry (OpenTelemetry exporter), before the runtime.
  5. Runtime: tokio::runtime::Builder::new_multi_thread(), then block_on(run(…)) [62].

Every failure goes through failed_to_start, which prints Spring Boot's "APPLICATION FAILED TO START" banner to stderr and returns ExitCode::FAILURE. There are no panics and no process::exit deep in the code [1, 25].

Part 2: async startup in run

  1. stop_signal(): a lazy future that completes on SIGTERM or Ctrl-C [63].
  2. database::connect: the sqlx pool [69].
  3. database::verify: compares the database's Flyway history with the migrations embedded by build.rs [14]. A schema this build doesn't know means refusing to start.
  4. seed::demo_data: in the local profile, an empty database gets a demo team.
  5. App::bind: builds every module (the wiring of section 13), and opens the API and management ports.
  6. app.serve(stop): serves until the stop signal, drains running requests for up to 30 s, stops the management port last, and aborts background tasks [63, 64].
  7. pool.close(), then back in main: drop(runtime) and telemetry.shutdown() [36].

Each ? converts its error into StartupError through #[from] variants [55, 56]: Io, Database, Schema, Identity, Seed, RateLimit. main then prints it.

Compared with a Node service

A Node index.ts often does the same steps with top-level await and a process.on("SIGTERM") handler. The Rust version is longer but explicit about two things Node leaves implicit: when the runtime exists, and what order things shut down in (stop accepting → drain → stop management → close the pool → stop the runtime).

Try it (needs Docker)
  1. just deps, then just run. Watch the "Started Ledgerly" log line with apiPort and managementPort.
  2. Press Ctrl+C and read the shutdown log lines. Which step in serve prints "Commencing graceful shutdown"?
  3. Run the binary with a bad database URL: SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:1/x just run. Which StartupError variant do you see in the banner?

Check yourself

The database schema is newer than this build knows. What happens?

  • The app starts and logs a warning only
  • database::verify fails and the app refuses to start
  • The app migrates the database to its version
  • Requests fail one by one with a 500
The check runs before the ports open (ADR 0006), and Rust never changes the schema.

How does a missing SPRING_DATASOURCE_URL reach the console?

  • A panic inside the config reader prints it
  • An Err from Config, printed by failed_to_start later
  • A log line at error level from tracing
  • process.exit is called inside the config reader itself
Config::from_environment returns Err(ConfigError), and main matches it and calls failed_to_start. Logging isn't even set up yet.

In what order does shutdown happen?

  • Pool closes, then API stops, then requests drain
  • API drains requests, management stops, then pool closes
  • Runtime drops first, then everything stops at once
  • Management stops, then the API, then the pool
api_then_management stops management after the API; run closes the pool after serve returns; main drops the runtime last.
