The libraries Ledgerly is built on

axum and Ledgerly's Routes

axum is the web framework (think Express or Fastify), and tower provides the middleware stack. Ledgerly adds a thin Routes table on top so that it can match Spring's routing behaviour exactly.

By the end of this lesson

You can find where an endpoint is registered, read its handler's arguments ("extractors"), and list the middleware a request passes through before it gets there.

Express → axum

A handler is an async fn whose parameters are extractors: types that know how to pull themselves out of the request. State(api) destructures the shared state (a pattern in parameter position, lesson 32), CurrentUser comes from the authentication middleware, PathParameters holds teamId/expenseId. Where Express hands you one req object, axum's handler signature lists exactly what it needs (axum: extractors). action isn't an extractor: the move closure from lesson 45 fills it in.

Why Ledgerly's own Routes instead of axum's Router directly? Paths like …/{expenseId}:approve, the exact 404/405/415 answers and the order of checks have to match Spring byte for byte, so routing is hand-written and checked against api/openapi.yaml by tests (ADR 0014).

Middleware: tower layers

Like app.use(…), but read it bottom-up: each .layer wraps everything above it, so the last one added (tracing) sees the request first. The doc comment above layered in crates/app/src/lib.rs lists the order from the outside in.

Where the comparison breaks

In Express, a handler can read anything from req at any time, and forgetting res.send hangs the request. In axum the handler's types declare what it reads and what it returns. A handler that returns nothing sendable doesn't compile. Middleware is typed too: a tower Layer wraps a Service, Rust's equivalent of (req) => Promise<res>.

Check yourself

Where does the user: CurrentUser argument of a handler come from?

  • The handler reads the Authorization header itself directly
  • An extractor that the authentication middleware fills in
  • A global variable holding the last logged-in user
  • The ExpensesApi state, which stores the current user
The authenticate layer runs first and records the caller; the CurrentUser extractor hands it to the handler.

In .layer(A).layer(B), which middleware sees the request first?

  • A, because it was added first
  • B, because it wraps A
  • Both at once, in parallel
  • Whichever is registered as global
Each layer wraps the service built so far, so the last-added layer is the outermost.

You add an endpoint to the expenses module. Where do you register it?

  • In crates/app/src/main.rs, next to the runtime builder
  • In ExpensesApi::routes in the expenses web module
  • In api/openapi.yaml, which axum reads at startup
  • In a new crate for one endpoint
Each module owns its route table. The app only merges them. (And the contract change itself happens in Ledgerly-Java first.)
