Ownership and borrowing

Borrowing: & and &mut

Moving everything around would be exhausting. A reference lets a function use a value without taking it. There's one rule to learn: many readers or one writer, never both.

By the end of this lesson

You can read every & and &mut in a Ledgerly signature, say what the callee may do with it, and predict when the borrow rule rejects code.

Two kinds of reference

&valueshared referencereadany number of other &
&mut valuemutable (exclusive) referenceread and changenothing else, not even a reader

Plus one more rule: a reference must never outlive the value it points to. Together these let the compiler rule out dangling pointers and data races at compile time (Book 4.2). The & in a type (&str, &[T], &Expense) and the & in an expression (&expense) are the same thing: "a borrow of".

In Ledgerly: borrows in one use case
  • &mut transaction is lent to actor, then to load, then to update, one after another. Each borrow ends when the call returns, so the next one is allowed. The function keeps ownership and commits at the end.
  • &expense: update only reads the expense to write it to the database. Two borrows of different values at once (&mut transaction and &expense) are fine.
  • &self in execute(&self, …): many requests can run the same use case at once, because none of them changes it.

Small conveniences you'll see

  • Auto-borrow on method calls: expense.status() works although status takes &self. Rust inserts the &. With approve(&mut self) it inserts &mut, which requires let mut expense.
  • Dereference with *: from a &u32 you get the u32 with *amount, as in ExpenseError::RuleViolated(rule) => …*rule. Comparisons and printing usually do it for you.
  • &String works where &str is expected, and &Vec<T> where &[T] is expected ("deref coercion").
Where the comparison breaks

TS's readonly is a promise about one alias. Another variable can still mutate the same object while you read it. Rust's rule is about the value: while any & exists, nobody can mutate it, and while a &mut exists, nobody else can even look. That one rule is what makes Ledgerly's multi-threaded request handling safe without locks around every object.

Check yourself

A function signature says fn publish(&self, tx: &mut PgConnection, event: &ExpenseEvent). What may it do?

  • Change the event and keep it after returning
  • Use the connection to write; only read the event
  • Close the connection by taking ownership of it
  • Change itself and the event, but not the connection
&mut allows changes, & only reading, and neither gives ownership, so nothing can be kept or dropped by the callee.

  • Yes, because rejections was declared with let mut

Error E0502. And it's a real bug, not pedantry: push may reallocate the vector, leaving oldest pointing at freed memory.

Why can execute(&self, …) serve many requests at the same time?

  • Each request gets its own copy of the case
  • Shared references allow any number of readers at once
  • The method is async, so borrow rules don't apply
  • A Mutex inside serialises all of the incoming requests
Many &self borrows can coexist. If execute took &mut self, requests would have to take turns.
