Rust vs TypeScript: the big picture

Before any syntax: what changes when you trade Node + tsc for a compiled language with no garbage collector.

By the end of this lesson

You can name the five big differences between running TypeScript and running Rust, and say which line of Ledgerly's main function each one explains.

What happens when you run your code

In TypeScript, tsc checks your types and then throws them away. What runs is JavaScript, inside an engine (V8 in Node) that interprets and JIT-compiles it, with a garbage collector freeing memory behind you and an event loop that's always there.

Rust's compiler, rustc, checks your types and then uses them to produce native machine code: one executable file for one operating system and CPU. No engine, no garbage collector, no built-in event loop. Ledgerly's whole backend is a single binary called ledgerly in a small container image (the Book's introduction covers who Rust is for).

Five differences, all in one function

Here is the start of Ledgerly's main. Don't try to read every token yet. Look for the five ideas from the table.

  1. Errors are values. Config::from_environment doesn't throw. It returns either Ok(config) or Err(error), and match handles both. Forgetting the Err case doesn't compile.
  2. The async runtime is a library. In Node the event loop just exists. Here main builds a Tokio runtime itself and hands it the async function run (block_on means "run this future until it finishes").
  3. Memory is freed at a known point. drop(runtime) destroys the runtime right there, not "whenever the GC gets to it". Usually Rust inserts the drop for you at the end of a scope. Here it's written out because the timing matters.
  4. The &. &error lends the error to failed_to_start without giving it away. This is borrowing, the idea TypeScript has no word for.
  5. A typed exit. main returns an ExitCode, not process.exit(1) from somewhere deep in the stack.
Where the comparison breaks

TypeScript is a type layer on top of a dynamic language. If tsc complains you can still run the JavaScript, and any switches checking off. Rust has no "run it anyway": the type checker and the borrow checker (which checks how memory is shared) must both agree before any binary exists. That's why Rust feels strict at first. In exchange, a whole class of bugs (null dereferences, use after free, data races, unhandled errors) can't reach production.

Why bother, for a backend?

  • Small and fast: one binary, no runtime to install, low memory use. The ledgerly image is about 39 MB.
  • Refactoring with a net: add a variant to an enum, and the compiler lists every match that must now handle it. You'll use this in the capstone ().
  • Rules as types: Ledgerly makes a TeamId and an ExpenseId different types, so swapping them doesn't compile ().

Comprehensive Rust's "Why Rust?" page sums up the trade-off well.

Check yourself

What does the Rust compiler produce for Ledgerly?

  • One native binary per platform
  • JavaScript plus a type map
  • Bytecode for a virtual machine
  • Source files for an interpreter
rustc compiles to machine code for one target platform. There is no VM or interpreter at runtime, which is why the image needs no Rust installation.

In TypeScript a failed config read would throw. What does Ledgerly's Config::from_environment do instead?

  • Panics and the process just stops
  • Returns a value: Ok(config) or Err(error)
  • Returns null and logs a warning
  • Sets a global error flag instead
Rust has no exceptions. A function that can fail returns Result<T, E>, and the caller must handle both cases, here with match.

Why does Ledgerly's main build a Tokio runtime itself?

  • Tokio acts as Rust's garbage collector here
  • The compiler requires it for every program
  • Rust has no built-in async event loop
  • It makes the binary smaller and faster
Rust's language has async/await, but the scheduler that runs futures comes from a library. Ledgerly uses Tokio (section 10).

Which of these has no equivalent in Rust?

  • Generics with constraints like extends
  • A value that is null
  • Union-like types with several variants
  • Interfaces that types can implement
Rust has generics with bounds, enums (much stronger than unions) and traits (interfaces). It has no null: possible absence is spelled Option<T>, and the compiler makes you handle None.
