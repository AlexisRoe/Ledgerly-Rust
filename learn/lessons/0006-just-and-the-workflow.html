just and the repo's workflow

The justfile is Ledgerly's "scripts" section: every task a developer or CI runs, with a comment saying why.

By the end of this lesson

You can list Ledgerly's tasks, say what just check runs and in which order, and know which tasks need Docker.

Recipes are npm scripts

A recipe is name: dependencies followed by indented commands. check has no commands of its own: it just runs seven other recipes in order and stops at the first failure. The comment line above a recipe becomes its description in just --list (just manual).

While you're editing, the fast loop is just cargo check (seconds), then cargo test -p <crate> for the crate you touched. Run just check before you commit. goes deeper.

Two more pieces around it

  • .pre-commit-config.yaml is husky + lint-staged: on git commit it runs cargo fmt, Prettier on YAML/JSON, and gitleaks (a secret scanner). It only works after you run pre-commit install once.
  • .cargo/config.toml sets environment variables for every cargo command in the repo. Ledgerly sets SQLX_OFFLINE = "true" so that SQL checking at compile time reads the committed .sqlx/ folder instead of needing a live database ().
Where the comparison breaks

npm scripts are plain strings run by sh. Recipes can also take arguments (parity url="":) and use a different shell per recipe. Ledgerly sets bash with -euo pipefail on line 1, so a failing command in a pipe fails the recipe. just isn't a Rust tool: it's a general command runner that happens to be written in Rust. Cargo has no task runner of its own.

Try it
  1. Run just in the repo root and read the list.
  2. Open justfile and find the test recipe. Why does it run two commands? (Answer is in its comment.)
  3. Run just fmt-check and just clippy. Both work without Docker.

Check yourself

What does the recipe line check: vendor-check fmt-check clippy … mean?

  • Run those seven tasks at the same time
  • Run those tasks in order, stopping at a failure
  • Define seven aliases that all point to check
  • Skip those tasks when check is called by CI
Names after the colon are dependencies, run in order before the recipe's own (here empty) body.

You changed one function in expenses. What's the fastest useful first check?

  • just verify
  • just check
  • cargo check
  • just up
cargo check takes seconds and catches type and borrow errors. Save just check for before a commit, and just verify (the full parity suite) for milestones.

Why does .cargo/config.toml set SQLX_OFFLINE = "true"?

  • So the app never connects to a database
  • So tests use an in-memory SQLite instead
  • So builds check SQL without a live database
  • So migrations run offline before every build
sqlx checks queries at compile time. Offline mode reads the saved query metadata in .sqlx/, so CI and the image build need no Postgres.
