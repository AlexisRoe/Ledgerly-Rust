The libraries Ledgerly is built on

sqlx: SQL checked at compile time

No ORM. Ledgerly writes plain SQL, and sqlx's macros check every query against the real schema while compiling: a misspelled column or a wrong parameter type is a compile error.

A checked update

  • At compile time, query! asks Postgres (or the saved .sqlx/ metadata) to prepare the statement. Unknown column, wrong number of $n, or a Rust argument type that doesn't fit the column → compile error.
  • where team_id = $1 and id = $2: every read and write is scoped to the team (OWASP API1, a hard rule of the project).
  • and version = $12 + rows_affected() == 0 is optimistic locking: if someone else changed the expense since you read it, nothing is updated, and the client gets 412.
  • &mut *connection re-borrows the connection so it can be used again afterwards (lesson 39).
In Ledgerly: rows into typed structs

sqlx::query_as!(ExpenseRow, "select …", team, id) (in find, lesson 25) checks that the selected columns match these fields and types, with nullable columns as Option. The row type is private and deliberately "dumb" (strings, UUIDs). TryFrom<ExpenseRow> then turns it into domain types, validating as it goes. In SQL, as "count!" is sqlx syntax for "trust me, not null".

Offline mode: .sqlx/

Requiring a running database for every build would be painful (CI, the Docker image build). So the query metadata is saved as JSON files in .sqlx/ (66 of them), committed, and used when SQLX_OFFLINE=true. When you add or change a query, run just deps (Postgres) and then just sqlx-prepare to regenerate them, and commit the result. A stale .sqlx fails the build with a clear message (sqlx docs: offline mode).

Where the comparison breaks

Most TS stacks find SQL mistakes at runtime, or trust generated types that can drift from the database. sqlx checks against the actual schema, here Ledgerly-Java's migrations, which Rust must never change. The cost: queries must be string literals known at compile time. Dynamic queries (the list endpoint's optional filters) use QueryBuilder and are checked by tests instead.

Check yourself

You misspell a column, set merhcant = $7. When do you find out?

  • When the parity suite runs the update endpoint
  • At compile time, from the query! macro
  • When Postgres rejects the query in production
  • Never; Postgres silently ignores the unknown column
The macro prepares the statement against the schema while compiling.

What does rows_affected() == 0 mean after the versioned update?

  • The database connection dropped in the middle of the update
  • The version didn't match: someone else changed it first
  • The new values were identical to the stored ones
  • The expense is in another team, which is allowed
Optimistic locking: no row matched version = $12 (or the expense is gone), so it's a Conflict → 412.

You changed a query. What else must be committed?

  • A new Flyway migration that changes the schema
  • The regenerated .sqlx metadata from just sqlx-prepare
  • An updated Cargo.lock with a new sqlx version
  • Nothing; queries are only re-checked at runtime anyway
Offline builds read .sqlx/. And Rust never changes the schema; that happens in Ledgerly-Java.
