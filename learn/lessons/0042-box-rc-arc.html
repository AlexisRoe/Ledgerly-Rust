Ownership and borrowing

Shared ownership: Box, Rc, Arc

"One owner" is the default, not a prison. Smart pointers put a value on the heap, and Arc gives it many owners, which is how every JS object behaves.

By the end of this lesson

You can explain why Ledgerly passes Arc<dyn Clock>, Arc<dyn Publisher> and PgPool around and clones them freely, and what Box::new(…) is doing in main.

Three smart pointers

TypeOwnersThreadsUsed for
Box<T>oneanyput a value on the heap: values whose size isn't known at compile time (Box<dyn Trait>), recursive types
Rc<T>many (reference counted)one thread onlyshared data inside single-threaded code; rare in a server
Arc<T>many ("atomically" reference counted)anyshared data across threads and tasks: Ledgerly's services

Arc::clone(&x) or x.clone() adds an owner (count + 1), and dropping a clone removes one. When the count hits zero, the value is dropped. It's a tiny, predictable garbage collector for one value. Arc only gives shared, read-only access; to change the inside you add a lock, Arc<Mutex<T>> (lesson 64) (Book 15.4, Arc docs).

In Ledgerly: one clock, many users

Every use case holds the same clock, the same membership lookup, the same event publisher. Who owns them? All of them together. That's exactly Arc. In TS you'd just pass the object, and the GC would sort out ownership. Here it's written down, and the .clone() calls in ExpensesApi::new are those extra owners being created.

dyn Clock means "some type implementing the Clock trait": the real SystemClock in production, a FixedClock in tests. Its size isn't known at compile time, so it must sit behind a pointer (Arc or Box). That's lesson 53.

A closure has a compiler-generated type of unknown size. Box::new puts it on the heap so set_hook can store it, with one owner.

Where the comparison breaks

In JS, every object is effectively in an Arc: on the heap, shared, freed when unreachable. Rust makes you choose per value, and the default (a plain value with one owner) is the cheapest. One thing Arc can't do that the GC can: collect cycles. Two Arcs pointing at each other never reach zero. Ledgerly's object graph is a tree (app → services → clock/pool), so it never comes up.

Check yourself

Why Arc<dyn Clock> and not Rc<dyn Clock> in Ledgerly?

  • Rc can't hold trait objects such as dyn Clock
  • Requests run on many threads; Rc is single-threaded
  • Arc is faster than Rc in every single case
  • Rc has been deprecated since the 2024 edition
Tokio runs handlers on a thread pool. Rc's counter isn't thread-safe, and the compiler refuses to send it between threads (it's not Send).

What happens on let c2 = clock.clone(); with clock: Arc<dyn Clock>?

  • A second, independent clock object is created from it
  • The count goes up; both point to one clock
  • The original clock is moved into c2 and gone
  • The clock is copied onto the stack of c2
Cloning an Arc clones the pointer, not the value.

You need a shared counter that many requests increment. Which type?

  • Arc<u64>
  • Box<u64>
  • Arc<Mutex<u64>>
  • Rc<u64>
Arc alone allows only shared, read-only access. Mutation through many owners needs a lock (or an atomic integer type).
