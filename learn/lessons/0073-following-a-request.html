Reading Ledgerly end to end

Following one request: submit an expense

POST /api/v1/teams/{teamId}/expenses/{expenseId}:submit, from the socket to the database and back. Every step uses something you've learned; the lesson numbers are in brackets.

By the end of this lesson

You can follow any Ledgerly endpoint through its layers yourself, using VS Code's Go to Definition, and say at each step what can make the request fail and with which status.

The route

  1. Middleware (): a tracing span with a trace id [71]; the JSON body limit; security headers; CORS; the per-address rate limit; authentication turns the bearer token into a CurrentUser or answers 401; the per-user rate limit (429); the panic catcher [57].
  2. Routing (shared/src/web/routing.rs): the path matches the template registered in ExpensesApi::routes for Action::Submit. Its handler is a move closure that remembers the action [45, 70].
  3. Handler transition (): extractors deliver the state, user and path parameters. team(&parameters)? parses the UUIDs (400 if malformed). Submit has no body [29]. It calls the use case and maps any error with problem::failure [58].
  4. Use case TransitionExpense::execute ():
    1. self.pool.begin().await?: a transaction, rolled back on any early return [36].
    2. access::actor(…): the caller's role in this team via the MembershipLookup trait object, i.e. the teams module [53]. Not a member → NotFound → 404 [24].
    3. access::load(…): the expense, scoped to the team, visible to this actor, or 404 [25].
    4. self.receipts.summary_for(…): asks the receipts module, through the ReceiptChecks trait, how many receipts are accepted or still scanning [72].
    5. expense.submit(actor, receipts)?: the domain decides (next step).
    6. persistence::update(…): versioned UPDATE; 0 rows → conflict → 412 [69].
    7. self.events.publish(…): an ExpenseEvent::Submitted row in the outbox, same transaction.
    8. transaction.commit().await?, then metrics::counter!(…) [71].
  5. Domain Expense::submit (): allowed_target checks who may submit (only the claimant, else 403) and the workflow table Action::target_from (only from Draft, else 409) [31]. Then the receipt rules: at least one accepted, none pending (else 422). Only then self.status = target [21].
  6. Response: ok(&changed) builds ExpenseResponse::from [51], serialises it with serde [68], and sets the ETag header to the new version. 200.
  7. After the commit: the outbox dispatcher (a spawned task [63]) delivers the event to its listeners, such as the audit trail.

Compared with a typical Express app

The flow is familiar: middleware, router, controller, service, repository. What's different is that every failure on this list is visible in a type or a ?, and every status is chosen in one exhaustive match. In a TS codebase, finding "all the ways this endpoint can fail" means reading every function it calls, including the ones that throw.

Check yourself

A member submits a colleague's draft. What do they get, and why?

  • 403, because only the claimant may submit it
  • 404, because members can't see a colleague's expense
  • 409, because the draft belongs to another person
  • 422, because the receipts belong to the colleague
access::load filters with is_visible_to before the domain runs. For a member, a colleague's expense "doesn't exist". (An approver would get 403 from the domain instead.)

The commit fails after expense.submit succeeded. What happens to the event?

  • It was already delivered to audit before commit
  • Same transaction, so it's rolled back as well
  • It stays in the outbox and gets delivered
  • It's logged as an error, then retried later
The outbox row is written in the same transaction, so change and event happen together or not at all (CONCEPT §3, rule 3).

Which component decides that submit needs at least one accepted receipt?

  • The receipts crate, inside its summary_for method
  • The domain layer, inside the Expense::submit method
  • The handler, before the use case starts running
  • A database constraint on the expenses table itself
Receipts only reports counts. The business rule lives in the expense aggregate.
