Designing Rust code

Constructors, Default and builders

Rust has no constructors, no optional parameters and no overloading. What it has instead is a set of conventions, and picking the right one for a type keeps its call sites short and its invariants safe.

By the end of this lesson

You can choose between new, Default with struct update syntax, and a builder, and write each one idiomatically.

Default and struct update

In Ledgerly

Hand-written, because #[derive(Default)] would make every limit 0. These are Java's defaults; the config loader starts from them and overrides what the environment sets. Tests write Limits { max_page_size: 5, ..Limits::default() } to change one value and keep the rest.

Builders

When a type has a few required and many optional settings, or the combination needs validating, a builder collects them and checks once in build():

In Ledgerly: Tokio's builder

The entry point (new_multi_thread) takes the required choice, setters chain, and build() returns a Result because creating threads and I/O drivers can fail. The tempfile::Builder in the receipts upload and reqwest's RequestBuilder in the parity tests are the same pattern.

Mark the builder #[must_use], so a forgotten .build() is a warning. Setters usually take mut self and return Self; that makes chains easy, and makes "reuse a half-configured builder" impossible unless the builder is Clone.

Where the comparison breaks

An options object in TS is checked only for shape; any combination of optional fields compiles. A Rust builder can validate the combination in build(), and with typestate (lesson 95) can even make build() uncallable until required fields are set. For a handful of fields, though, a plain struct with Default is simpler and just as clear.

Check yourself

Why does Ledgerly write impl Default for Limits by hand?

  • Because derive(Default) only works on enum types
  • A derived Default would set limits to zero
  • Because Default must always be written by hand
  • So Limits can be built in const contexts
Derived Default uses each field's default: 0 for numbers.

What does Limits { max_page_size: 5, ..Limits::default() } do?

  • Changes the global default page size to five
  • Builds the defaults with only max_page_size replaced
  • Fails, because Limits has more than one field
  • Copies max_page_size into every field of Limits
Struct update syntax: like { ...defaults, maxPageSize: 5 }.

When is a builder the better choice over Default + struct update?

  • Whenever a struct has more than two fields
  • When fields are required or combinations need checking
  • Only when the struct is used across crates
  • Only when every field has a sensible default
Builders earn their boilerplate through required inputs and a validating build().
