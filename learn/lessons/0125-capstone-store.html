Decisions to make

  • Methods take &self, not &mut self: the store is shared, so it must handle mutation inside (interior mutability, lesson 84).
  • Sync or async methods? In memory, nothing waits, so sync. A Postgres adapter would return BoxFutures (lesson 92); say so in the trait's docs.
  • "Taken" is checked inside one lock: a get followed by a separate insert would let two requests claim the same slug between the two calls. The entry API does both atomically.
  • get returns an owned Link (a clone): a reference couldn't outlive the lock guard.
Reference solution

The match on Entry is the long form of or_insert, needed here because the occupied case is an error. The poisoning comment records a decision, as Ledgerly's FixedClock does.

Where the comparison breaks

In Node, a Map in module scope is a perfectly good in-memory store, because only one callback runs at a time. With Tokio's worker threads, the same map needs a lock, and the "check, then insert" race is real, not theoretical. The compiler won't let you forget the lock; avoiding the race is still your job.

Check yourself

Why does get return Option<Link> rather than Option<&Link>?

  • Because references can't be wrapped in an Option
  • A reference couldn't outlive the read lock's guard
  • Because cloning is faster than borrowing it here
  • Because dyn traits can't ever return references
The guard is dropped when get returns; the data behind it is only safe while it's held.

What goes wrong with if self.get(&slug).is_none() { self.put(link) }?

  • Nothing; both calls happen at the same instant
  • Two requests can pass the check, then both insert
  • It deadlocks, because get keeps the lock held
  • It doesn't compile, because get borrows self mutably
Check and insert must happen under one lock: the entry API.
