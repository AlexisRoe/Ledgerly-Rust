Ownership and lifetimes in depth

'static and T: 'static

The same word means two different things. &'static str is a reference valid for the whole program. T: 'static is a bound that most owned values meet, including every String. Confusing them is the most common lifetime misunderstanding.

By the end of this lesson

You can tell the two meanings apart, and fix "borrowed value does not live long enough" when spawning a task.

Warm-up
Why does a borrowing struct carry a lifetime parameter?
So it can't outlive what it borrows from. (81)
Why must a future passed to tokio::spawn be Send?
The task may run on any worker thread. (63)

Meaning 1: a reference that's always valid

&'static T points to something that is never freed: string literals (baked into the binary), static items, or memory deliberately leaked. Ledgerly uses it everywhere for fixed text, such as error codes and event types.

In Ledgerly

The event type is a literal, so the caller can keep it as long as it likes. It's the TS equivalent of returning a const string.

Meaning 2: a type that holds no short borrows

T: 'static says: a value of type T could be kept forever, because it holds no reference that might expire. String, Vec<u8>, Arc<Pool> and u32 are all 'static; they own everything. &'a str and Header<'a> aren't, unless 'a is 'static. It's about what the type contains, not how long a value actually lives: a String is 'static and is still dropped at the end of its scope.

Why tokio::spawn asks for it

A spawned task may outlive the function that spawned it, so it may not borrow that function's locals. Its future must be Send + 'static. The fix is always the same: give the task its own copy (often a cheap Arc clone) and move it in.

In Ledgerly: clone, then move

Using self.storage inside the task would borrow self, which isn't 'static (error E0521, "borrowed data escapes"). The clone is owned, so the task owns it.

In Ledgerly: a future that borrows, on purpose

Here + 'a instead of + 'static: the scan borrows the scanner and the file reader. That's fine because the caller awaits it right there; it's never spawned. Trait objects default to 'static in many positions (Box<dyn Error> means Box<dyn Error + 'static>), so a borrowing one must say so.

Where the comparison breaks

In Node, a callback passed to setTimeout can close over anything; the GC keeps it alive. In Rust, "keep it alive for a task that might run later" must be expressed through ownership: move + owned data or Arc. If the work doesn't need to outlive the caller, std::thread::scope (lesson 97) lifts the 'static requirement entirely.

Check yourself

Is String a 'static type?

  • No, only string literals and statics are 'static
  • Yes, it owns its text and borrows nothing
  • Only if it's stored in a static item
  • Only after calling .leak() on the String first
T: 'static is about borrows inside the type, not about how long the value lives.

tokio::spawn(async { repo.save(&expense).await }) fails with "borrowed data escapes". The usual fix?

  • Annotate the async block with a 'static lifetime
  • Clone what the task needs and use async move
  • Replace tokio::spawn with a plain .await call instead
  • Wrap the whole async block in a Box
Owned (often Arc) values moved in make the future 'static. Awaiting in place also works, if you didn't need a separate task.

What does Box<dyn Error> mean, written out in full?

  • Box<dyn Error + Send>
  • Box<dyn Error + 'static>
  • Box<dyn Error + Sync + Send>
  • Box<dyn Error + '_>
A boxed trait object without a lifetime defaults to 'static.
