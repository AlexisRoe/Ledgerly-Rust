Data types

Generic types you'll see everywhere

Array<T>, Promise<T>, Map<K, V>: you already read generics. Rust's are the same idea, just nested deeper. Here's how to read the deep ones from the outside in.

By the end of this lesson

You can read a type like Arc<Mutex<HashMap<String, Entry>>> or Result<Option<Versioned<Expense>>, PersistenceError> out loud and say what each layer adds.

Reading from the outside in

Read the outermost type first. Each layer answers one question:

  1. Result<…, PersistenceError>: the call may fail with a persistence error.
  2. Option<…>: if it worked, there may be nothing.
  3. Versioned<…>: if there's something, it comes with a version.
  4. Expense: and it's an expense.

"Might fail; if not, maybe an expense with its version."

In Ledgerly: the rate limiter's state

Arc: shared by every request handler. Mutex: only one may change it at a time. HashMap<String, Entry>: one entry per client key. In Node you'd write const buckets = new Map<string, Entry>() and be done, because one thread and a GC make the first two layers unnecessary. Rust runs handlers on many threads in parallel and has no GC, so the sharing and locking must be spelled out.

Type aliases name the scary ones

type works exactly like TS's type X = …: a new name, not a new type. Read it as "a boxed future that eventually yields a ReceiptSummary or a database error". Its parts (Pin, dyn, Send, 'a) come in sections 5, 7 and 10. Until then, you can treat it like a Promise<ReceiptSummary>. Also note sqlx::Result<T>: many crates define a Result alias with their error type built in.

Where the comparison breaks

TS generics are erased: Array<number> and Array<string> are the same at runtime. Rust generates separate machine code for each concrete type ("monomorphization"), so Vec<u8> and Vec<Expense> are really different. It's fast, and it's why the type must be known at compile time, which is where the turbofish comes in.

Check yourself

Read Option<Vec<Rejection>> out loud.

  • A list where each rejection may be missing
  • Maybe a list of rejections, maybe nothing
  • A rejection that may hold a list inside
  • A list that is guaranteed to be non-empty
Outside in: Option (maybe), Vec (a list), of Rejection. A list of maybe-rejections would be Vec<Option<Rejection>>.

Why does the rate limiter need Arc<Mutex<…>> where Node needs only a Map?

  • Rust maps can't hold strings as their keys
  • Many threads share and change it, without a GC
  • HashMap is slower without a Mutex around it
  • Arc and Mutex are required for any struct field
Arc handles shared ownership (who frees it), Mutex handles concurrent writes. Node avoids both with one thread and a GC.

What does pub type SummaryFuture<'a> = … create?

  • A new distinct type, like a newtype
  • A shorter name for an existing type
  • A trait that all futures can implement
  • A macro that expands into future code
A type alias is interchangeable with what it names, unlike a newtype.
