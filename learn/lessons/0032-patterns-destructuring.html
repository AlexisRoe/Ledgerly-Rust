Patterns and destructuring

JS destructuring (const { a, b } = obj, const [x, y] = arr) is one use of a bigger idea. In Rust, every let, every function parameter and every match arm is a pattern.

Refutable vs irrefutable

A let pattern must always match: let (a, b) = pair; is fine, but let Some(x) = maybe; is an error, because maybe could be None. For patterns that might not match there's if let and let … else, coming next (Book 19.2).

Where the comparison breaks

JS destructuring of a missing property quietly gives undefined. Rust patterns are checked: a field that doesn't exist is a compile error, and a pattern that might not match is only allowed where there's a plan for the "no" case. JS has no @ bindings, no range patterns and no exhaustive struct patterns.

Check yourself

What does let StoredExpense { id, status, .. } = stored; do with the other fields?

  • Collects them into a variable named rest
  • Ignores them; only id and status are bound
  • Fails to compile until all fields are listed
  • Sets them all to their default values instead
.. means "and the rest, which I don't need". Leave out .. and you must list every field, which is what restore does on purpose.

Why doesn't let Some(note) = expense.note(); compile?

  • Option can't be used inside a let binding
  • The value might be None: a refutable pattern
  • note is a keyword and can't be bound
  • Some must be imported before being used here
let needs a pattern that always matches. Use if let, let … else or match.

In status @ (Submitted | Approved) => Err(NotDraft { status }), what's status?

  • A boolean that says whether the pattern matched
  • The matched value itself, either Submitted or Approved
  • The position of the arm inside the match
  • A string holding the name of the status
@ binds the whole value that matched the sub-pattern, so the error can say which status it was.
