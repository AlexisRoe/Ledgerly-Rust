Async Rust

Sharing state across tasks

In Node, a module-level Map is shared by every request for free. In Ledgerly, requests run in parallel on several threads, so shared state needs a recipe: Arc to share, a lock to change, Clone to hand it out.

By the end of this lesson

You can read the rate limiter's Arc<Mutex<HashMap<…>>>, explain why handler state types derive Clone, and recognise a watch channel used as a shutdown switch.

In Ledgerly: the rate limiter
  • lock() waits until no one else holds the lock and returns a guard. Through the guard you get &mut HashMap, and when the guard is dropped (end of the function) the lock is released. That's ownership doing the unlocking (lesson 36).
  • A lock is "poisoned" if a thread panicked while holding it. unwrap_or_else(PoisonError::into_inner) means "use the data anyway", because a token count is still fine (and unwrap is banned).
  • The lock is held only for a quick in-memory update and never across an .await, which is why a plain std::sync::Mutex is fine here. Holding a std mutex across .await is a classic mistake, and Tokio's own Mutex exists for that case.

Why handler state is Clone

ExpensesApi derives Clone, and axum's State<ExpensesApi> clones it for each request. That's cheap because its fields are use cases whose fields are Arcs and a PgPool. Each clone is a bundle of handles to the same shared services. This is the Rust shape of "inject singletons into each request".

In Ledgerly: a shutdown switch any task can wait on

A watch channel holds one value that many receivers can observe. start() flips it to true; wait() completes once it's true, immediately if it already is. In Node you'd use an EventEmitter or an AbortSignal.

Where the comparison breaks

In Node, data races are impossible because only one callback runs at a time. In Rust they're impossible because the compiler refuses to share non-Sync data or mutate shared data without a lock. Try putting a plain HashMap in an Arc and calling insert: it doesn't compile (no &mut through an Arc). Same safety, enforced by types instead of by a single thread.

Check yourself

When is the rate limiter's lock released?

  • When unlock() is called at the end
  • When the guard returned by lock() is dropped
  • When the request that took it has finished
  • When the runtime runs its next garbage collection
The MutexGuard releases the lock in its drop. There's no unlock() to forget.

Why is cloning ExpensesApi per request cheap?

  • Clone is always free in Rust for every type
  • Its fields are Arcs and a pool: clones share them
  • axum clones it once at startup and reuses that
  • ExpensesApi is Copy, so the clone is a memcpy
Cloning an Arc or PgPool copies a pointer and bumps a count.

What's wrong with holding a std::sync::Mutex guard across an .await?

  • Nothing; std and Tokio mutexes behave the same
  • The task may pause while locked, blocking others
  • The guard is dropped automatically at every await
  • It turns the async function into blocking code
While suspended the task still holds the lock, and other threads trying to lock it block. (The compiler also often refuses, because the guard isn't Send.)
