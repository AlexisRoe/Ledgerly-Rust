Data types

Numbers: one number becomes many

TypeScript has number (a 64-bit float) and bigint. Rust has twelve integer types and two float types, and it never converts between them on its own.

By the end of this lesson

You can read u32, i64, usize and u8 in Ledgerly and say why each was picked. You also know why Ledgerly writes u32::try_from(x) and saturating_add instead of as and +.

Warm-up
What's the difference between let and let mut?
let can't be changed at all. let mut can be reassigned and modified.
A pub struct has fields without pub. What can other modules do?
Use the type, but not read or set the fields directly, or build it with Struct { … }. They must go through its functions.

Literals: 1_000_000 (underscores for readability, like JS), 0xff, 5u8 (suffix sets the type). Without a hint, an integer literal is i32 and a float is f64 (Book 3.2).

In Ledgerly: types as documentation

Picking u32 instead of a signed type removes a validation: a negative receipt count can't exist, so no code has to check for one.

No silent conversions

  • From exists only for conversions that can't lose information (u32 → u64). TryFrom returns a Result for those that can.
  • x as u32 also converts, but silently truncates (300 as u8 is 44). Ledgerly avoids as for numbers.

Overflow is your decision

255u8 + 1? In a debug build, arithmetic overflow panics. In a release build it silently wraps around to 0 (Book 3.2, "Integer Overflow"). Neither is good for a backend, so every integer type has explicit methods:

MethodOn overflowReturns
a.checked_add(b)tells youOption: None on overflow
a.saturating_add(b)sticks at the max/minthe number
a.wrapping_add(b)wraps aroundthe number

The CSV export counts rows sent against a cap. saturating_sub can't go below zero, and try_from converts between u32 and usize explicitly. In the domain modules, Ledgerly turns on the clippy lint arithmetic_side_effects, which makes a bare + on numbers an error. You saw that #![cfg_attr(…, deny(…))] line in .

Money is never a float

Like dinero.js or decimal.js in TS projects, Ledgerly stores amounts as a decimal: Money { amount: Decimal, currency: Currency }, with Decimal from the rust_decimal crate. Adding two amounts is money.checked_add(&other), which returns an error when the currencies differ.

Where the comparison breaks

TS has one number type, so mixing is never an error and precision loss is invisible. Rust makes every width and every conversion explicit. That's noisy at first, but it's where a whole class of "negative count", "lost cents" and "overflowed ID" bugs disappears.

Check yourself

Why is ReceiptSummary::accepted a u32 and not an i32?

  • u32 is faster on 64-bit processors
  • A negative count simply can't be represented
  • Postgres stores counts as unsigned integers
  • i32 can't hold more than 255 receipts
The type rules out invalid values, so no runtime check is needed. The doc comment says exactly that.

What does let n: u64 = 7; let m: u32 = 3; n + m do?

  • Returns 10 as a u64 value
  • Returns 10 as a u32 value
  • Fails to compile: mismatched types
  • Panics at runtime with an overflow
Rust never widens implicitly. Write n + u64::from(m).

You need u32 from a usize length and don't want silent truncation. Which do you write?

  • len as u32
  • u32::try_from(len)
  • u32::from(len)
  • len.into::<u32>()
try_from returns a Result you must handle. as truncates silently, and From<usize> isn't implemented for u32 because it could lose data.

What is 200u8.checked_add(100)?

  • 300
  • 44
  • 255
  • None
300 doesn't fit in a u8 (max 255). checked_add returns None, saturating_add would give 255, wrapping_add 44.
