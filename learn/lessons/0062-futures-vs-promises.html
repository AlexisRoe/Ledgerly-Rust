Async Rust

Futures vs Promises

async/await reads almost exactly like TypeScript. The one big difference: a Rust future does nothing until it's awaited (or handed to a runtime). A Promise starts running the moment you create it.

By the end of this lesson

You can read async fn, .await and .await? in Ledgerly, explain why main isn't async, and recognise the Pin<Box<dyn Future<…>>> shape as "a Promise behind a trait".

Same syntax

  • async fn f() -> T really returns impl Future<Output = T>, like Promise<T>.
  • .await is postfix (after the expression), so it chains: .await? means "wait, then propagate an error".
  • .await is only allowed inside async functions or async { } blocks.

Lazy, not eager

A future is a state machine the compiler builds from your async fn. Something has to poll it to make progress. In Node, the event loop and V8 do that for every Promise. In Rust, that "something" is a runtime library, and Ledgerly uses Tokio (Book 17.1).

In Ledgerly: where sync ends and async begins

main is ordinary synchronous code. It builds the runtime by hand (most projects write #[tokio::main] async fn main(), which generates the same thing) because some setup must happen before the runtime exists. run(…) creates a future, and block_on drives it to completion: the whole server lives inside that one call.

Futures behind traits

Each async fn produces its own unnamed future type, which doesn't work with dyn Trait (lesson 53). So trait methods used as Arc<dyn Publisher> return a boxed future instead. Read the return type as Promise<sqlx::Result<()>>:

  • dyn Future<Output = …>: some future producing that value.
  • Box: on the heap, because its size isn't known. Pin: it won't move in memory once polled (needed for futures that borrow from themselves; you never handle it directly).
  • + Send: may move between threads. + 'a: borrows self, the connection and the event while it runs.

Implementations write Box::pin(async move { … }).

Where the comparison breaks

Lazy futures mean "fire and forget" doesn't happen by accident. To run something in the background you must tokio::spawn it (next lesson). And there's no unhandled-rejection warning to rely on: a future returning Result that you .await but don't use triggers the normal "unused Result" warning instead.

Check yourself

let f = publisher.publish(&mut tx, &event); and then the function returns without .await. Was the event published?

  • Yes, the future started running when it was created
  • No, futures do nothing until they're awaited or polled
  • Yes, but only after the current function has returned
  • It depends on whether the runtime is multi-threaded
Rust futures are lazy. Dropping one cancels it before it starts, and the compiler warns about it.

Why isn't Ledgerly's main an async fn?

  • Rust doesn't allow main to be async at all
  • It sets things up before building the runtime itself
  • Async main functions can't return an ExitCode value ever
  • Tokio requires binaries to block in main manually
The comment says it: the telemetry exporter uses a blocking HTTP client and must be created before the runtime exists. #[tokio::main] would hide that order.

How would you read Pin<Box<dyn Future<Output = Result<Verdict, ScanError>> + Send>>?

  • A pinned result that is already available right now
  • Like a Promise of Result<Verdict, ScanError>, boxed for traits
  • A thread handle that returns the verdict much later
  • A stream of verdicts arriving one at a time
A heap-allocated future yielding that result, safe to move between threads.
