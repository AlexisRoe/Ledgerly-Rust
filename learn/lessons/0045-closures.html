Functions, closures and iterators

Closures vs arrow functions

(x) => x + 1 becomes |x| x + 1. Same idea, same everyday use, plus one new keyword, move, because capturing a variable now has to say whether it borrows or takes ownership.

Syntax

Parameter types are usually inferred from how the closure is used, unlike fn items, which always need them. A closure can read variables from the surrounding scope ("capture" them), exactly like an arrow function (Book 13.1).

In Ledgerly: closures as small helpers

The same error is needed in two places, so it's built by a closure that captures amount. It's called directly (too_large()) and also passed to ok_or_else, which only calls it if there's no value. That's the lazy version of ok_or: no error string is built on the happy path. Note the shadowing: the last line's let amount is a new variable.

move: take the captured values with you

By default a closure borrows what it captures. That's fine as long as the closure is used right away. But a closure that's stored, returned, or handed to another thread or task may outlive the variables it borrowed, and the compiler refuses. move makes it take ownership (or a copy, for Copy values) instead:

For each of the six transitions, Ledgerly builds a request handler that remembers which action it is. The handler lives in the router for the whole life of the server, long after this setup code returns, so it must own its copy of action: move. You'll see move on almost every closure passed to tokio::spawn for the same reason.

Closures have types too: Fn, FnMut, FnOnce

When a function accepts a closure, its signature says how it will call it: Fn (call many times, read-only captures), FnMut (many times, may mutate captures), FnOnce (at most once, may consume captures). For example, ok_or_else<F: FnOnce() -> E> calls its closure at most once. You rarely write these, but you'll see them in docs.

Where the comparison breaks

JS closures capture variables by reference, and the GC keeps them alive as long as the closure exists. That's also the source of the classic "every callback sees the last loop value" bug. Rust must decide borrow vs own at compile time, so long-lived closures need move, and the classic bug can't happen: each move closure gets its own value.

What's the Rust for TS (a, b) => a * b?

  • (a, b) => a * b
  • fn(a, b) { a * b }
  • |a, b| a * b
  • \a b -> a * b
Pipes around the parameters, then the body expression.

Why does the handler closure in ExpensesApi::routes need move?

  • Closures can't capture enum values without moving them first
  • It outlives the setup code, so owns its action
  • move makes the closure faster when called repeatedly
  • Handlers must always be declared with move there
A borrowed action would end with the setup function, but the router keeps the handler for the life of the server.

Why ok_or_else(too_large) and not ok_or(too_large())?

  • ok_or doesn't accept error values of this kind
  • The error is only built when it's needed
  • ok_or_else also converts the error type automatically
  • There's no difference; both forms build it lazily
ok_or(x) evaluates x first, always (here: formatting a string). ok_or_else(f) calls f only on None.
