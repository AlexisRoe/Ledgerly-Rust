Loops: loop, while, for

Three loops. for always iterates over something, so there's no C-style for (let i = 0; …), and loop can return a value.

for: always over an iterator

a..b is a range value (end excluded), and a..=b includes the end. Ranges also slice: &v[1..3]. Looping over &items borrows the items, while looping over items (no &) consumes the collection, which is why you'll see for x in &list so often. Section 5 explains why.

while and loop

while cond { … } is TS's while. loop { … } is while (true), and it's the one you'll see when the exit condition sits in the middle:

The virus scanner's reply is read one byte at a time until a NUL byte or the end of the stream, with a cap so a misbehaving scanner can't fill memory. Three exits: break (done), return Err (too long), and the ? on the read (I/O error or timeout).

break with a value, and labels

Labels look like lifetimes ('name) but are unrelated. JS has labels too, but they're rarely used.

Where the comparison breaks

No index-based for means no off-by-one bugs from <= vs <, and no i leaking out of the loop. In idiomatic Rust, many loops disappear entirely in favour of iterator chains (.iter().map().filter().collect(), lesson 46), much like you'd prefer .map() over a for loop in TS.

1..5 is 1, 2, 3, 4 (end excluded). 1..=5 would run 5 times.

What's the TS equivalent of loop { … }?

  • do { … } while (false)
  • while (true) { … }
  • for (const x of xs) { … }
  • setInterval(() => { … })
An endless loop, left with break or return. Unlike while (true), it's an expression that can produce a value via break value.

In read_reply, which line leaves the loop when the scanner sends too much?

  • The break after checking for a NUL byte
  • The return Err when the length hits the cap
  • The question mark after the socket read call
  • The push, which panics once the vector fills
