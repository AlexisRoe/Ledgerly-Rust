Concurrency and async internals

Shared mutable state

When several threads or tasks must change the same data, wrap it: Arc for shared ownership, and a lock or an atomic for safe mutation. Choosing the right one, and keeping locks short, is most of the skill.

By the end of this lesson

You can use Arc<Mutex<T>>, RwLock and atomics correctly, handle poisoning, and choose between std::sync::Mutex and tokio::sync::Mutex.

The building blocks

  • lock() returns a guard; the data is reachable only through it, and dropping it unlocks (RAII, lesson 86). You can't forget to unlock, and you can't touch the data without locking.
  • Poisoning: if a thread panics while holding the lock, later lock()s return Err, because the data may be half-updated. Ledgerly decides case by case; its test clock ignores poisoning, since a timestamp can't be half-written.
  • RwLock allows many readers at once; worth it for read-mostly data.
  • Atomics (AtomicUsize, AtomicBool) for single counters and flags, no lock at all. Ordering::Relaxed is enough for a counter; SeqCst is the safe default when unsure.

This Mutex is tokio::sync::Mutex (imported at the top). With Keycloak login, the first request discovers the identity provider and fetches its signing keys over HTTP while holding the lock. Concurrent requests wait for that one fetch instead of all fetching at once. That's a valid reason to hold a lock across .await, so it must be Tokio's.

Where the comparison breaks

In Node, counter++ in two async callbacks never races, because only one runs at a time; the only danger is interleaving at await points. In Rust's multi-threaded runtime, two tasks really do run at the same instant. The compiler forces a lock or an atomic on shared mutable data; it can't force you to keep the critical section short. Lock, change, unlock; compute outside.

Short, synchronous critical section: the std mutex is faster and recommended.

What does a poisoned mutex tell you?

  • Two threads tried to lock it at once
  • A thread panicked while it held the lock
  • The data inside was dropped by another thread
  • The lock was held across an await point
The data might be half-updated; you decide whether that matters.
