Concurrency and async internals

Threads and scoped threads

Node gives you one thread for your code and worker threads that share nothing. Rust gives you real OS threads that can share memory, and a compiler that checks the sharing. Before async, this is the foundation.

By the end of this lesson

You can spawn and join threads, move data into them, and use thread::scope to let threads borrow from the stack.

Warm-up
Why does tokio::spawn require a 'static future?
The task may outlive the function that spawned it, so it can't borrow its locals. (82)
What does move before a closure do?

Node vs Rust

spawn starts an OS thread immediately (unlike a future, it doesn't wait to be awaited) and returns a JoinHandle. join() blocks until it finishes and returns its result, or Err if the thread panicked: a panic ends only that thread. Like tokio::spawn, the closure must be Send + 'static: the thread may outlive the caller.

Scoped threads: borrowing allowed

scope doesn't return until every thread spawned in it has finished, so those threads can borrow local data, no Arc and no 'static needed (std: thread::scope). It's the tool for "split this work across cores and wait".

In Ledgerly: proving a trait object can cross threads

Ledgerly itself never spawns OS threads; Tokio does (lesson 104). This test exists to prove that an Arc<dyn Clock> may be sent to another thread: if Clock weren't Send + Sync, it wouldn't compile. Note the idiom: a block that clones the Arc, then returns the move closure, so the original stays usable.

Where the comparison breaks

In JS, shared mutable memory between threads exists only through SharedArrayBuffer and Atomics, which few people touch. In Rust it's normal, and the type system decides what may be shared: try moving an Rc into a thread and it doesn't compile. Data races are compile errors; logic races (two threads updating in the wrong order) are still yours to avoid.

Check yourself

A spawned thread panics. What happens to the rest of the program?

  • The whole process aborts at that moment
  • That thread ends; join returns an Err
  • The panic is silently ignored and lost
  • The main thread panics at the same time
Panics unwind one thread. The joiner decides what to do with the Err.

Why can scoped threads borrow values while thread::spawn can't?

  • Scoped threads copy the data before they start
  • The scope waits for them before it returns
  • Scoped threads all run on the main thread
  • Scoped threads use Arc for every borrowed value
Borrows can't outlive the scope, because the threads can't either.

When does a std::thread::spawned closure start running?

  • When join is called on its handle
  • Immediately, on its own OS thread
  • When the current function has returned
  • When the Tokio runtime polls it first
Threads are eager. Futures are lazy. Don't mix up the two.
