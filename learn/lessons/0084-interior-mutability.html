Ownership and lifetimes in depth

Interior mutability

Sometimes you must change something through a shared &: a cache, a counter, a test clock that every request shares. Rust allows it, through types that move the "one writer" check from compile time to run time.

By the end of this lesson

You can pick the right cell for a job: Cell, RefCell, Mutex, RwLock, an atomic, or OnceLock/LazyLock.

Why can't you call self.label() while mutating self.log?

What's Arc for?
Shared ownership across threads: several owners, freed when the last one goes. (42)

Better names for & and &mut

Think of &T as a shared reference and &mut T as an exclusive one. The real rule is "no mutation through a shared reference unless the type allows it safely". Interior-mutability types allow it, each with its own way of keeping it safe.

(std::cell, std::sync.) The single-threaded ones aren't Sync, so the compiler won't let you share them between threads by mistake.

In Ledgerly: a clock that tests can move

The Clock trait's methods take &self, and the clock is shared as Arc<dyn Clock> by every request, so a test can only move it through a shared reference. It must be Send + Sync, which rules out RefCell; hence a Mutex.

In Ledgerly: a global computed once

Hashing takes tens of milliseconds, so it happens once, on first use, and every login for an unknown email reuses it. It's TS's module-level let cached; function get() { return cached ??= compute(); }, but thread-safe.

Where the comparison breaks

TS's readonly is shallow and compile-time only; anything can mutate anything at run time. In Rust, mutation through & is the exception, visible in the type. When you see Cell, RefCell or Mutex in a struct, you know exactly where shared mutation can happen. Treat RefCell as a tool, not a way out: a borrow conflict becomes a panic at run time.

Check yourself

What happens if you call borrow_mut() on a RefCell that's already borrowed?

  • A compile error at the second call's line
  • A panic at run time with BorrowMutError
  • It waits until the other borrow ends
  • It silently returns a copy of the value
RefCell moves the check to run time. Use try_borrow_mut to get a Result instead.

Why does FixedClock use Mutex rather than RefCell?

  • A Mutex is faster for a single value
  • The shared clock must be Sync across threads
  • RefCell cannot hold a chrono DateTime value
  • Clippy forbids RefCell anywhere in Ledgerly's code
Clock: Send + Sync, and RefCell isn't Sync.

A request counter is incremented by every request, on many threads. What's the leanest choice?

  • Cell<u64>
  • RefCell<u64>
  • AtomicU64
  • Mutex<Vec<u64>>
An atomic counter needs no lock. The Cells aren't Sync.
