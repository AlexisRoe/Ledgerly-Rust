unsafe, briefly

What unsafe allows

Every guarantee in this course (no dangling references, no data races) comes from rules the compiler can check. unsafe marks code where the programmer, not the compiler, vouches for those rules. Ledgerly forbids it outright. Here is what you're giving up, and why that's fine.

By the end of this lesson

You can list what unsafe unlocks, explain "safe abstraction over unsafe code", and say why Ledgerly uses forbid rather than deny.

The five superpowers

Inside an unsafe { … } block or unsafe fn, you may (Book 20.1):

  1. dereference a raw pointer (*const T, *mut T);
  2. call an unsafe function, including C functions over FFI;
  3. read or write a mutable static;
  4. implement an unsafe trait (Send, Sync);
  5. access fields of a union.

That's all. The borrow checker and type checker still run inside unsafe; you just get these extra operations, and the duty to uphold the rules they could break. Break them, and the result is undefined behaviour: the program may do anything, including appearing to work.

Safe abstractions

Vec, String, Mutex, Arc and Tokio are built on unsafe code. Their authors prove once, carefully, that every possible use of the safe API keeps the rules, and wrap the unsafe parts behind it. You use Vec::push without unsafe because someone else did the proof. That's the whole model: a small amount of audited unsafe at the bottom, safe code everywhere else.

In Ledgerly

Twice: as a workspace lint and as a crate attribute at the top of every crate. forbid means no module can opt back in with #[allow(unsafe_code)]. A web backend has no need to: everything it does (HTTP, SQL, JSON, crypto) is available as safe APIs, and a memory-safety bug in a service that handles receipts and passwords would be a security bug.

Where the comparison breaks

TS's escape hatches (any, as, // @ts-ignore) only weaken type checking; the JS engine still prevents memory corruption. Rust's unsafe can corrupt memory, so it's treated far more seriously: minimal, commented, reviewed, and in application code, usually banned.

Check yourself

Does the borrow checker still run inside an unsafe block?

  • No, unsafe turns off every compiler check
  • Yes; unsafe only adds five extra operations
  • Only for references created outside the block
  • Only when built in debug mode
unsafe unlocks operations; it doesn't switch checks off.

Why can you call Vec::push without unsafe, though it uses unsafe code inside?

  • Because std is compiled with a special compiler flag
  • Its safe API is proven sound for any use
  • Because Vec checks all its pointers at runtime
  • Because unsafe code inside std can never misbehave
Safe abstraction: the proof obligation sits with the author of the unsafe code.

Why forbid(unsafe_code) rather than deny?

  • Because forbid also bans unsafe in dependencies
  • No module can override it with an allow
  • Because deny only produces warnings, not errors
  • Because forbid makes the build noticeably faster
Dependencies are unaffected; that's lesson 122.
