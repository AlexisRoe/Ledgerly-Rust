Private field, one fallible constructor, read-only access, every entry point uses it. (112)
When does a function deserve a Result and when not?
When it can fail for reasons the caller must handle. A generator that always produces a valid value doesn't. (25, 111)

Start from these tests

Decisions to make

  • Which derives? Slug becomes a HashMap key: it needs Eq and Hash. Tests compare errors: DomainError needs PartialEq.
  • generate returns Slug, not Result: its output is valid by construction, so don't make callers handle an impossible error.
  • Error messages come from #[error(…)] and can use constants: min = Slug::MIN_LEN. They'll appear in API responses, so they're user-facing text.
  • Display for Slug: handy for logs and for to_string().
Reference solution (compare after you're green)

A closure as a named predicate, a range's contains for the length check, an early return per rule. The rest of the file: (generate) and (Target::parse, with a match guard).

Where the comparison breaks

In a TS service the domain is often interfaces plus validation functions called from the controller. Here the domain types are the validation: a handler can't forget to check a slug, because it can't get a Slug without checking.

Check yourself

Why must Slug derive Hash and Eq?

  • Because every newtype must derive both of them
  • The store uses it as a HashMap key
  • Because serde needs Hash to serialise a String
  • Because Display can't be written without them
Map keys need Eq + Hash, and they must agree (lesson 94).

Why does Slug::generate return Slug, not Result<Slug, _>?

  • Because functions taking numbers can never fail
  • Its output is always valid; errors are impossible
  • Because the counter guarantees slugs are unique
  • Because a Result would need an extra allocation
Uniqueness is the store's job (next lesson); validity is guaranteed by construction.
