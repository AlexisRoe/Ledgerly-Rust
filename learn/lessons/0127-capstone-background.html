Capstone: a service from scratch

Capstone 5: background work and shutdown

Visits are counted by a background task that batches them, so redirects never touch the write lock. And when the server stops, the last batch must still be written. Ownership solves that more neatly than any signal.

By the end of this lesson

Your visits.rs has a batching worker driven by select!, and your main.rs starts everything, shuts down gracefully on Ctrl-C, and lets the worker finish.

Warm-up
When does mpsc::Receiver::recv() return None?
When every sender has been dropped. (100)
Is recv() cancel-safe in a select! loop?
Yes: if another branch wins, no message is lost. (103)

The worker

Reference solution

The worker owns pending, so it needs no lock (the actor pattern, lesson 100). It takes the write lock once per flush, not once per visit.

Shutdown by ownership

Reference solution: main

Ctrl-C → axum stops accepting connections and lets running requests finish → serve returns, dropping the router → the last Sender (inside the state) is dropped → the worker's recv() returns None → it flushes and ends → main returns. No shutdown flag, no timeout. It only works because main moved its sender into the state instead of keeping a copy; keep one by accident and counter.await waits forever.

  1. Write visits::run and its two tests (one with a long interval that checks the final flush, one with a short interval that checks a flush while running).
  2. Write main: tracing, PORT from the environment with a default, bind (print the error and return ExitCode::FAILURE on failure: no unwrap), spawn the worker, serve.
  3. Try it: PORT=3000 cargo run, create a link with curl, follow it twice, wait a second, look at its visits. Press Ctrl-C and watch the log.
Where the comparison breaks

A Node service would listen for SIGINT, call server.close(), then flush the counter from a callback, coordinating by hand. Here the order of shutdown follows from who owns what: when the last owner of the sender is gone, the channel tells the worker. Ledgerly's own shutdown (lesson 74) uses a watch channel instead, because several independent servers must stop together.

Check yourself

What makes the worker's loop end when the server stops?

  • A shutdown flag that main sets after serving
  • The router's drop closes the channel: recv returns None
  • The interval timer stops once Ctrl-C is pressed
  • Tokio aborts every spawned task when main ends
Ownership is the signal.

main keeps a clone of the sender "just in case". What happens on Ctrl-C?

  • Nothing different; the worker still ends normally anyway
  • counter.await hangs, because the channel never closes now
  • The program panics because of the extra sender
  • The final batch gets written twice to storage
A channel closes only when all senders are gone.
