Visibility and re-exports

Everything is private until you say pub. Ledgerly uses that, plus pub(crate) and pub use, to make each crate expose only a small facade.

By the end of this lesson

You can tell, for any item in Ledgerly, who's allowed to use it: only its module, the whole crate, or other crates. You can also read a crate's public API from its lib.rs.

Warm-up
What do crate::, super:: and self:: mean at the start of a path?
This crate's root, the parent module, the current module.
Does use add a file to the program?
No. mod adds files. use only creates a shortcut to a name.

The rule (Reference: visibility): an item is reachable only if every module on its path is visible to you. A pub fn inside a private mod is still invisible from outside, unless something re-exports it.

In Ledgerly: a crate's facade

Every module is private, and the crate's entire public API is these four pub use lines plus pub fn routes. The Expense aggregate itself is pub(crate) (see domain/mod.rs), so no other crate can touch it. That's ADR 0010: module boundaries that Java checked with tests are compile errors here.

Fields have visibility too

The type is public, its fields are not. Outside the money module nobody can write Money { amount, currency } or change money.amount. They have to go through Money's constructor, which validates. That's how Ledgerly guarantees that every Money in the system is valid ().

Where the comparison breaks

TS private is per class and only enforced by tsc. At runtime anyone can read the field, and as any gets around it. Rust privacy is per module: all code in the same module (and its child modules) can see private fields, which is why tests in mod tests can inspect internals. There's no cast that gets around it.

Check yourself

pub(crate) struct Expense lives in ledgerly_expenses. Can ledgerly_app use it?

  • Yes, because the struct itself is marked pub
  • No, pub(crate) ends at its own crate
  • Only if it imports it with use crate
  • Only in tests marked with cfg test
pub(crate) means "public inside this crate". Other crates can't name it at all.

A pub fn sits inside a private mod helpers; of lib.rs. Can another crate call it?

  • Yes, a pub function is always visible everywhere
  • Only if lib.rs re-exports it with pub use
  • Only if the other crate declares mod helpers
  • No, and nothing can ever change that fact
The path crate::helpers::f passes through a private module. A pub use helpers::f; in lib.rs creates a public path to it.

Why can a mod tests at the bottom of money/mod.rs read money.amount?

  • Tests are always exempt from privacy rules
  • Child modules see their ancestors' private items
  • The field becomes public under cfg test
  • use super::* makes private items public
Privacy is per module, and descendants see everything in their ancestors. Tests in a child module can therefore check internals.
