Making changes

Exercise: add an enum variant

Add a status Archived to ExpenseStatus and let the compiler lead you to every place that must decide what it means. This is the payoff of all those matches without _.

By the end of this exercise

You've followed compile errors across three files, made a decision at each, found the one place the compiler can't help (the ALL array), and fixed the two tests that pin the old behaviour.

Warm-up
What's E0004?
Non-exhaustive patterns: a match doesn't cover every value. (31, 75)
What does status @ (A | B) do in a pattern?
Matches A or B and binds the matched value to status. (32)

Step 3: the compiler's blind spot

The library compiles. But look at ExpenseStatus::ALL: it still lists five statuses, and nothing complained, because an array literal isn't a match. So "ARCHIVED".parse::<ExpenseStatus>() would fail (it searches ALL), and the database could never load an archived expense. Fix it: add Self::Archived and change [Self; 5] to [Self; 6] (try leaving the 5 and read the error).

What this shows

In TypeScript, adding "ARCHIVED" to a string union with default: branches compiles immediately and quietly does something everywhere. Here you had to answer four questions, the type system found three of them, and the tests found the rest. Step 4 also exposed a design gap: a status no action can reach. In the real project that's a conversation for Ledgerly-Java (contract, schema, workflow) before any Rust is written.

Check yourself

Why didn't the compiler flag ExpenseStatus::ALL?

  • Arrays are checked only when the tests run
  • An array literal isn't a match; nothing's checked
  • const items are skipped by the type checker
  • It did, but only as a warning
Only match (and patterns) are checked for completeness. That's why the names_… test exists.

What would a _ => None arm in target_from have changed?

  • Nothing; the behaviour would be exactly the same
  • One fewer error, and Archived silently gets None
  • A compile error, since _ isn't allowed there
  • Archived would accept every action without any checks
Here None happens to be right, but nobody would have been asked. That's the trade-off from lesson 31.

The workflow test's (6, 24) becomes (6, 30). Is updating it "weakening" a test?

  • Yes, a test's expected values must never change
  • No, the behaviour changed on purpose; it's recorded
  • Yes, the test should be deleted and rewritten
  • No, because unit tests needn't be accurate anyway
Updating an expectation to match an intended change is fine. Weakening means making a test accept behaviour it should reject.
