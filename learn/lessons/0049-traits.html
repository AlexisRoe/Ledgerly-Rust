Traits and generics

Traits are interfaces, but nominal

A trait lists methods a type promises to have, like an interface. The difference: having the right methods isn't enough. A type implements a trait only when someone writes impl Trait for Type.

By the end of this lesson

You can read Ledgerly's Clock trait and its two implementations, explain default methods and supertraits (: fmt::Debug + Send + Sync), and say why tests can swap in a fixed clock.

Warm-up
What does impl Into<String> in a parameter mean?
"Any type that implements the trait Into<String>." (44)
Where do methods of a struct live?
In an impl Type { … } block, separate from the struct definition. (21)

Defining and implementing

  • Required methods have only a signature (now). Default methods have a body (today) that implementors get for free and may override. It's like an abstract class method, without the inheritance.
  • impl Clock for SystemClock is a separate block from impl SystemClock. A type collects its abilities one trait at a time.
  • Supertraits: trait Clock: fmt::Debug + Send + Sync means "every Clock must also be debug-printable and safe to share between threads". That's how Arc<dyn Clock> can be used by every request (lesson 53).
In Ledgerly: a seam for tests

The domain never asks the OS for the time; it gets a &dyn Clock. Production passes SystemClock, tests pass a FixedClock set to "2026-11-05T10:00:00Z", so a rule like "incurredOn must not be in the future" is testable. The same pattern appears in config::Environment (the process environment, or a HashMap in tests) and in MembershipLookup, ReceiptChecks, Publisher.

You can implement traits for types you didn't write

Ledgerly makes the standard library's HashMap an Environment, so a test can write Config::from_environment(&HashMap::from([("SPRING_PROFILES_ACTIVE", "prod")])). The one limit (the "orphan rule"): either the trait or the type must be defined in your crate (Book 10.2).

Traits must be in scope to call their methods

Remember use std::fmt::Write as _; from lesson 12? Trait methods only work when the trait is imported. That's why files that call "TRAVEL".parse::<Category>() don't need anything special (FromStr is in the prelude), while code calling write! on a String needs std::fmt::Write.

Where the comparison breaks

TS is structural: { now: () => … } is a Clock. Rust is nominal: a type with a now method is not a Clock until impl Clock for … says so. In exchange you get default methods, implementations for foreign types, and operators driven by traits (== is PartialEq, + is Add, {} is Display), which is the next lesson.

Check yourself

A struct has a method fn now(&self) -> DateTime<Utc> but no impl Clock. Can it be passed as &dyn Clock?

  • Yes, the shape matches the trait's methods
  • No, Rust needs an explicit impl Clock block
  • Yes, but only if it also derives Debug
  • No, only enums can implement trait methods
Traits are nominal. Add impl Clock for MyClock { fn now(&self) … }.

Does FixedClock have a today() method?

  • No, it only implements the required now method
  • Yes, it inherits the trait's default implementation
  • Only if FixedClock writes its own today body
  • No, default methods only apply to SystemClock
Default methods come with the trait. today calls whatever now the implementor provides, so a fixed clock gets a fixed day.

What does trait Clock: fmt::Debug + Send + Sync require?

  • That Clock's methods return values of those traits
  • That every implementor also implements those three traits
  • That Clock inherits fields from those three types
  • That clocks are only used inside debug builds
They're supertraits: requirements on implementors, so code holding a dyn Clock can debug-print it and share it across threads.
