Traits and generics

Conversions: From, Into, TryFrom, FromStr, Display

Instead of ad-hoc toResponse(), parseX() and toString() helpers, Rust has a handful of standard traits for converting between types. Implement one, and .into(), .parse(), ? and format! start working.

By the end of this lesson

You can find where a .into(), .parse() or try_from in Ledgerly gets its behaviour, and choose the right trait when you write a conversion yourself.

Warm-up
Which trait gives {} formatting, and which {:?}?
Display (hand-written) and Debug (usually derived). (50)
Can you implement a trait for a type from another crate?
Yes, if the trait is yours (orphan rule: trait or type must be local). (49)

The map

Implement From, and Into comes for free. Implement Display, and to_string() comes for free (Rust by Example: conversion). The type Error = … lines are associated types: each implementation names its own error type.

In Ledgerly: domain → API response (From)

The JSON shape lives in the web layer, and the domain knows nothing about it. Callers write ExpenseResponse::from(&found), or pass the function itself: .map(ExpenseResponse::from). Note expense.id().to_string(): that's the id's Display.

In Ledgerly: database row → domain (TryFrom)

A row from Postgres is untrusted (someone could edit the database by hand), so turning it into an Expense can fail with PersistenceError::Corrupt. That's what row.map(Versioned::try_from).transpose() in find calls (lesson 47).

In Ledgerly: text → enum (FromStr)

Now "OWNER".parse::<Role>() works anywhere, and so does the serde deserializer that calls it.

Where the comparison breaks

TS has no standard conversion protocol (only toString, valueOf and toJSON), so every codebase invents names. In Rust the names are fixed, which is why you can find every conversion with "Go to implementations" in VS Code. One more payoff: ? calls From::from on errors automatically. That's how a CurrencyError becomes a MoneyError (section 8).

Check yourself

You implemented From<TeamRow> for Team. Which call now also works?

  • let row: TeamRow = team.into();
  • let team: Team = row.into();
  • let team = row.parse::<Team>();
  • let team = Team::try_into(row);
Into is implemented automatically in the same direction as From. The reverse needs its own From.

Why is row → Versioned<Expense> a TryFrom and not a From?

  • From can never be implemented for generic types
  • A stored row may break rules and fail
  • TryFrom is faster for database rows than From
  • From only converts between the numeric types here
From promises it can't fail. A corrupt currency or amount in the database must become an error, not a panic.

What does "MEMBER".parse::<Role>() call?

  • Role's Display implementation, run in reverse order
  • The from_str method of Role's FromStr implementation
  • A serde deserializer configured for the Role
  • The Debug implementation derived for the Role
str::parse::<T> works for any T: FromStr.
