Memory and performance

Stack, heap and layout

In TypeScript you never ask how big a value is. In Rust the compiler must know, for every type, at compile time. Learning to predict sizes tells you where your data lives and what a move actually copies.

By the end of this lesson

You can predict size_of for common types, explain padding and niches, and say what's on the stack and what's on the heap for a String, a Vec and a Box<dyn Trait>.

Fixed size, known at compile time

Every local variable lives in its function's stack frame, so its size must be known when compiling. Types whose content can grow (String, Vec, HashMap) are a small, fixed-size header on the stack pointing to a buffer on the heap (std: size_of).

Padding and field order

Values are aligned: a u64 sits at an address divisible by 8. A struct { u8, u64, u8 } laid out in that order would need 7 bytes of padding after each u8, 24 bytes in total. Rust is free to reorder fields (C isn't), so it puts the u64 first and the size is 16. Use #[repr(C)] only when you need C's layout, for FFI.

Enums and niches

An enum is a tag plus room for its largest variant. But when the payload has "impossible" bit patterns, the compiler hides the tag in them: a niche.

  • Option<Box<T>> and Option<&T> are 8 bytes: a reference is never null, so None is null. Rust's Option costs exactly what a nullable pointer costs in other languages.
  • Option<u32> is 8: every u32 value is valid, so it needs a real tag (plus padding). Option<NonZeroU32> is 4.
  • A field-less enum with three variants is one byte, and Option of it is still one byte.
In Ledgerly: the id types

A newtype is exactly the size of what it wraps: 16 bytes, no header, no heap. Copying one is copying two machine words, so Copy is the right call, and passing ids by value everywhere costs nothing.

Where the comparison breaks

In JS, every object is a heap allocation behind a reference, and numbers are boxed or not as the engine decides. In Rust, a struct of five numbers is 40 bytes laid out inline wherever it's stored, on the stack, inside a Vec, inside another struct. The heap appears only where you ask for it: Box, Vec, String, Arc…

You move a Vec with a million elements into a function. How much is copied?

  • All million elements, element by element
  • 24 bytes: pointer, capacity and length
  • Nothing; moves never copy anything at all
  • Only the first page of the elements
The header moves; the heap buffer stays put.

Why is &str 16 bytes but &String 8?

  • Because references to a String are always compressed
  • &str carries a length; &String points at one
  • Because str is stored on the stack
  • Because &str also stores the capacity too
str is unsized, so references to it are fat: pointer + length.
