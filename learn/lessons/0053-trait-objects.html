Traits and generics

Trait objects: dyn Trait

dyn Clock means "some value implementing Clock, decided at runtime". It's the closest thing Rust has to a TS variable typed as an interface, and Ledgerly's dependency injection is built on it.

By the end of this lesson

You can explain why Ledgerly writes Arc<dyn Publisher> and &dyn Clock instead of generics, what Send + Sync on a trait means, and when you'd choose generics instead.

In Ledgerly: services as trait objects

Why dyn here and not struct TransitionExpense<C: Clock, M: …, R: …, E: …>? With generics, every type that holds a use case would need those four type parameters too, all the way up to the router. With dyn, the struct has one concrete type, and which implementation sits behind each field is decided when the app is wired up: the real teams lookup in production, an in-memory double in tests (application/doubles.rs). The cost, one indirect call per use, is irrelevant next to a database round trip.

This is also how the crate boundaries stay clean: expenses defines ReceiptChecks, and receipts implements it, so expenses never depends on receipts (lesson 72).

Send and Sync

Two marker traits the compiler implements automatically when safe: Send means "can be moved to another thread", Sync means "can be shared between threads by reference". Requiring them on the trait guarantees that any Arc<dyn Publisher> can be used by request handlers running in parallel. A type containing an Rc, for instance, isn't Send, so it couldn't implement Publisher by accident (Book 16.4).

Where the comparison breaks

In TS every interface-typed variable works like a trait object, and there's no alternative. In Rust you choose: generics when the type is known at the call site and speed matters (iterators, serde, axum handlers), and dyn when implementations are swapped at runtime or need to be stored side by side. Not every trait can be a dyn: generic methods, for example, aren't allowed ("dyn compatibility"), which is one reason Ledgerly's async trait methods return a boxed future instead (section 10).

Check yourself

Why can't a struct field have the type dyn Clock without a pointer?

  • Traits can never be used as field types
  • Its size isn't known; implementations differ in size
  • Fields must be Copy, and dyn isn't Copy
  • The vtable can only live inside a Box
SystemClock is zero bytes, FixedClock holds a mutex. A struct needs a fixed size, so the field holds a pointer (Arc, Box, &).

What does the Send + Sync requirement on Publisher guarantee?

  • Publishing an event never blocks the calling thread
  • Any implementation is safe to share across threads
  • Events are synced to the database in order
  • The publisher runs on a dedicated background thread
They're thread-safety markers. Without them, Arc<dyn Publisher> couldn't be used from a multi-threaded runtime.

When would generics be the better choice over dyn?

  • When the implementation is picked from the configuration
  • When the type is fixed and speed matters
  • When different implementations share one single vector
  • When the trait has many default method bodies
Generics avoid the indirect call and allow inlining. Runtime choice and mixed collections need dyn.
