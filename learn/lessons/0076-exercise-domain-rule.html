Making changes

Exercise: change a domain rule and its test

Your first real change to Ledgerly, test first: rejection reasons must be at least 10 characters, so "no" is no longer a valid reason. Then find out what else your rule touches.

By the end of this exercise

You've written a failing test, made it pass in the domain, read four test failures you didn't expect, and decided what each one means. That's the everyday loop of changing a Rust codebase.

Step 2: the rule

In RejectionReason::new, after let stripped = text::strip(text);, add a guard in the same style as the maximum-length check. Use text::utf16_len(stripped) so the count matches Java's (lesson 18). Bonus: make 10 a pub const MIN_LEN: usize next to MAX_LEN and use it in the message with format!.

Show a solution

Your new test passes. Now run the whole domain: cargo test -p ledgerly-expenses domain.

Step 3: the surprise

Four tests you didn't touch. For each one, open the line from the panicked at message and decide:

  • Is the test using a short reason incidentally (e.g. e.reject(actor, "reason"))? Then the test data is out of date: give it a longer reason.
  • Or is the test about short reasons? Then the rule really changes behaviour, and the test's expectation must change deliberately.
What you should find
All four use short reasons incidentally: "reason" in the 30-pair workflow test, "no"-style reasons in the others, and a short sample text in the printing test. Updating the test data is right here. In the real project, Ledgerly's rule (from CLAUDE.md) still applies: never weaken a parity test to make it pass. A parity test failing would mean Rust now disagrees with Java, and the fix belongs in Java first.

Step 4: finish the loop

  1. cargo test -p ledgerly-expenses domain is green.
  2. cargo clippy -p ledgerly-expenses --all-targets -- -D warnings and cargo fmt.
  3. Look at git diff: one rule, one new test, four updated test inputs.
  4. Throw it away: git restore . && git switch - && git branch -D practice/rejection-reason.

Check yourself

Why write the test before the rule?

  • The compiler requires tests to exist before code
  • To watch it fail, proving it checks something
  • Tests run faster when they are written first
  • clippy rejects functions that have no test yet
A test that never failed might not test anything. Red, then green.

Why text::utf16_len and not stripped.len()?

  • len() is not available on a &str slice
  • len() counts bytes; Java counts UTF-16 units
  • utf16_len is faster for short strings in Rust
  • len() includes the whitespace that was stripped
Ten euro signs are 10 UTF-16 units for Java but 30 bytes. Ledgerly matches Java's counting (18).

A parity test fails after your change. What does Ledgerly's process say?

  • Update the parity test to match the rule
  • Don't weaken it; behaviour changes start in Java
  • Mark it ignored and continue with the work
  • Delete it, since parity tests are optional checks
Parity tests define "same as Java". A rule change goes to Ledgerly-Java first, then re-vendored.
