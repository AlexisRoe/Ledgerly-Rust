unsafe, briefly

Reading unsafe in dependencies

forbid(unsafe_code) covers Ledgerly's own crates. Its dependencies (Tokio, hyper, sqlx, rustls…) contain plenty of unsafe. You don't audit them line by line; you judge them, the way you'd judge an npm package, with some Rust-specific signals.

By the end of this lesson

You can read a // SAFETY: comment, know what Miri and cargo-deny contribute, and use a short checklist before adding a crate.

Warm-up
The five things unsafe allows?
Dereference raw pointers, call unsafe functions (FFI), use mutable statics, implement unsafe traits, read union fields. (121)
What is a "safe abstraction"?
A safe API whose authors proved that every use keeps the rules, around unsafe internals. (121)

What good unsafe code looks like

  • Every unsafe fn has a # Safety doc section: the caller's obligations.
  • Every unsafe { } block has a // SAFETY: comment: why the obligations hold here. Clippy's undocumented_unsafe_blocks lint enforces it.
  • Blocks are small, and wrapped in a safe function as soon as possible.

When you read a dependency, these comments are where to look: each one is a claim you can check.

Tools

Mirian interpreter that runs tests and detects undefined behaviour (use after free, invalid aliasing). cargo +nightly miri test.
cargo-denyknown vulnerabilities (RustSec advisory database), licences, banned crates, allowed sources. Ledgerly runs it in just check.
cargo-geigercounts unsafe usage per dependency, to see where it concentrates.
In Ledgerly: supply-chain rules

deny.toml refuses yanked versions and known advisories (each exception has a written reason), allows only permissive licences, bans a second HTTP client and OpenSSL, and accepts crates.io only. The hard rules in CLAUDE.md add: new dependencies need a reason in the commit message.

Before adding a crate

  1. Does std or an existing dependency already do it?
  2. Who maintains it, how many people use it (downloads, reverse dependencies), when was the last release?
  3. How much unsafe, and is it documented with SAFETY comments? Is it tested under Miri?
  4. Does cargo deny check pass with it?
  5. What does it pull in? cargo tree -p the-crate.
Where the comparison breaks

An npm package can't corrupt V8's memory, but it can run install scripts and do anything at run time. A crate can run code at build time too (build.rs, proc macros), and with unsafe or FFI it can corrupt memory. Rust's ecosystem compensates with culture and tooling: documented unsafe, Miri, RustSec. The supply-chain questions are the same as for npm; the answers are checked differently.

Check yourself

What should a // SAFETY: comment explain?

  • That the block was reviewed by a second person
  • Why the unsafe operation's requirements hold right here
  • Which compiler version the block was tested with
  • How fast the block is compared to safe code
It's the local proof, which a reviewer can check.

What does Miri find that ordinary tests don't?

  • Slow functions that should be optimised later
  • Undefined behaviour that happens to work today
  • Crates with licences that aren't allowed
  • Public functions that are missing their docs
UB can pass every test and still break with a new compiler or CPU.

Does #![forbid(unsafe_code)] in Ledgerly's crates stop unsafe code in Tokio?

  • Yes, the lint applies to the whole dependency tree
  • No; lints apply only to the crate declaring them
  • Yes, but only in release builds of the binary
  • No, because Tokio is linked as a C library
Dependencies are judged and checked with other tools: review, Miri, cargo-deny.
