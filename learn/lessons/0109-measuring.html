Memory and performance

Measuring: release builds, benchmarks, profiles

Performance intuition is unreliable, in any language. Rust adds a trap of its own: debug builds can be 10–50× slower than release builds, and differently so. Measure the build you ship.

By the end of this lesson

You can read a [profile.release], run a fair micro-benchmark with black_box, and know which tool to reach for: criterion for benchmarks, a sampling profiler for "where does the time go".

Debug vs release

cargo build and cargo test use the dev profile: no optimisation, fast compiles, debug assertions and overflow checks on. cargo build --release optimises (Cargo: profiles). Never judge speed from a debug build.

In Ledgerly

lto = "fat" optimises across all crates at link time, and codegen-units = 1 lets the optimiser see each crate whole: slower builds, faster binary. strip drops symbols for a smaller image. panic = "unwind" (the default, written down) keeps a panic in one request from killing the process.

A micro-benchmark, and its traps

Run both. On the author's machine, release made building 100k strings with one presized buffer 2.7× faster than 100k format!s, while in debug the two were the same. The benchmark uses std::hint::black_box, which hides a value from the optimiser (std: black_box). Without it the optimiser may delete work whose result is unused, or compute it at compile time, and you'd be measuring nothing.

For real measurements use criterion: it warms up, repeats, and reports confidence intervals and changes since the last run. Benchmarks live in benches/ and run with cargo bench.

Profiling: where does the time go?

A benchmark answers "how fast is this?"; a profiler answers "what is slow?". On macOS and Linux, samply records a release binary and opens the result in the Firefox profiler: samply record ./target/release/ledgerly. Set debug = true in [profile.release] (temporarily) so function names show up. For a running async service, add tokio-console or look at the tracing spans you already have: Ledgerly's are exported to OpenTelemetry.

Where the comparison breaks

Node has one build and a JIT that warms up while running; you profile with --inspect and the Chrome DevTools. Rust's optimisation happens entirely at compile time and depends on the profile. That makes results reproducible, and it means a test suite's timings (debug) say nothing about production (release).

Check yourself

Your test suite shows a function takes 6 ms. What does that say about production?

  • Production will take the same 6 ms
  • Little: tests run unoptimised debug builds instead
  • Production will be exactly twice as fast
  • Production will be slower because of tracing
Measure with --release; debug builds can be many times slower.

What does black_box(x) do in a benchmark?

  • Measures the time it takes to compute x
  • Stops the optimiser from removing or precomputing work
  • Runs x on a separate thread to isolate it
  • Hides x from the debugger and the profiler
It returns x unchanged, but the optimiser must assume anything could have happened to it.

What does lto = "fat" trade?

  • Smaller binaries for slower code at runtime
  • Longer builds for optimisation across all crates
  • Safety checks for a faster development build
  • Debug symbols for a faster linker step
Link-time optimisation lets the optimiser inline across crate boundaries.
