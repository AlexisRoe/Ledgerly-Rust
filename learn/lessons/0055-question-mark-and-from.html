Error handling the Ledgerly way

? and From: errors that convert themselves

Each layer of Ledgerly has its own error type. ? moves errors up through the layers, and a From implementation at each step translates them: domain error → use-case error → HTTP problem.

By the end of this lesson

Given a ? in Ledgerly, you can say which error type goes in, which comes out, and which From implementation connects them.

Each type describes failures in its layer's terms. Higher layers wrap lower ones, which is the TS pattern throw new UseCaseError("…", { cause: e }), but typed.

When there's no From: map_err

At the web boundary, a UseCaseError becomes a Problem through an explicit function rather than From. The mapping is a deliberate decision (which status, which message) that deserves a name you can search for (lesson 58).

Where the comparison breaks

In TS, an error thrown deep in the database driver arrives at your Express error handler untouched and untyped. Rust forces every layer boundary to say what it does with the errors from below: wrap them (#[from]), translate them (map_err), or handle them (match). That's more to write, but you can always tell where an HTTP 500 came from.

Check yourself

In a function returning Result<_, UseCaseError>, expense.approve(actor)? fails. What does the function return?

  • The ExpenseError itself, with no conversion
  • UseCaseError::Refused, wrapping the original ExpenseError
  • A generic error built from text
  • UseCaseError::NotFound, used for every refusal
? calls the From<ExpenseError> impl generated by #[from], which wraps it in Refused.

You add a call returning Result<_, StorageError> and use ?, but UseCaseError has no matching variant. What happens?

  • The error is silently converted into text
  • Compile error: From<StorageError> isn't implemented for it
  • It compiles; the error is boxed automatically
  • It panics when the call first fails
Add a #[from] variant, write a From impl, or use map_err.

Why does the web layer use map_err(|e| problem::failure(&e)) instead of a From impl?

  • Problem lives in another crate, so From is impossible
  • Mapping errors to HTTP is a decision worth naming
  • map_err is faster than From for large error types
  • From only works with the ? operator inside loops
Either would compile. A named function makes the status mapping easy to find, read and test (it has its own tests in web/problem.rs).
