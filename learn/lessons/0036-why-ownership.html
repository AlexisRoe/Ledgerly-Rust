Ownership and borrowing

Why ownership: memory without a GC

JavaScript frees memory "eventually", whenever the garbage collector notices nobody uses an object. Rust frees it at a point the compiler knows in advance. Three rules make that possible.

By the end of this lesson

You can state the three ownership rules, say when a value is dropped, and explain why a Ledgerly database transaction rolls back by itself when a ? returns early.

Stack and heap, in one paragraph

Values whose size is known at compile time (numbers, bool, a TeamId, a fixed array) live on the stack, which is fast and cleaned up automatically when a function returns. Values that grow (a String's text, a Vec's elements) live on the heap, and someone must free that memory exactly once. Free it too early and you have a crash or security hole. Free it twice, same. Never free it, and you leak. JavaScript hands the problem to a garbage collector. C hands it to you. Rust hands it to the compiler, through ownership (Book 4.1).

The three rules

  1. Each value has an owner, a variable or a field.
  2. There's exactly one owner at a time.
  3. When the owner goes out of scope, the value is dropped (its memory and any other resources are released).

No free() calls, no GC pauses: the compiler inserts the drop at each closing brace. That's also why section 1's main could write drop(runtime) to end the runtime at a precise moment.

Drop is more than memory

"Release resources" includes files, sockets, locks, and database transactions. TS has try/finally and the newer using declarations for this. In Rust every value works that way.

In Ledgerly: a transaction that can't be left open

This function owns transaction. Every ? before commit() is an early return, and when the function returns, transaction goes out of scope and is dropped. sqlx's transaction rolls back on drop unless it was committed. So a refused approval, a database error or a failed event publish leaves no half-written change behind. There's no catch/rollback boilerplate, and nobody can forget it.

Where the comparison breaks

In JS, const a = obj; const b = obj; gives you two references to one object, and the GC keeps it alive while any reference exists. Rule 2 forbids that kind of sharing by default: assigning a String to another variable moves ownership. That's the next lesson, and it's the single biggest mental shift from TypeScript.

Check yourself

When is the String in let note = String::from("x"); freed?

  • When the garbage collector next runs a cycle
  • When note's owning scope ends at its brace
  • When the program exits and memory is reclaimed
  • When you call free(note) somewhere explicitly later on
Rule 3: the owner going out of scope drops the value. The compiler knows exactly where.

An approval is refused and expense.approve(actor)? returns early. What happens to the open transaction?

  • It stays open until a timeout closes the connection
  • It's dropped, and dropping it rolls it back
  • It commits whatever was written up to that point
  • It panics, because transactions must be closed by hand
The function returns, the owner transaction goes out of scope, and its drop code rolls back.

Which value lives entirely on the stack?

  • String::from("EUR")
  • vec![1, 2, 3]
  • 42_u32
  • Box::new(42)
A u32 has a fixed size. String, Vec and Box keep a small handle on the stack and their contents on the heap.
