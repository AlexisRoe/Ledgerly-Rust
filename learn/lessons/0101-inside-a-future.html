Concurrency and async internals

Inside a future: poll and Waker

A JS Promise is pushed: it resolves and runs your callbacks. A Rust future is pulled: an executor asks it "are you done yet?", and it answers ready or not yet, I'll tell you when to ask again. You'll write both sides.

The trait

The contract (std: Future):

  • poll must never block. It does what it can and returns Ready(value) or Pending.
  • Before returning Pending, the future must arrange for cx.waker() to be woken when progress is possible (a socket became readable, a timer fired). Typically it stores cx.waker().clone() where the event source can find it.
  • When woken, the executor polls it again. A future that returns Pending and arranges no wake-up is never polled again: it hangs forever.

The other side: an executor

That's a real, if minimal, executor. Tokio is the same loop at industrial scale: many tasks, a queue of woken ones, worker threads, and a reactor that turns OS events (epoll/kqueue) into wake() calls.

What async fn compiles to

The compiler turns each async fn into a state machine: an enum with one variant per .await point, holding the locals alive there, and a poll that resumes from the current state. .await means "poll the inner future; if Pending, return Pending myself". That's why futures need no heap allocation per call, and why they're lazy: nothing happens until the first poll.

Where the comparison breaks

A Promise starts work when created and pushes its result to callbacks via the microtask queue. A future does nothing until polled, has no built-in result storage, and can be dropped mid-way, which cancels it (lesson 103). Same async/await syntax, inverted control flow.

Check yourself

A hand-written future returns Pending without storing or calling the waker. What happens?

  • The executor polls it again in a busy loop
  • It may never be polled again, so it hangs
  • The runtime panics with a missing waker error
  • It is retried automatically after about one second
Executors poll only woken tasks. No wake, no progress.

What does x.await do inside an async fn's generated poll?

  • Blocks the whole thread until x has finished
  • Polls x; if Pending, returns Pending as well
  • Spawns x as a separate runtime task
  • Registers a callback, the way Promise.then would
Pending propagates outward to the task; the waker brings the poll back in.

Why must poll never block?

  • Because blocking inside poll is a compile error
  • It stalls every task sharing that executor thread
  • Because the Waker cannot be cloned while blocking
  • Because futures must always return Ready at first
Cooperative scheduling: tasks give the thread back by returning. Lesson 104 shows the fix.
