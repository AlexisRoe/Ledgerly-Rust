The libraries Ledgerly is built on

tracing, metrics and secrecy

Three small libraries for running in production: structured logs (like pino), counters for Prometheus (like prom-client), and a wrapper that keeps passwords and tokens out of both.

By the end of this lesson

You can read and add a log line with fields, increment a counter, and handle a secret value the way Ledgerly's rules require.

Debug. A derived Debug prints every field, secrets included, unless the field's type prints something else. (50)

tracing: structured logging

  • Macros by level: trace!, debug!, info!, warn!, error!. Fields go first as key = value, then the message.
  • %value records the field with Display, and ?value with Debug.
  • Spans group events: every request runs inside a span carrying its traceId, so every log line inside it gets the id. It's like AsyncLocalStorage, built in (tracing docs).
  • Where the output goes is configured once, in crates/app/src/logging.rs: JSON lines in Spring Boot's ECS format, so Ledgerly's logs look exactly like Java's.

metrics: counters for Prometheus

A counter with a label, incremented only after the commit succeeded. The exporter serves all metrics on the management port at /actuator/prometheus (metrics docs).

secrecy: secrets that can't leak by accident

  • SecretString's Debug prints [REDACTED], and it has no Display. So format!("{password}") doesn't compile, and {:?} of a config or request struct can't reveal it.
  • Reading it requires an explicit, greppable call: password.expose_secret(), used only where the value is really needed (hashing it, in crates/identity/src/password.rs).
  • It's zeroed in memory when dropped (secrecy docs).
In Ledgerly: a test that guards the rule

The project rule (from CLAUDE.md): passwords, tokens, keys, cookies and Authorization headers are SecretString from the moment they're read, and never logged. The parity suite's log-hygiene tests check the running app's logs too.

Where the comparison breaks

In Node, keeping a token out of the logs depends on remembering pino's redact paths. In Rust the type does it: a SecretString field has no way to print itself, so leaking it requires writing expose_secret(), and that shows up in review.

Check yourself

What does tracing::error!(error = %storage, "Unhandled exception") record for error?

  • The Debug output of storage, with its fields
  • The Display output of storage, its error message
  • Only the type name of storage, nothing else
  • A stack trace captured at the call site
% means Display; ? would mean Debug.

What happens with println!("{}", password) when password: SecretString?

  • It prints the password as plain text output
  • It prints [REDACTED] instead of the actual value
  • It doesn't compile, since SecretString has no Display
  • It panics at runtime to stop the leak
No Display impl, so {} is a type error. {:?} would print [REDACTED].

Why is the transitions counter incremented after commit()?

  • Metrics can only be recorded outside a transaction
  • So only really stored transitions are counted
  • The counter needs a free database connection first
  • Prometheus rejects counters updated inside async code paths
A refusal or a failed commit returns earlier via ?, so it's never counted.
