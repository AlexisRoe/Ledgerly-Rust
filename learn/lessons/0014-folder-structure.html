Basic syntax and code organisation

Folder structure of a crate and of this repo

Cargo gives special meaning to a few folder names. Ledgerly adds a second convention on top: the same layers in every module crate.

By the end of this lesson

Looking at a path such as crates/teams/src/web/dto.rs or crates/shared/tests/outbox.rs, you can say what kind of code is in it and how it gets compiled.

Warm-up
What's the difference between pub and pub(crate)?
pub(crate) is visible anywhere in the same crate, never in other crates. pub is visible to anyone who can reach the module.
What does pub use domain::Category; in lib.rs do?
It re-exports Category at ledgerly_expenses::Category, even though domain is private.

What Cargo knows about folders

Cargo finds targets by convention (Cargo book: package layout), so the folder name decides how a file is compiled:

Folder / fileNode analogueNote
src/lib.rs"main" / "exports" entryWhat other crates import
src/main.rs, src/bin/*.rs"bin" in package.jsonEach file is a separate binary crate that can use the library
tests/*.rs__tests__/ or *.e2e.tsEach file is compiled as a separate crate, like an outside user
build.rsa "prebuild" scriptReal Rust code that runs at build time
In Ledgerly: the targets that exist
  • crates/app/src/main.rs → the ledgerly binary (renamed in [[bin]]); crates/app/src/lib.rs → the library it calls.
  • crates/app/tests/startup.rs, architecture.rs, … → integration tests. They start the real binary or inspect the workspace.
  • crates/shared/tests/outbox.rs etc. → integration tests against a real Postgres.
  • crates/shared/build.rs → reads the vendored SQL migrations and embeds them into the crate, so the binary can check the database schema at startup.
  • crates/parity-tests/src/bin/parity.rs → the runner behind just parity, which prints passed / ignored / failed per milestone.

Ledgerly's own convention: one crate per module, same layers inside

Inside a module crate like expenses the layers are always the same, like a hexagonal/clean architecture in a NestJS project:

ModuleContainsDepends on
domain/Pure business rules (Expense, Action, errors). No I/O, no asyncnothing
application/Use cases: open a transaction, ask the domain, persist, publishdomain, persistence
persistence/SQL in and out of Postgresdomain
web/HTTP: routes, request/response DTOs, error → problem JSONapplication
facade.rs, events.rsThe only things other crates may use

A small module uses files instead of folders (teams/src/domain.rs, teams/src/persistence.rs), but the names are the same. Unit tests live next to the code they test: web/tests.rs, application/tests.rs, or a mod tests at the bottom of a file.

Where the comparison breaks

In a TS project, any file can import any other, and the layering is just good manners (or an ESLint rule). In Ledgerly, crossing a crate boundary the wrong way is a compile error, and the layering inside a crate is guarded by privacy (pub(crate)) plus a test that reads cargo metadata (crates/app/tests/architecture.rs).

Try it

For each path, say (1) library module, binary, integration test or build script, and (2) which layer:

  1. crates/teams/src/web/dto.rs
  2. crates/receipts/src/scanner.rs
  3. crates/app/tests/probes.rs
  4. crates/expenses/src/application/transition_expense.rs
Answers
1: library module, web layer (request/response shapes). 2: library module of receipts, the virus-scanner adapter (infrastructure, like persistence). 3: integration test of app (health probes). 4: library module, application layer (the submit/approve/… use case).

Each file in tests/ is compiled as its own crate and sees only pub items, exactly like an outside user. Unit tests (mod tests inside src/) see private items.
