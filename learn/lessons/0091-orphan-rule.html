Traits in depth

Coherence: the orphan rule

You can't implement a foreign trait for a foreign type. That rule guarantees there is never more than one impl of a trait for a type, anywhere in a program. When it gets in your way, wrap the type.

By the end of this lesson

You can tell which impls are allowed in your crate, read E0117, and work around it with a newtype.

A one-field tuple struct, a distinct type around another. Nothing: same size and layout. (26)

The rule

An impl Trait for Type is allowed in your crate only if the trait or the type is defined in your crate (simplified; the full rule allows some generic cases, Reference: orphan rules).

ImplAllowed?
your trait for your typeyes
foreign trait (Display, Deserialize) for your typeyes
your trait for a foreign type (Vec<T>, str)yes: extension traits
foreign trait for a foreign type: impl Display for Vec<Line>no, E0117

Why: if two crates could both write impl Display for Vec<Line>, a program using both would have two answers to "how does this print?". Rust rejects the possibility up front, so adding a dependency can never make your code ambiguous.

In Ledgerly: both allowed directions

Local trait (Environment), foreign type (HashMap): allowed. Tests pass a plain map as the environment instead of real environment variables.

Foreign trait (serde's Deserialize), local type (ExpenseId and friends, generated by the macro): allowed.

The workaround: a newtype

Ledgerly's id types are this pattern at scale: struct TeamId(Uuid) may implement Deserialize its own way (canonical form only), which Uuid itself never could inside Ledgerly. The cost is forwarding: the wrapper has none of the inner type's methods unless you expose them.

Where the comparison breaks

TS has nothing like it: module augmentation lets any package add members to any interface, and conflicts surface late, if at all. Rust's coherence is stricter, and it's also what makes trait resolution predictable: given a type and a trait, there's at most one impl, and the compiler can always find it.

Check yourself

Which impl fails with E0117 in Ledgerly's expenses crate?

  • impl Display for ExpenseStatus
  • impl MyTrait for Vec<Expense>
  • impl Display for Vec<Expense>
  • impl From<Uuid> for ExpenseId
Display and Vec are both std's. Vec<Expense> is still a foreign type, even though Expense is local.

What does the orphan rule protect against?

  • Slow compile times in very large workspaces
  • Two crates giving conflicting impls for one type
  • Traits being implemented for private types only
  • Runtime errors from missing trait method bodies
Coherence: at most one impl per (trait, type), program-wide.

The usual price of the newtype workaround?

  • An extra allocation for every wrapped value
  • The inner type's methods need forwarding
  • A vtable lookup on each method call
  • The wrapper can't be used in generics
Zero run-time cost, some boilerplate. (Implementing Deref to skip forwarding is tempting; lesson 93 explains why it's discouraged.)
