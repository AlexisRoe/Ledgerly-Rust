Ownership and borrowing

Lifetimes, enough to read them

A lifetime like 'a is a name for "how long a borrow is valid". The compiler infers nearly all of them. You only need to read the few that are written out.

By the end of this lesson

You can read &'static str, Formatter<'_> and fn summary_for<'a>(&'a self, connection: &'a mut PgConnection, …) -> SummaryFuture<'a>, and say in plain words what each promises.

Elision rules in short: one reference in → the output borrows from it. A method with &self → the output borrows from self. Otherwise you must write it out (Book 10.3, "Lifetime Elision").

Why &'static str in errors? ExpenseError::RuleViolated("Receipts are still being scanned") stores a pointer to a literal, which costs no allocation and can never dangle. Messages built at runtime need String instead, as in InvalidInput { message: String }.

In Ledgerly: an async method that borrows

Read it as: "the future I return borrows both me and the connection, so neither may go away (or be used by anyone else) until that future has finished." Without 'a the compiler couldn't know that the returned future still holds the connection. This shape (a trait method returning a boxed future) is the one place where Ledgerly writes lifetimes regularly. Section 10 explains why.

Where the comparison breaks

There is nothing like this in TypeScript, because the GC keeps anything alive that's still referenced. A lifetime doesn't change how long a value lives; it's a constraint the compiler checks. If you find yourself fighting lifetimes in a change to Ledgerly, the usual answer is to own the data (String, Vec, a clone of an Arc) instead of borrowing it.

Check yourself

What does &'static str as a return type promise?

  • The text is stored in a static global variable
  • The text stays valid for the whole program run
  • The text can never be printed or compared
  • The function itself must be declared as const
'static means "lives as long as the program". String literals do, because they're part of the binary.

Why doesn't fn strip(text: &str) -> &str need a written lifetime?

  • Lifetimes are optional and only serve as documentation
  • Elision ties the output to the single input
  • &str values always have the 'static lifetime anyway
  • The function is public, so lifetimes are inferred
The elision rules fill in <'a>(text: &'a str) -> &'a str.

Why is InvalidInput::message a String while field is a &'static str?

  • Struct fields can't hold two borrowed strings together
  • Field names are literals; messages come from format!
  • Messages are longer than 'static strings may be
  • It's arbitrary; the two types are fully interchangeable
"merchant" is fixed text. format!("Merchant is longer than {}", …) creates a new String at runtime, which must be owned.
