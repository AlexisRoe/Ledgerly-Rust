Newtypes: branded types done right

A one-field tuple struct around an existing type. It costs nothing at runtime, and Ledgerly uses it to make swapped ids and unvalidated text impossible.

By the end of this lesson

You can explain why TeamId, ExpenseId, Merchant and Money exist instead of bare Uuid, String and Decimal, and recognise the "parse, don't validate" pattern in any Ledgerly constructor.

The bug that branded types prevent

In TS a brand is a type-level fiction that a cast can forge. A Rust newtype is a real, distinct type. Because its field is private, the only ways to make one are the constructors its module provides. And it's free: a TeamId is stored exactly like a Uuid, 16 bytes, no wrapper object (Rust by Example: New Type Idiom).

In Ledgerly: seven id types from one macro

macro_rules! typed_id stamps out the same struct and methods for UserId, TeamId, ExpenseId, ReceiptId, InvitationId, ImportId and EventId ($name is the macro's placeholder; reads it fully). #[serde(transparent)] makes the JSON a plain string, so the wrapper is invisible on the wire. And the doc test you saw in lesson 10 proves that swapping two ids doesn't compile.

Parse, don't validate

The second use: a newtype whose constructor validates. If you hold a Merchant, it's valid, because there's no other way to get one.

Compare with a TS service that calls validateMerchant(s) and passes the same string on. Every later function has to trust that someone validated it. With newtypes, the type carries the proof: Expense's field is merchant: Merchant, not String (Alexis King, "Parse, don't validate"). Ledgerly does the same with Note, RejectionReason, Money (always positive, right decimals, fits the column) and Currency.

Where the comparison breaks

A newtype doesn't inherit the inner type's methods. TeamId has no .to_string() until someone implements Display, and Merchant has no .len(). That's on purpose: you expose exactly the operations that make sense (as_str, as_uuid). TS brands inherit everything from string, including .toUpperCase() on an id.

Check yourself

What does a TeamId cost at runtime compared with a bare Uuid?

  • An extra heap allocation for each wrapper
  • A type tag stored next to the UUID
  • Nothing; it's laid out exactly like a Uuid
  • A runtime check on every function call
A single-field struct has the same layout as its field. The distinction exists only at compile time.

Code in the web layer has a String from JSON and needs a Merchant. What must it do?

  • Cast it with as, like a brand
  • Write Merchant(text) directly inside the web handler
  • Call Merchant::new(&text) and then handle the Result
  • Nothing; String is accepted where Merchant is
The field is private, so Merchant(text) only works inside its module. The only public way in is the validating constructor.

Why does TeamId have #[serde(transparent)]?

  • So it compares equal to raw UUID values
  • So its JSON is the plain UUID string
  • So it becomes public outside the shared crate
  • So the macro generates a v4 constructor too
Without it, serde would serialise the tuple struct as an array, ["…"]. Transparent means "serialise exactly like the inner value".
