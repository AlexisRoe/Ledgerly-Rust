Ownership and borrowing

Copy and Clone

Some types are so small and simple that "moving" them just copies them. Others can be duplicated, but only when you ask with .clone(). Which is which is part of each type's design.

By the end of this lesson

You can tell why actor and the ids are passed around freely while a String moves, and why pool.clone() and clock.clone() in Ledgerly are cheap while expense.clone() would not be.

A type gets them by #[derive(Clone, Copy)], and Copy is only allowed if every field is Copy. A type that owns heap memory (String, Vec) can never be Copy, because two owners of one buffer would free it twice (Book 4.1, "Stack-Only Data: Copy").

In Ledgerly: Copy by design

Actor (a user id plus a role), Action, ExpenseStatus, Role, every id type and even Money derive Copy. So approve takes actor by value and passes it on to allowed_target, and the caller still has its own actor. Accessors return copies: pub const fn money(&self) -> Money. These types behave like JS primitives.

By contrast Merchant wraps a String, so it's Clone but not Copy, and its accessor lends it: fn merchant(&self) -> &Merchant.

Cheap clones: handles to shared things

Eight use cases each get "the" database pool and "the" clock. PgPool and Arc<dyn Clock> are handles: cloning one copies a pointer and bumps a reference count, and all clones share the same pool. It's a JS reference, made explicit (). Cloning an Expense would really duplicate its strings and vector. So when you see .clone(), ask what the type is before worrying about cost.

Where the comparison breaks

In JS, primitives copy and objects share, and you can't choose. In Rust, each type decides: a struct of two ids can be as cheap to pass as a number (Copy), a big struct requires an explicit .clone() so the cost is visible, and sharing is a deliberate Arc. Sprinkling .clone() to silence move errors works, but borrowing (next lesson) is usually the better fix.

Check yourself

Why can Actor be passed to two functions in a row without .clone()?

  • Function parameters are always passed by reference in Rust
  • Actor is Copy, so each pass makes a copy
  • The compiler clones it automatically whenever it is needed
  • Actor is stored in a global and never moves
Actor derives Copy (it's an id and a role), so it's copied like a number.

Which type cannot derive Copy?

  • struct Actor { id: UserId, role: Role }
  • enum Category { Travel, Meals }
  • struct Merchant(String)
  • struct Version(i64)
String owns heap memory, so it isn't Copy, and a struct can only be Copy if all its fields are.

What does pool.clone() on a PgPool do?

  • Opens a second set of database connections
  • Makes another handle to the same shared pool
  • Copies every open connection into new memory
  • Moves the pool and leaves the original empty
The pool is reference-counted inside. Clones share it, which is why every use case can hold its own PgPool.
