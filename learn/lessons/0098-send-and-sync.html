Concurrency and async internals

Send and Sync, really

Two marker traits with no methods decide what may cross a thread boundary. The compiler derives them for you, which is why you rarely write them and often read them in errors.

By the end of this lesson

You can define both traits precisely, predict which std types have them, and fix a "cannot be sent between threads safely" or "future is not Send" error.

The definitions

T: Senda value of type T may be moved to another thread
T: Synca &T may be shared with other threads. Precisely: T: Sync exactly when &T: Send

Both are auto traits: a struct is Send if all its fields are, and so on. You never write impl Send in safe code (doing so is unsafe). Almost everything is both; the exceptions are the interesting part (Nomicon: Send and Sync).

In Ledgerly: requiring it on a trait

For a concrete type the compiler works out Send/Sync itself. For dyn Clock it can't (any type might be behind it), so the trait demands them as supertraits. Every port in Ledgerly (MalwareScanner, MembershipLookup, Publisher) does the same, because axum shares handler state across Tokio's worker threads.

"future cannot be sent between threads safely"

An async fn's future stores every local that's alive across an .await. If one of them isn't Send, the future isn't either, and tokio::spawn or an axum handler rejects it:

Fixes: end the non-Send value before the .await (a block { … } or drop(guard)), copy what you need out of it, or use a type designed to live across awaits (tokio::sync::Mutex, lesson 99). The compiler's note points at the exact variable and the .await.

Where the comparison breaks

Nothing in TS describes "safe to use from another thread", because JS objects are never shared between threads. In Rust, thread safety is a property of types, checked like any other. That's what "fearless concurrency" means: not that concurrency is easy, but that data races don't compile.

Check yourself

You replace Arc<Config> with Rc<Config> in axum state. What happens?

  • It works, and runs slightly faster than with Arc
  • A compile error: Rc is neither Send nor Sync
  • It compiles, then crashes under heavy concurrent load
  • It works, but only on a single worker thread
The check happens at compile time; there's nothing to crash.

What does T: Sync mean?

  • T's methods are synchronised with a lock
  • &T may be shared with other threads
  • T can only be used on one thread
  • T is copied whenever another thread reads
T: Sync ⇔ &T: Send.

An axum handler holds a std MutexGuard across an .await. Simplest fix?

  • Mark the handler function as unsafe
  • Drop the guard before the await
  • Wrap the guard itself in an Arc
  • Implement Send for the guard type
Scope the lock to the synchronous part; never hold a std lock across an await.
