Ownership and lifetimes in depth

Structs that borrow

A struct can hold references instead of owned data. Then it carries a lifetime parameter, and it can't outlive what it borrows. It's how parsers, views and "context" structs avoid copying.

By the end of this lesson

You can write a struct with a 'a parameter, give its methods the right return lifetimes, and decide when a borrowing struct is worth the trouble.

The shape

Header<'a> reads "a header borrowing from something that lives for 'a". '_ is the "elided lifetime" placeholder: "the one you'd infer anyway", here from line (rule 2). The TS version copies two substrings; the Rust version copies nothing, and the compiler makes sure nobody uses a Header after the line is gone.

In Ledgerly: a borrowed wiring context

At startup, the app passes this to the receipts module's constructor: a bundle of things the module needs. It borrows rather than owns because it lives only for the duration of the constructor call; the module clones what it wants to keep. It's TS's "options object", with the borrow checker making sure it isn't stashed away.

Methods: whose lifetime does the result get?

This is the most common surprise with borrowing structs. The struct is only a cursor; the words come from the text it points to. Writing &'a str says so, and then let a = w.next_word(); let b = w.next_word(); compiles.

When to own instead

Borrow (Struct<'a>)Own (String, Vec, Arc)
short-lived: a parse result, a view, a constructor's argumentsstored for later: state, caches, anything in a Router
hot path where copying matterssent to another task or thread (lesson 82)
the lifetime spreads to everything that holds itno lifetime parameters at all

A common, good default for application code: own data in long-lived structs, borrow in function parameters. That's what Ledgerly does almost everywhere; Modules<'a> is the exception because it never outlives startup.

Where the comparison breaks

A struct can't borrow from itself: struct Doc { text: String, first: &str } pointing into its own text doesn't work, because moving the struct would move the text and leave the reference dangling. Store an index range (first: Range<usize>) instead. (Lesson 102 shows how async Rust deals with exactly this problem.)

Check yourself

What does Header<'_> in a return type mean?

  • The header holds no references at all
  • Its lifetime is the one elision would infer
  • The header lives for the whole program
  • The lifetime is chosen at run time
'_ makes the hidden lifetime visible without naming it.

You store a Header<'a> in your app's long-lived state. What's the likely result?

  • It works, and the line is kept alive automatically
  • Lifetime errors; store owned Strings in state instead
  • It works, but the header is copied every time
  • A runtime panic once the line is dropped
Nothing keeps the line alive for you. Long-lived structs should own their data.

Why does next_word return &'a str rather than &str?

  • Because &str in a return type is not allowed
  • So words borrow the text, not the cursor itself
  • So the words are copied out of the text
  • Because methods taking &mut self cannot return references
Tied to &mut self, every word would block the next call.
