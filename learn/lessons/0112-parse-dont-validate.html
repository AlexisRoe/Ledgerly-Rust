Designing Rust code

Parse, don't validate, in depth

Lesson 26 named the idea. This lesson is the design technique: make invalid values impossible to construct, so code that receives a value never has to check it again.

By the end of this lesson

You can design a type with a private field and a fallible constructor, route serde through the same constructor, and decide where in a program parsing should happen.

Warm-up
When should an error be an enum, and when anyhow?
Enum when callers handle it; anyhow when they only report it. (111)
What does a newtype cost at run time?
Nothing: same size and layout as the wrapped value. (26, 106)

The recipe

  1. A newtype with a private field: pub struct Merchant(String);. Outside the module, nobody can write Merchant(any_string).
  2. One fallible constructor that checks and normalises: Merchant::new(&str) -> Result<Self, InvalidInput>. Also the place to trim, lowercase, round.
  3. Read-only access: as_str(), Display. No &mut to the inside, no Deref (lesson 93).
  4. Every entry point uses it: JSON through #[serde(try_from = "String")], the database through the row conversion, tests through the same new.
In Ledgerly

The module doc states the design. Note the second constructor just above it, stored: it's pub(crate) and skips the checks, because rows in the database were checked when they were written, and Java reads the column as it is. A deliberate, visible, crate-private back door.

Where to parse: at the edge

Parse as soon as untyped data enters (request body, query string, CSV row, environment variable) and pass typed values inward. The domain then takes Merchant, Money, TeamId, never &str. In TS you'd do the same with zod at the boundary; the difference is that zod's output type is still a plain string, so nothing stops other code from passing an unchecked one. A Rust newtype can't be faked.

Where the comparison breaks

TS branded types (string & { __brand: "Merchant" }) give the name but not the guarantee: a cast makes one from anything. Rust's privacy is enforced by the compiler, and the only constructor is yours. The cost is writing as_str() and conversions; the gain is that a whole class of "did anyone validate this?" questions disappears.

Check yourself

Why is Merchant's field private?

  • Private fields make the struct smaller overall
  • So new, with checks, is the door
  • Because tuple struct fields can't be public
  • So serde can't serialise the merchant text
Privacy turns "valid" from a convention into a guarantee.

With #[serde(try_from = "String")], what happens to {"email": "nope"}?

  • It deserialises, and validation happens later on
  • Deserialisation fails with the constructor's own error
  • serde silently replaces it with a default
  • It panics inside the serde derive code
serde builds the String, then calls your TryFrom.

Where should a CSV import turn text cells into typed values?

  • In the database layer, just before saving
  • Right after reading each row, at the edge
  • In every domain function that uses a value
  • Nowhere; strings are fine inside the domain
Parse once at the boundary; the rest of the code works with types that can't be wrong.
