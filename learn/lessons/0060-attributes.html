Macros and attributes

Attributes: #[…] and #![…]

The lines starting with # look like TypeScript decorators, and some behave like them. Most, though, are instructions to the compiler: what to compile, what to generate, what to check.

By the end of this lesson

You can sort every attribute you meet in Ledgerly into one of four kinds (generate, compile-conditionally, lint, configure a library) and say what it does.

Outer vs inner

  • #[attr] (outer) applies to the next item: a function, struct, field, module, or mod line.
  • #![attr] (inner, with !) applies to the enclosing item, usually the whole file/module or crate when it's at the top. Same idea as /// vs //! (Reference: attributes).

The four kinds in Ledgerly

KindExamplesEffect
Generate code#[derive(Debug, Clone, thiserror::Error)], #[tokio::test], #[tokio::main]a macro writes implementations or wraps the function
Conditional compilation#[cfg(test)], #[cfg(any(test, feature = "testing"))]the item exists only under that condition
Lints#![forbid(unsafe_code)], #[must_use], #[expect(clippy::…, reason = "…")], #![cfg_attr(not(test), deny(…))]turn checks on, off, or into errors
Configure a library#[serde(rename_all = "camelCase")], #[serde(transparent)], #[error("…")], #[from]"helper attributes" read by that library's derive
In Ledgerly: one of each

At the top of every crate: unsafe doesn't compile here, and nothing below can allow it.

cfg_attr(condition, attr) applies attr only when the condition holds: in production builds of the domain module, indexing and unchecked arithmetic are errors. Tests are exempt.

Clippy suggests "a method named cmp should be the Ord trait". Ledgerly disagrees on purpose and says why. Unlike #[allow], #[expect] fails if the lint stops firing, so stale exceptions get cleaned up.

The struct fields are snake_case in Rust, and the JSON keys become camelCase (team_id → teamId). Lesson 68.

Where the comparison breaks

TS decorators run at runtime and wrap classes or methods. Rust attributes act at compile time: they can remove code entirely (cfg), generate code (derive), or change what the checker accepts (lints). Nothing of an attribute remains at runtime except the code it generated.

Check yourself

What's the difference between #[forbid(x)] on a function and #![forbid(x)] at the top of lib.rs?

  • None at all; the exclamation mark is optional style
  • The first covers that function, the second the whole crate
  • The first is a lint, the second a derive macro
  • The first runs at runtime, the second at compile time
Outer attributes apply to the next item, inner ones to the enclosing item.

Why #[expect(lint, reason = …)] instead of #[allow(lint)]?

  • expect is faster to compile than allow in clippy
  • It fails once the lint stops, and records why
  • allow is deprecated in the 2024 edition of Rust
  • expect also suppresses the lint inside all the tests
An exception that's no longer needed becomes a warning (an error in Ledgerly's CI), and the reason is written next to it.

Where does FixedClock exist?

  • In every build, but it's hidden from the docs
  • In test builds, or with the testing feature on
  • Only in the ledgerly binary's optimised release build
  • Only in the parity tests, which run against Docker
#[cfg(any(test, feature = "testing"))]: otherwise the code isn't compiled at all, so it can't reach production.
