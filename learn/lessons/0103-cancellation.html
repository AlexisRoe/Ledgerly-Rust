Concurrency and async internals

Cancellation and structured concurrency

In Rust, cancelling async work is as simple as dropping its future. That's powerful and occasionally surprising: the work stops at whichever .await it was paused on, and code after it never runs.

By the end of this lesson

You can predict what a dropped future leaves behind, judge whether a branch in a select! loop is cancel-safe, and manage a group of tasks with JoinSet, abort and timeout.

Dropping is cancelling

A future only makes progress while it's polled. Drop it, and it's never polled again: its locals are dropped (RAII cleanup runs), and everything after its current .await simply never happens. Things that cancel:

  • the losing branches of select!;
  • tokio::time::timeout(limit, fut) when the limit passes;
  • handle.abort() on a spawned task (it stops at its next .await);
  • axum dropping a handler's future when the client disconnects;
  • dropping a JoinSet, which aborts every task still in it.

JS has no equivalent: a Promise can't be cancelled, so cancellation is opt-in via AbortSignal, checked by the code itself. In Rust it's the default, and you design for it.

Tokio documents cancel safety for every method that matters (select!: cancellation safety). A database transaction is safe by construction: dropped uncommitted, it rolls back.

In Ledgerly: cancelling on purpose

After the servers stop, the background tasks are aborted. The comment states the design: an event delivery cut off mid-way isn't lost, because its record in the outbox table stays open and the next start delivers it. Cancellation is safe because the state that matters is in the database, not in the task.

Structured concurrency with JoinSet

A JoinSet owns its tasks, so none can outlive the code that started them; it's Promise.all/allSettled with results as they arrive and cleanup built in (JoinSet). Prefer it over loose tokio::spawn calls whose handles nobody keeps.

Where the comparison breaks

A Node request handler keeps running after the client disconnects, unless you check a signal. An axum handler is dropped at its current .await. If a handler does two writes without a transaction, a disconnect between them leaves half the work done. Ledgerly's use cases do their writes inside one transaction, so a cancelled request rolls back cleanly.

What happens to unfinished tasks when a JoinSet is dropped?

  • They keep running detached in the background
  • They are aborted together with the set
  • The drop waits until all of them finish
  • The program panics because they were lost
That's the "structured" part: tasks don't outlive their owner.

Why is it safe for Ledgerly to abort the outbox dispatcher mid-delivery?

  • Because abort always waits until the delivery completes
  • Open deliveries stay in the database for later
  • Because events are delivered exactly once by Tokio
  • Because the dispatcher never awaits anything at all
Cancel-safe by design: the durable state lives outside the task.
