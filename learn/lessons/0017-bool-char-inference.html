Data types

bool, char and type inference

No truthiness, a real character type, and inference that's stronger than TypeScript's within a function and absent at its edges.

By the end of this lesson

You can predict when Rust needs a type annotation, read the turbofish ::<T>, and you won't trip over 'a' vs "a" or if count {.

Warm-up
Which type does .len() return, and why does Ledgerly write u32::try_from(x.len())?
usize. Converting to the narrower u32 can fail, and try_from makes that explicit, unlike as.
What does checked_add return on overflow?
None: it returns an Option.

bool: no truthiness

&&, ||, ! work as in TS, but only on bool, and they return bool, never one of the operands. There's no ?? trick with ||.

char: one Unicode scalar value

TypeScript has no character type: "a"[0] is a one-character string, and it counts UTF-16 units, so an emoji is two of them. Rust's char is a 4-byte Unicode scalar value written in single quotes: 'a', '€', '\u{00A0}'. Double quotes are always strings.

Ledgerly needs this because Java and Rust disagree about what counts as whitespace. A merchant name of one non-breaking space is valid in Java, so it must be valid here too. 'a'..='z' is an inclusive range of chars. matches! is lesson 33.

Where the comparison breaks

TS infers return types and widens literals (let x = 5 is number). Rust never infers across a function boundary, and an unconstrained integer literal defaults to i32. Turn on rust-analyzer's inlay hints: they show every inferred type in grey, which makes Ledgerly's terse code much easier to read.

Check yourself

Which condition compiles?

  • if rows.len() { … }
  • if note { … } (note: Option<Note>)
  • if !rows.is_empty() { … }
  • if rows.len() || 1 { … }
Conditions must be bool. There's no truthiness for numbers, options or strings.

What's '€' in Rust?

  • A one-character string, as in TS
  • A char: one Unicode scalar value
  • A syntax error; use double quotes
  • A lifetime annotation named euro here
Single quotes make a char. Strings use double quotes. (Lifetimes like 'a look similar but have no closing quote.)

Which of these always needs written types?

  • Every let binding inside a function body
  • A function's parameters and return type
  • Closure parameters passed to map or filter
  • Integer literals such as 42 or 1_000
Signatures are the contract, and they're always explicit. Inside bodies, inference does the rest.

What does "42".parse::<u8>() do differently from "42".parse()?

  • It parses faster by skipping all validation
  • It tells parse which type to produce
  • It returns the number, not a Result
  • It accepts only ASCII digits as input
The turbofish fills in parse's generic type parameter. Both return a Result.
