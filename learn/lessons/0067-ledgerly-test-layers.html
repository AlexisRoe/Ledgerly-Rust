Testing

Ledgerly's test layers

Five layers, from pure functions to a black-box suite that talks HTTP to the real container image. When you change something, this map tells you which tests will notice and which command runs them.

By the end of this lesson

For any change you might make, you can predict which layer of tests covers it, run that layer, and read a parity test.

In TS terms: layers 1–2 are your Vitest unit tests, layer 3 is Supertest against an Express app, and layer 5 is a Playwright/Postman API suite against a deployed container.

The parity suite

Ledgerly-Rust must behave exactly like Ledgerly-Java. The parity suite proves it from the outside: it only sends HTTP requests and writes SQL fixtures, so it could run against either implementation (ADR 0011).

  • mod m3: tests are grouped by the milestone that introduced them, and the runner reports passed/failed per milestone.
  • Every test names the Java test it ports in its doc comment. tests/inventory.rs checks that every Java test is either ported or listed in NOT_PARITY.md with a reason.
  • World is the fixture: a running app, a database to seed, helpers to log in.
Where the comparison breaks

Most TS projects mock the database. Ledgerly almost never does: layers 2–5 use real Postgres in Docker, because the SQL is part of what's being tested (sqlx checks it compiles, the tests check it does the right thing). The price is that just test needs Docker. Only the domain layer is fully pure, which is exactly why the domain is kept free of I/O.

Try it
  1. Run the pure tests only: cargo test -p ledgerly-expenses domain (no Docker needed).
  2. With Docker running: cargo nextest run -p ledgerly-expenses. Watch the first test start the shared Postgres container.
  3. Open crates/parity-tests/NOT_PARITY.md and find one Java test that's ported in-process instead, and why.

Check yourself

You change the wording of a domain error message. Which layer fails first?

  • The parity suite, the next time it runs
  • Domain or web tests that compare the message
  • The app's startup test, which prints all messages
  • None; messages are never checked by any tests
Messages are part of the contract with Java, so tests in web/problem.rs and the domain compare them, and the parity suite would catch it later too.

What does the parity suite not do?

  • Send HTTP requests to a running container image
  • Write SQL fixtures straight into the shared schema
  • Call Rust functions inside the app's own process
  • Validate the responses against the OpenAPI contract file
It's black-box: HTTP and SQL only, so the same tests could be pointed at Ledgerly-Java.

Which tests can run without Docker?

  • All of them; Docker only builds the image
  • Pure unit tests, such as the domain's tests
  • The web tests, since they run in-process
  • The parity tests, since they only speak HTTP
Anything that uses TestDatabase, starts the binary against a database, or the parity suite needs Docker.
