The libraries Ledgerly is built on

serde: JSON in and out

JSON.parse gives you any, and zod checks it at runtime. serde generates a typed parser and printer for each struct at compile time: #[derive(Deserialize)] in, #[derive(Serialize)] out.

zod → serde

  • rename_all = "camelCase": Rust field incurred_on ↔ JSON key incurredOn.
  • deny_unknown_fields: an unexpected key is an error, like zod's .strict(). This is part of Ledgerly's protection against mass assignment (OWASP API3).
  • Option<T>: the key may be missing or null. Why is everything optional here? So that a missing field becomes a proper 400 listing all violations (Validate::validate below the struct), as Java's Bean Validation does, instead of serde's first error.
  • Nested types (MoneyBody, CategoryBody, DateBody) have their own Deserialize, some hand-written to accept exactly Java's formats.

In Ledgerly: the wrapper is invisible on the wire

Recall #[serde(transparent)] on the id types (lesson 26): a TeamId serialises as the bare UUID string, not as ["…"]. And hand-written impl Serialize for Role (in role.rs) writes "OWNER" via as_str, keeping Java's spelling.

Where the comparison breaks

zod builds a validator object at runtime and infers a TS type from it. serde generates code at compile time from the Rust type, so the type is the schema and parsing is very fast. serde is format-agnostic: the same derives work for JSON (serde_json), YAML, TOML and more. Business validation (lengths, ranges) isn't serde's job; Ledgerly does it afterwards with Validate and the domain's constructors.

Why are all fields of CreateExpenseRequest Options, although most are required?

  • serde can only deserialise the optional fields of structs
  • So all missing fields are reported at once
  • Because the PATCH endpoint shares the same type
  • So the database can fill in default values
serde would stop at the first missing field. Optional fields plus Validate produce one 400 with all violations.
