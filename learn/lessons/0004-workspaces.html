Setting up and the toolbox

Workspaces

Ledgerly is a monorepo of nine crates. A Cargo workspace works like pnpm workspaces: one lock file, one build folder, shared settings.

By the end of this lesson

You can read the root Cargo.toml: which crates belong to the workspace, how settings and dependency versions are shared, and what the [profile.release] block does.

Warm-up
What's the difference between a package and a crate?
A package is one Cargo.toml. A crate is a unit of compilation: a library (lib.rs) or a binary (main.rs). One package can contain both.
What does cargo check skip that cargo build does?
Generating code: it type- and borrow-checks but produces no binary.
What is a cargo feature?
An optional, compile-time part of a crate, switched on in the dependent's Cargo.toml.

The root manifest

Notice what's not there: no [package]. The root is a "virtual manifest", so it describes the workspace but is not a crate itself.

In Ledgerly

The lints table is a design decision. unwrap_used = "deny" makes .unwrap() in production code an error whenever clippy runs (and just check always runs it). unsafe_code = "forbid" is a lint of the compiler itself, so unsafe doesn't even build. You'll see why in . Every crate's manifest contains [lints] workspace = true, so no crate can quietly opt out.

Profiles: debug vs release

cargo build uses the dev profile: fast to compile, slow to run, debug info included. --release uses this one. Ledgerly asks for whole-program link-time optimisation (lto) and one code-generation unit (smaller, faster binary, slower build) and strips symbols for the container image (Cargo book: profiles). Where the comparison breaks

In a pnpm monorepo, a cycle between packages is legal and only bites at runtime. Cargo refuses a dependency cycle between crates outright: if teams depends on expenses, then expenses can never depend on teams. Ledgerly uses this to enforce its module boundaries at compile time ().

Try it
  1. Open crates/teams/Cargo.toml. Which sibling crates does it depend on?
  2. Run cargo tree -p ledgerly-teams --depth 1 at the repo root to confirm.
  3. Find tokio in the root [workspace.dependencies], then find a crate that adds an extra feature to it (hint: crates/shared/Cargo.toml).

Check yourself

A crate's manifest says serde.workspace = true. Where does the version come from?

  • The newest serde release on crates.io
  • The entry in the root's [workspace.dependencies]
  • The version another member already uses
  • The serde entry in its lock
Versions (and default features) are written once in the root. A member can add features on top, as sqlx = { workspace = true, features = ["macros"] } does.

How many Cargo.lock files does Ledgerly's workspace have?

  • One, at the root
  • One per crate
  • One per binary
  • None; it's generated
A workspace has one lock file and one target/ directory, shared by all members.

Why can't ledgerly-shared depend on ledgerly-expenses?

  • Shared crates are not allowed any dependencies
  • The path would point outside the workspace
  • Expenses depends on shared, and cycles are refused
  • Workspace members may only depend on crates.io
ledgerly-expenses lists ledgerly-shared as a dependency, and cargo rejects cyclic dependencies between crates.

What does [workspace.lints.clippy] unwrap_used = "deny" do to a member crate?

  • Nothing unless it runs clippy with a flag
  • Makes .unwrap() a lint error after opting in
  • Removes unwrap from the standard library for it
  • Logs a warning at runtime when unwrap panics
Member crates opt in with [lints] workspace = true. Every Ledgerly crate does, so cargo clippy fails on an unwrap() in production code.
