Ownership and lifetimes in depth

Writing lifetime annotations

Lesson 41 taught you to read 'a. This one teaches you to write it: the three rules the compiler uses to fill lifetimes in for you, and what to write when they aren't enough.

By the end of this lesson

You can predict when a function signature needs explicit lifetimes, and write them so the result borrows from the right argument.

Why TypeScript never asks

In TypeScript every object lives as long as something references it; the garbage collector guarantees it. A function can return any reference it likes. Rust has no GC, so when a function returns a reference, the compiler must know which input it borrows from. Only then can it check, at each call site, that the caller doesn't drop that input while still using the result.

A lifetime parameter is that piece of information. It's a generic parameter, like T, but for "how long": fn longer<'a>(a: &'a str, b: &'a str) -> &'a str reads "for some span 'a during which both a and b are valid, the result is valid too". The caller doesn't pick 'a; the compiler infers the shortest span that works.

The three elision rules

Most signatures have no 'a because the compiler fills it in with three fixed rules (Reference: lifetime elision):

  1. Every reference in the parameters gets its own lifetime.
  2. If there is exactly one input lifetime, every reference in the result gets it.
  3. If a parameter is &self or &mut self, every reference in the result gets self's lifetime.

If the result still has a reference without a lifetime after these rules, you get E0106 "missing lifetime specifier", and you write it yourself. The rules are a guess about the common case, not inference from the body: the compiler never looks inside the function to decide.

In Ledgerly: rule 2 at work

One input reference, so the &str items borrow from text. Written out, it's fn java_lines<'a>(text: &'a str) -> impl Iterator<Item = &'a str>. Each line is a slice of the migration file's text: nothing is copied.

When you must write them

Give the result the lifetime of exactly the inputs it can borrow from, and no more. Tying name to 'a as well would compile, but it would force callers to keep name alive as long as they use the result, for no reason.

Where the comparison breaks

Generics in TS describe what a value is; lifetime parameters describe how long a borrow may be used. They don't exist at run time at all, and they never change what the code does: a lifetime error is the compiler refusing a program it can't prove safe. The fix is usually a better signature, or returning an owned value (String) instead of a reference.

Check yourself

Does fn first(words: &[String]) -> &str need explicit lifetimes?

  • Yes, every function returning a reference needs them
  • No, rule two applies: there is one input
  • No, because the compiler reads the function body
  • Yes, because slices always need named lifetimes
One input lifetime, so the output gets it. The compiler never reads the body to decide.

A method fn name(&self, fallback: &str) -> &str returns fallback sometimes. What happens?

  • It compiles, since rule one gives each input a lifetime
  • Rule three ties the result to self; fallback fails
  • It compiles, but returning fallback panics at run time
  • The compiler silently picks the shorter of the two lifetimes
With &self, elision assumes the result borrows from self. To return either, write fn name<'a>(&'a self, fallback: &'a str) -> &'a str.

Why does longer give both parameters the same 'a?

  • Two parameters can't have two different lifetimes
  • The result may borrow from either of them
  • It makes the function faster at run time
  • It forces both strings to have equal length
The result can only be trusted while both are alive, and one shared 'a says exactly that.

What does adding a lifetime annotation change in the compiled program?

  • Values stay in memory for the annotated duration
  • Nothing; it only changes what the compiler accepts
  • References become reference-counted for the annotated duration
  • The function is copied once for each lifetime
Lifetimes are erased after checking. They describe; they never extend.
