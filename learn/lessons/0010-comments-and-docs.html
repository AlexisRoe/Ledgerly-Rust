Basic syntax and code organisation

Comments and doc comments

Three kinds of comment: //, /// and //!. Two of them become documentation, and the code examples in them run as tests.

By the end of this lesson

You can tell at a glance whether a comment is a note, docs for the next item, or docs for the whole module, and you know that ``` blocks in docs are compiled and run.

Warm-up
What turns an expression into a statement?
A trailing semicolon. The statement's value is ().
Where does a function's return type go?
After ->: fn rank(self) -> u8. Without one, the function returns ().

The three kinds

// note, /* … */sameNothing; for the reader of the code
/// text/** JSDoc */ above a declarationThe item that follows: fn, struct, enum, field, variant
//! text@packageDocumentation / @moduleThe item that contains it: the module or crate (top of a file)

Doc comments are written in Markdown, not with @param tags. Rust signatures already carry the types. cargo doc --open renders them as HTML, and rust-analyzer shows them on hover (Book 3.4, rustdoc guide).

In Ledgerly: all three in one file

//! describes the crate ledgerly_expenses itself. /// describes routes. [`ExpenseEvent`] is an intra-doc link: rustdoc resolves the name like code does and warns if it doesn't exist.

Doc tests: examples that can't go stale

A fenced code block inside a doc comment is compiled and run by cargo test (Ledgerly: cargo test --doc inside just test). Ledgerly uses one to prove a point no ordinary test could, namely that some code doesn't compile:

The first block must compile and run. The second is marked compile_fail,E0308: the test passes only if it fails to compile with a type mismatch. If someone made ids interchangeable, this test would break (rustdoc: documentation tests). Other markers: ```text (not code, as in action.rs's diagram), ```ignore, ```no_run.

Where the comparison breaks

JSDoc examples are prose, and nothing checks them. Rust's are tests. Also, /// is not a stylistic variant of //: it attaches to the next item, so a /// before nothing (for example inside a function body, before a let) produces a warning, "unused doc comment".

Try it
  1. Hover over routes where crates/app/src/lib.rs calls ledgerly_expenses::routes (search for it). rust-analyzer shows the /// text.
  2. Run cargo doc -p ledgerly-shared --no-deps --open and open the id module. The //! text is the page's introduction.
  3. Run cargo test -p ledgerly-shared --doc id and find the compile_fail test in the output.

Check yourself

A file starts with //! Typed ids: one newtype per kind of thing. What does it document?

  • The first item declared below it
  • The module that this file defines
  • Nothing; it's an ordinary code comment
  • The crate's README on crates.io
//! documents the enclosing item. At the top of id.rs, that's the id module.

When does a compile_fail doc test pass?

  • When the code compiles and runs without panicking
  • When the code fails to compile, as expected
  • When the code panics while the test runs
  • Never; such tests are skipped by default
It asserts a compile error, optionally with a specific code like E0308. Useful to pin down what the type system forbids.

How do you document a parameter in a /// comment?

  • With a JSDoc-style @param tag for every argument
  • In Markdown prose, since types are in signatures
  • With an attribute such as #[param(name)] above it
  • Parameters can't be documented in Rust at all
rustdoc has no tags. Ledgerly's docs name parameters in backticks inside sentences, like "capped at limits.max_page_size".
