Traits in depth

AsRef, Borrow, Deref and flexible parameters

Three traits that all say "this can be seen as a reference to that", for different purposes. Used in parameters, they let one function accept &str, String and more, without making callers convert.

By the end of this lesson

You can choose between &str, impl AsRef<str> and impl Into<String> for a parameter, and say why Deref is for smart pointers only.

Choosing a string parameter

ParameterAcceptsUse when
&str"lit", &string (auto-deref)you only read it: the default
impl AsRef<str>also String by value, Box<str>…generic helpers, mostly for paths: impl AsRef<Path>
impl Into<String>"lit", Stringyou store it: a String is moved in, a literal converted once
StringString onlyyou store it and want callers to see the cost

TS doesn't need any of this: a string parameter takes any string. In Rust the choice says whether the function reads or keeps the text, and who pays for the allocation.

In Ledgerly: Into for stored text

Callers write UseCaseError::invalid("amount", "must be positive") or pass a format!(…) result. The literal is converted once; the formatted String is moved in without a copy.

The three traits

AsRef<T>"cheaply viewable as &T". A type may implement it for many targets: String is AsRef<str>, AsRef<[u8]>, AsRef<Path>…
Borrow<T>like AsRef, plus a promise: Eq, Ord and Hash give the same answers on the borrowed form. That's why a HashMap<String, V> can be queried with a &str: map.get("taxi").
Derefwhat *x and auto-deref use: Box<T>, Arc<T>, String → str, Vec<T> → [T], MutexGuard. One target per type. It's why arc.method() calls the inner value's method.
Where the comparison breaks

It's tempting to implement Deref on a newtype so it "inherits" the inner type's methods, like class Merchant extends String. Don't: every method of the inner type leaks through, including ones that break your invariants, and method resolution gets confusing. The API guidelines say Deref is only for smart pointers. Ledgerly's Merchant has an explicit as_str() instead.

Check yourself

A constructor stores a name in a String field. Best parameter type for callers?

  • name: &str
  • name: impl Into<String>
  • name: impl AsRef<str>
  • name: &String
It keeps the text: an owned String moves in for free, a literal is converted once. With &str, a caller holding a String pays for a copy.

Why can HashMap<String, u32>::get take a &str?

  • The map converts every key into a &str
  • String: Borrow<str> promises equal hashing and equality
  • &str and String are one type at runtime
  • get clones the &str into a String first
get<Q>(&self, k: &Q) where K: Borrow<Q>: no allocation per lookup.

Should Merchant(String) implement Deref<Target = String>?

  • Yes, it is the idiomatic way to forward methods
  • No, Deref is meant for smart pointers only
  • Yes, otherwise it cannot be printed with braces
  • No, Deref cannot target a String in Rust
Expose what you mean (as_str()), not everything String can do.
