Traits in depth

Comparison and operator traits

In Rust, ==, <, + and sort() are all traits. Deriving them is one line, but each comes with a contract. And sometimes the right design is to leave one out on purpose.

By the end of this lesson

You can write Ord by hand, overload + and .sum(), and explain why Ledgerly's Money has neither Ord nor +.

The four comparison traits

TraitGivesContract
PartialEq==, !=symmetric, transitive
Eq(marker)also reflexive: a == a. Not true for f64 (NaN), so floats aren't Eq
PartialOrd<, <=…may answer "incomparable" (None)
Ord.cmp(), sort(), max(), BTreeMap keysa total order: every pair has an answer

Plus Hash, which must agree with Eq: equal values, equal hashes. Derives satisfy all of these. A derived Ord compares fields in declaration order and enum variants in declaration order, which is often exactly what you want, and occasionally a silent bug when someone reorders fields.

Writing Ord by hand

TS's sort((a, b) => b.priority - a.priority || a.title.localeCompare(b.title)), but attached to the type. For a one-off order, don't implement Ord: use v.sort_by(|a, b| …) or v.sort_by_key(|t| t.title.clone()).

Operators

a + b is Add::add(a, b); -, *, +=, [i], ! have their own traits in std::ops. Implement Add for a Cents(u64) newtype, and std::iter::Sum to make .sum() work too.

In Ledgerly: leaving traits out on purpose

Ord is a total order, and Add must return a value; neither can say "these currencies don't mix" except by panicking. So Money offers methods that return a Result instead. The #[expect(clippy::should_implement_trait)] right below silences clippy's suggestion to implement Ord, with the reason written down.

Where the comparison breaks

JS compares objects by reference ({a: 1} !== {a: 1}) and coerces in <. Rust compares by value, through traits, and only types that opt in. A struct without PartialEq can't be compared at all, which is sometimes exactly the design you want.

Check yourself

Why isn't f64 Ord, so vec_of_f64.sort() doesn't compile?

  • Floats are too imprecise to ever be compared
  • NaN compares with nothing, so no total order
  • Sorting floats needs a separate crate installed first
  • Floats are only comparable with the == operator
Use sort_by(|a, b| a.total_cmp(b)) for floats.

You reorder two fields of a struct that derives Ord. What can change?

  • Nothing; derived orders always ignore the field order
  • The sort order, silently, with no compile error
  • The code stops compiling until you fix it
  • Only the Debug output, not any comparison result
Derived Ord is lexicographic in declaration order.

Why does Money::cmp return Result<Ordering, MoneyError>?

  • Because Ord can only be derived, never written
  • Two currencies have no order; Ord can't say so
  • Because Results compare faster than plain Orderings do
  • Because Java's compareTo method returned a Result too
A missing trait plus a fallible method makes the impossible case visible to callers.
