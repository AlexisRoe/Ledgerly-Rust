Concurrency and async internals

Pin, just enough

Pin has a reputation. For reading and writing application code you need three facts: why it exists, where it shows up, and the two ways to make one.

By the end of this lesson

You can explain why futures get pinned, read Pin<Box<dyn Future…>>, and use Box::pin and pin! where the compiler asks for them.

Warm-up
What is the signature of Future::poll?
fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>. (101)
Why can't a struct hold a reference into its own field?
Moving the struct would move the field and leave the reference dangling. (81)

Why: futures can point into themselves

The state machine for this function holds both bytes and head, which points into bytes. That's the self-referential struct from lesson 81, generated by the compiler. If the future were moved in memory after its first poll, head would dangle. Pin<P> is a wrapper around a pointer that promises: the value behind it will not move again (std::pin).

Types that can't be harmed by moving (almost all: u32, String, your structs) implement the auto trait Unpin, and for them Pin changes nothing. Compiler-generated futures are the main !Unpin types.

In Ledgerly

Box: the future lives on the heap, at a stable address, so pinning it there is easy. dyn: callers don't know which scanner's future it is. Every BoxFuture in Ledgerly is this shape, built with Box::pin(…) (lesson 92).

Where the comparison breaks

JS engines move objects in memory all the time (compacting GC) and fix up the references; you never see it. Rust has no GC to fix up pointers, so "don't move this" must be part of the type. Most of the time, .await pins for you and you never see Pin at all.

Check yourself

What does Pin<&mut T> promise?

  • T is stored on the heap, not stack
  • The T behind it won't be moved again
  • T can't be changed through this pinned reference
  • T is shared safely between several other threads
Pinning is about location, not mutability or sharing.

An if returns one of two different async blocks and fails to compile. Fix?

  • Await both blocks inside the if instead
  • Box::pin both, returning a boxed dyn Future
  • Mark the function as unsafe to allow it
  • Wrap both of the blocks in Arc::new
Each async block has its own anonymous type; boxing erases them to one type.

Why does select! in a loop need &mut to a pinned future?

  • Because select! only accepts boxed futures as branches
  • To poll it each round without consuming it
  • Because pinned futures run faster inside loops
  • To clone the future for every loop iteration
Passing the future by value would drop it when another branch wins.
