Async Rust

Tokio: the runtime

Tokio is Ledgerly's event loop, with one difference from Node's: it runs tasks on several threads at once. Its toolbox maps neatly onto Promise.all, Promise.race, setTimeout and fire-and-forget.

By the end of this lesson

You can read Ledgerly's startup and shutdown code: tokio::join!, tokio::select!, tokio::spawn, tokio::time::sleep, and the #[tokio::test] attribute.

(Tokio tutorial: spawning, select.)

In Ledgerly: waiting for SIGTERM or Ctrl-C

A future that completes when either signal arrives: Promise.race of two listeners. It's returned unawaited (lazy!) and awaited later by serve.

In Ledgerly: drain, but not forever

Graceful shutdown: when shutdown starts, the server stops accepting connections and lets running requests finish. If that takes longer than drain (30 s), the deadline wins the race and the server future is dropped, which cancels it.

In Ledgerly: two servers side by side

The API listener, the management listener (health checks, metrics) and the shutdown trigger run concurrently, and serve returns when all three are done. Background work, like the event outbox dispatcher, runs as spawned tasks that are abort()ed afterwards.

Where the comparison breaks

Node runs your JS on one thread, so two callbacks never run at the same instant. Tokio's multi-threaded runtime runs spawned tasks truly in parallel on a thread pool. That's why everything shared between tasks must be Send + Sync and why mutable shared state needs a lock (next lesson). Also, never do blocking work (a slow CPU loop, a blocking file read) inside an async task: it stalls that worker thread. Tokio has spawn_blocking for that.

Check yourself

In tokio::select! { r = server => r, () = deadline => Ok(()) }, the deadline finishes first. What happens to server?

  • It keeps running in the background until it finishes
  • It's dropped, which cancels it at its current await
  • select! waits for it too before returning anything
  • It panics because it was interrupted in mid-request
Unlike Promise.race, losers aren't left running: their futures are dropped.

What's the Tokio for await Promise.all([loadUser(), loadTeam()])?

  • load_user().await; load_team().await;
  • tokio::join!(load_user(), load_team())
  • tokio::select! { … }
  • tokio::spawn(load_user()).await
join! runs them concurrently and waits for both. Two sequential awaits would run one after the other.

Why must a future passed to tokio::spawn be Send?

  • Spawned futures are serialised and sent across the network
  • The task may run on another thread of the pool
  • Send makes the future start immediately when it's created
  • Only Send futures may return a Result to callers
The multi-threaded runtime moves tasks between worker threads.
