Functions, closures and iterators

Collecting into Result and Option

What if the closure in map can fail? Rust can turn "a list of results" into "a result of a list" in one call, which is Promise.all for errors. Two small methods, transpose and map_err, handle the remaining shapes.

By the end of this lesson

You can read .collect::<Result<Vec<_>, _>>(), note.map(Note::new).transpose()? and .map_err(|_| InvalidId), and use them to keep ? working inside iterator code.

What does ? need from the surrounding function?
A Result (or Option) return type it can return the error through. (34)

All or nothing: collect into Result

An iterator of Result<T, E> collects into Result<Vec<T>, E>: the first Err stops the iteration and becomes the result. The same works for Option (Rust by Example: iterating over Results). When you want all problems rather than the first one, collect the Results themselves (Vec<Result<…>>), which is what Ledgerly's batch endpoint does in lesson 46's example, so it can report every invalid item.

transpose: swap the two wrappers

note is an Option<&str>. Mapping it through the fallible Note::new gives Option<Result<Note, InvalidInput>>, but ? needs the Result on the outside. .transpose() flips it to Result<Option<Note>, InvalidInput>: no note → Ok(None), valid → Ok(Some(note)), invalid → Err. Then ? applies. The same trick appears in persistence::find: row.map(Versioned::try_from).transpose().

map_err: translate the error

The uuid crate's error type isn't what Ledgerly wants to expose, so it's replaced with its own InvalidId. |_| means "I don't need the original error". It's TS's catch (e) { throw new InvalidId() }, in one call. (Section 8 shows the automatic version, #[from].)

Where the comparison breaks

In TS, errors and iteration are separate worlds: you throw out of a map callback and hope something catches it. Here an error is a value flowing through the chain like any other, so "stop at the first error", "collect all errors" and "skip the errors" (filter_map(Result::ok)) are each one method, and the types say which one you chose.

Check yourself

What does ["1", "x", "3"].iter().map(|s| s.parse::<u32>()).collect::<Result<Vec<_>, _>>() give?

  • Ok with the vector containing 1 and 3
  • Err with the parse error for input "x"
  • Ok with a vector of three Result values
  • A panic at the second element, "x"
The first Err wins and iteration stops there.

What does .transpose() turn Option<Result<T, E>> into?

  • Option<T>
  • Result<T, E>
  • Result<Option<T>, E>
  • Vec<Result<T, E>>
It swaps the layers so ? can deal with the error and leave the Option.

Why does the batch endpoint not collect into Result<Vec<_>, _>?

  • Batch items can never fail validation in Ledgerly
  • It reports every invalid item, not just one
  • collect only works with Option, not with Result
  • Results can't be stored inside any vector type
Collecting into Result stops at the first error. The API answers with all field violations, so each item's outcome is kept.
