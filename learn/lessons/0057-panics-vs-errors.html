Error handling the Ledgerly way

Panics vs errors, and why unwrap is banned

A panic is Rust's "this is a bug, stop here". It unwinds the stack like an uncaught exception, but it's not meant to be caught. Ledgerly forbids the easy ways to cause one in production code.

By the end of this lesson

You can tell an expected failure (return a Result) from a bug (a panic), know what Ledgerly does if a request handler panics anyway, and replace any unwrap() you're tempted to write.

Two kinds of failure

Meanssomething expected went wrong: bad input, missing row, network downa bug: an invariant the code relied on doesn't hold
RustResult<T, E>, ?panic!, unwrap() on None/Err, v[99] out of bounds, integer overflow (debug)
Callermust handle itcan't reasonably handle it
TS feela typed return valuean uncaught throw / assertion failure

(Book 9.3 "To panic! or Not to panic!".) unwrap() says "I'm sure this is Some/Ok". When you're wrong, the whole request (or, outside a request, the program) dies. In a server that runs for months, "I'm sure" is the most common source of crashes.

Ledgerly's rules

  • Production code: unwrap, expect, panic!, todo!, unimplemented! are clippy errors (root Cargo.toml). Indexing and unchecked arithmetic are errors in the domain modules too.
  • Tests: all allowed (clippy.toml), because a panic there is just a failing test.
  • Exceptions are written as #[expect(lint, reason = "…")]: like an eslint-disable comment that must explain itself, and that fails the build if it ever becomes unnecessary.

What to write instead of unwrap()

SituationWrite
the caller should know?, or .ok_or(MyError)? for an Option

an index might be out of range.get(i), .first()
a number might overflowchecked_* / saturating_*
a lock might be poisoned.unwrap_or_else(PoisonError::into_inner) (as FixedClock does)
In Ledgerly: the safety net anyway

A dependency could still panic. The CatchPanicLayer middleware catches the unwinding panic of one request and answers 500, so the server keeps serving everyone else. That's why the release profile keeps panic = "unwind" (lesson 4): with abort, one panic would end the process. Note what's not logged: the panic message, because it might contain user data.

Where the comparison breaks

In TS, throw is used for both expected failures and bugs, and try/catch handles both. Rust splits them: expected failures are values (Result), bugs are panics. You shouldn't use catch_unwind as a try/catch. Ledgerly's catch layer is a last-resort net, not a control-flow tool.

Check yourself

A user sends a merchant name that's too long. Panic or error?

  • Panic, because the request is plainly invalid input
  • Error: bad input is expected; return a Result
  • Panic, because CatchPanicLayer turns it into a 400
  • Neither; silently truncate the name and then continue
Bad input is the most expected failure there is. Merchant::new returns Err(InvalidInput), which becomes a 400. A panic would become a 500.

You need the first rejection reason and want "-" if there is none. What do you write?

  • e.rejections()[0].reason().as_str()
  • e.rejections().first().unwrap().reason().as_str()
  • e.rejections().first().map_or("-", |r| r.reason().as_str())
  • e.rejections().first().expect("-").reason().as_str()
Indexing and unwrap/expect panic on an empty list (and are linted away). map_or handles both cases.

What happens when a request handler panics in Ledgerly?

  • The whole server process exits and restarts later
  • That request gets a 500; the server keeps running
  • The panic message is returned to the client verbatim
  • The request is retried automatically one more time
CatchPanicLayer catches the unwind for that request and answers with the generic internal-error problem.
