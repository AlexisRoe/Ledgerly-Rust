Channels and the actor pattern

Instead of sharing data behind a lock, give it to one task and send that task messages. Tokio has four channel types for the four common shapes of communication.

By the end of this lesson

You can pick mpsc, oneshot, watch or broadcast for a job, and write a small actor with a request/reply channel.

(Tokio tutorial: channels.) A channel closes when all senders are dropped: recv() then returns None, which is how consumer loops end without any "stop" message.

In Ledgerly: a watch channel as a shutdown switch

A boolean everybody can wait on. watch fits because late subscribers must see the current value: a request that starts waiting after the shutdown began must return immediately. The app's probe tests use a oneshot the same way, to stop a test server ().

The actor pattern

Callers hold a cloneable handle around the mpsc::Sender. The state is never shared, so it can never be locked wrongly, and commands are processed in order. It's a good fit for a connection, a rate limiter or a cache with complex updates (Alice Ryhl: Actors with Tokio).

Where the comparison breaks

Node's single thread makes "shared state in a closure" safe by default, so actors are rare there. In Rust, choosing between a lock and an actor is a real design decision. Locks are simpler for small, quick updates; actors shine when updates involve awaiting or when ordering matters. Bounded channels add one thing Node streams make you think about too: when the queue is full, send().await waits.

Why does an actor's state need no Mutex?

  • Actors run on a special single-threaded runtime
  • Only the actor's own task ever touches it
  • The channel copies the state for each message
  • Tokio locks the state automatically for it
Ownership instead of sharing: other tasks only send messages.
