Error handling the Ledgerly way

From domain error to HTTP problem

The last step: how "the expense is a draft and can't be approved" becomes 409 Conflict with a problem+json body. This is Ledgerly's version of an Express error middleware, built from two exhaustive matches.

By the end of this lesson

You can trace any refusal from the domain to the HTTP status and body the client sees, and you know which file to change if a new error kind needs a status.

The path

Patterns from section 4 at work: nested enum patterns (Storage(PersistenceError::Conflict { .. })), an @ binding, and no _. A database error is logged and becomes a bare 500 with no detail that could leak internals.

Step 3: the handler's return type

The handler returns Result<Response, Problem>, so every ? inside can bail out with a Problem. axum turns both Ok and Err into an HTTP response, because Problem implements axum's IntoResponse trait (in shared/src/web/problem.rs).

Where the comparison breaks

An Express error middleware receives err: any and usually ends in res.status(err.status ?? 500). A new error class silently becomes a 500. Here a new ExpenseError variant doesn't compile until refusal gives it a status, and the test every_domain_refusal_has_javas_status_code_and_message checks that the status and message match Ledgerly-Java.

Check yourself

Which file decides the HTTP status for ExpenseError::SelfDealing?

  • The domain's error.rs file, via an attribute there
  • The web layer's problem.rs, plus ErrorCode in shared
  • The app crate's lib.rs, in the panic layer
  • The OpenAPI contract, read at runtime by axum
refusal picks the ErrorCode; the code's entry holds the status. The domain knows nothing about HTTP.

What does the client get for a database failure?

  • The full sqlx error text, to help debugging
  • A bare 500; details go only to logs
  • A 503 asking the client to retry later
  • A 404, so the database stays hidden there
The Storage(Corrupt | Database) arm logs and returns Problem::internal_error().

You add ExpenseError::Archived. What's the first thing that fails?

  • A parity test, the next time it runs
  • The match in refusal stops compiling at once
  • Nothing; it defaults to an internal server error
  • The OpenAPI linter, since the code is unknown
The exhaustive match is the first guard. Tests and the contract check follow.
