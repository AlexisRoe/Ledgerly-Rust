Error design: libraries vs applications

Part I taught you to read Ledgerly's error enums. Designing your own starts with one question: will the caller handle this error, or only report it? The answer picks the tool.

By the end of this lesson

You can choose between a thiserror enum and anyhow, design variants around what callers do with them, and add context to errors on their way up.

(anyhow, thiserror; both by the same author, meant to be used together.) "Library" and "application" describe the caller, not the crate: inside one app, a domain module is a library for its use cases.

In Ledgerly: everything is handled

Every Ledgerly error ends as an HTTP problem response whose status and body must match Java's exactly, so every error is matched, and Ledgerly has no anyhow. Variants are designed around what the web layer must decide: InvalidTransition becomes 409, Forbidden 403, InvalidInput 400 with a field name. Even startup failures are typed (ConfigError), because their message format is part of the operational contract with Java (ADR 0013).

Designing variants

  • One variant per different reaction, not per underlying cause. Three ways a database call can fail usually become one Storage(#[from] sqlx::Error) variant, because callers treat them the same.
  • Carry data the handler needs (from and action, a field name), not preformatted strings.
  • Don't leak internals into messages users see: SQL, file paths, secrets.
  • Add context where you know it: with anyhow, .with_context(|| format!("reading {path}")); with enums, a variant that wraps the source.
Where the comparison breaks

In TS, any function can throw anything, and the type system doesn't track it. Rust puts the error type in the signature. That's more work up front, but it's the only way the compiler can tell you that a new variant needs handling somewhere (lesson 77). anyhow opts out of that on purpose, for code where nobody will ever match.

Check yourself

A CLI tool's main loads a file, parses it, and prints any failure. Which error type fits?

  • A hand-written enum with one variant per line of main
  • anyhow::Result with .context(…)
  • Box<dyn Any>
  • String errors built with format!
Nobody matches; the error is reported. Context makes the report useful.

Why does Ledgerly not use anyhow at all?

  • anyhow is not allowed by the cargo-deny licence list
  • Every error must map to a precise, Java-identical response
  • anyhow does not work inside async functions at all
  • thiserror and anyhow cannot be used in one project
Handled errors need variants; reported-only errors are rare in a parity port.

Three sqlx failures (timeout, connection reset, deadlock) all lead to a 500. How many variants?

  • Three, one for each distinct sqlx failure
  • One wrapping sqlx::Error; the reaction is identical
  • None; sqlx errors should simply panic instead
  • Four: one per failure plus a fallback
Variants follow the caller's decisions, not the causes.
