Memory and performance

Generics vs dyn: what abstractions cost

"Zero-cost abstractions" is Rust's promise: an iterator chain or a generic function compiles to the same code you'd write by hand. The costs are real, just elsewhere: in compile time and binary size for generics, and in a pointer hop for dyn.

By the end of this lesson

Warm-up
Which allocation does every Box<dyn Trait> make?
One heap allocation for the value it holds. (107)
What's in a vtable?
One function pointer per method of the trait, plus size, alignment and drop. (92)

Generics: copies, specialised and inlined

For each concrete type a generic function is used with, the compiler generates a separate copy: monomorphisation. drain_all::<Countdown> and drain_all::<Names> are two functions in the binary. Each copy knows its exact types, so the optimiser can inline calls (paste the callee's body into the caller) and then simplify across the boundary. That's how values.iter().map(f).sum() ends up as a plain loop.

The price: more code to compile and a bigger binary. Heavy generic use is a main reason Rust builds are slow.

dyn: one copy, an indirect call

A dyn Trait method call loads a function pointer from the vtable and calls through it. That costs a few nanoseconds and, more importantly, blocks inlining: the optimiser can't see which function will run. One copy of the calling code serves every implementation.

Measured

From the playground's bench binary (lesson 109), release build, on the author's machine:

1 million calls of |x| x + 1Time
through Box<dyn Fn(u64) -> u64>~0.9 ms
through a generic closure~2 ns

The generic version isn't "a million times faster calls": after inlining, the optimiser saw the whole loop and replaced it with a formula. That's the real benefit of static dispatch: not a cheaper call, but code the optimiser can see through. And the dyn version, a nanosecond per call, is still fast enough for nearly everything.

In Ledgerly: dyn at the seams, generics inside

Ports (clock, event publisher, scanner, membership lookup) are Arc<dyn …>. They're called a few times per request, next to database round trips; a vtable hop is invisible there. In exchange, use cases aren't generic over five type parameters, tests swap implementations without changing types, and compile times stay lower. Hot, inner code (iterators, serde, sqlx row decoding) is generic, and inlined.

Where the comparison breaks

In TS, every call through an interface is dynamic, and the JIT optimises hot paths at run time by guessing types. Rust decides at compile time: generics are always specialised, dyn never is. You choose per call site, which is why the same codebase uses both.

Check yourself

What is monomorphisation?

  • Converting all generic types to dyn at runtime
  • One compiled copy of a generic per type
  • Removing every type parameter that's never used
  • Merging similar functions into one shared copy
Each copy is specialised and can be inlined.

What's the main performance benefit of static dispatch?

  • It avoids one pointer load per method call
  • The optimiser can inline and simplify across calls
  • It stores every value on the stack instead
  • It makes the final binary smaller than dyn
Inlining unlocks every other optimisation. The pointer load itself is cheap.

Why are Ledgerly's ports dyn rather than generic parameters?

  • Generic parameters can't be used with async code
  • Calls are rare and simpler types beat a nanosecond
  • dyn calls are faster than generic calls here
  • Traits with methods can't be used as bounds
A vtable hop next to a database query is noise; five type parameters on every use case aren't.
