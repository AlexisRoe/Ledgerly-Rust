Memory and performance

Where allocations hide

Heap allocations are the most common avoidable cost in Rust code. Most are visible (String::new, Vec::new, Box::new), but many hide in innocent-looking calls. A handful of habits remove most of them.

By the end of this lesson

You can spot hidden allocations (format!, to_string, clone, collect), and fix them with with_capacity, borrowing, buffer reuse and iterator consumers.

In Ledgerly: one allocation for a hex string

A SHA-256 hash as hex: exactly two characters per byte, so the final size is known up front. The naive bytes.iter().map(|b| format!("{b:02x}")).collect::<String>() would allocate once per byte, 32 times, plus regrowth of the result. write! on a String can't actually fail; let _ = discards the Result without an unwrap.

Keep perspective

An allocation takes tens of nanoseconds. A Postgres round trip takes a millisecond: 10,000 times more. In a request handler, a few clones don't matter; in a loop over 10,000 import rows, or in code that runs on every request, they can. Write the clear version first, and optimise where a measurement says so (lesson 109). Clippy helps: redundant_clone, format_collect and friends point out the easy ones.

Where the comparison breaks

V8 allocates constantly and its GC is tuned for short-lived garbage, so JS developers rarely think about it. Rust has no GC; each allocation is a call to the allocator and each drop a call to free. That's still fast, and fully deterministic: no pauses, but also no batching. Fewer allocations translate directly into less work.

Check yourself

How many allocations does words.iter().filter(…).collect::<Vec<_>>().len() make, compared with .count()?

  • The same; collect is optimised away for len
  • At least one more; count allocates nothing
  • Fewer, because collect reuses the words vector
  • None of the two versions allocate anything
Consumers like count pull items one by one without storing them.

A loop builds one CSV line per row into a fresh String. The cheapest fix?

  • Use format! instead of push_str in the loop
  • One String outside the loop, cleared every iteration
  • Wrap each line's String in an Arc instead
  • Convert the line to a Box<str> afterwards
clear() keeps the capacity, so after the first rows no allocation happens.

A handler clones a 40-byte String once per request, then queries Postgres. Worth fixing?

  • Yes, clones are always the main bottleneck
  • Rarely; the query costs thousands of times
  • Yes, because clones block the async runtime
  • No, because Rust strings are always reference-counted
Measure first; optimise hot loops, not one-off clones.
