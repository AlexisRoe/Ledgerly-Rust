Concurrency and async internals

Blocking inside async

Async code runs on a few worker threads that tasks take turns on. A task that computes for 50 ms without an .await holds its thread for 50 ms. Move such work to the blocking pool.

By the end of this lesson

You can recognise blocking code in an async function, move it to spawn_blocking, and explain why Ledgerly hashes passwords there.

Warm-up
What happens to a task when its future is dropped?
It's cancelled at its current .await; code after it never runs. (103)
Why must poll never block?
It would hold the executor thread and stall every task waiting for it. (101)

What counts as blocking

"Blocking" means spending a long time between two .awaits. A rule of thumb from a Tokio maintainer: more than 10–100 µs (Alice Ryhl: "Async: What is blocking?").

  • CPU-heavy work: password hashing, compression, parsing a large CSV, image processing;
  • synchronous I/O: std::fs, std::net, a blocking HTTP client, std::thread::sleep;
  • waiting on a std::sync::Mutex that someone holds for a long time.

The fix

Tokio keeps a separate, larger pool of threads for blocking work (spawn_blocking). The async task awaits the result like any other future, and its worker thread is free meanwhile. For lots of parallel CPU work, a dedicated pool (the rayon crate) is the better tool.

In Ledgerly

Argon2 is slow on purpose (that's what makes stolen hashes expensive to crack). Done inline, every login would freeze a worker thread for tens of milliseconds, and a burst of logins would stall unrelated requests. Two ?-like steps: the first map_err handles the task failing (a panic), the second the hashing itself failing. The password moves into the closure as a SecretString.

Where the comparison breaks

In Node, CPU work blocks the event loop, and everything stops; you notice fast. With Tokio's multi-threaded runtime, one blocked worker leaves the others running, so the damage is quieter: latency spikes under load, timers firing late. Same mistake, harder to spot. Tests on a current_thread runtime make it visible.

Check yourself

Which of these belongs in spawn_blocking?

  • sqlx::query(…).fetch_one(&pool).await
  • argon2.hash_password(…)
  • tokio::time::sleep(d).await
  • reqwest::get(url).await
The others are async and yield while waiting. Hashing is pure CPU work.

Why does Ledgerly's hash_password have two map_errs?

  • One for each of the two password fields
  • One for the task failing, one for hashing
  • One for debug builds, one for release builds
  • One for Argon2 and another one for bcrypt
JoinHandle gives Result<Result<Hash, HashingFailed>, JoinError>.

A handler reads a 200 MB file with std::fs::read. What's the risk?

  • None, because std::fs is async under Tokio
  • A worker thread is blocked, slowing other requests
  • The file is read twice, once per thread
  • The compiler rejects std::fs in async functions
Use tokio::fs (which uses the blocking pool) or spawn_blocking.
