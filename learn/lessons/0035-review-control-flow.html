Mixed questions

When is a _ => arm a bad idea in Ledgerly?

  • Whenever the matched value is a plain number
  • When matching an enum that might gain variants later
  • Whenever the match is used as an expression
  • When the match has more than three arms
A wildcard silently absorbs new variants. Listing them keeps the compiler's exhaustiveness check on. On numbers (parse_canonical), _ is fine. (31)

What does Expense::restore gain by destructuring StoredExpense without ..?

  • It runs faster than reading each field directly
  • A new field breaks the build until handled
  • It moves the fields without needing any clones
  • It validates every field again while it restores
A struct pattern that names fields without .. must name all of them. (32)

Which form fits "keep retrying while it fails"?

  • if let Err(e) = try_it() { … }
  • while let Err(e) = try_it() { … }
  • let Err(e) = try_it() else { … };
  • matches!(try_it(), Err(_))
Ledgerly's bucket check at startup does exactly this. (33)

(Data types) A function returns Result<Option<Team>, DbError>. What does find(id)? give you on success?

  • Team
  • Option<Team>
  • Result<Team, DbError>
  • Option<Result<Team>>
? peels the outer Result only. You still decide what None means, often with .ok_or(NotFound)?. (25, 34)

(Data types) Why is let label = if n == 1 { "item" } else { "items" }; fine but if n == 1 { "item" } else { 2 } not?

  • Strings can't appear inside an if expression
  • The branches of the second have different types
  • The second is missing a semicolon after it
  • Integers need an explicit type suffix there
&str vs integer: E0308. (17, 29)

Trace a use case

Do this in VS Code (10 minutes)

Open , the login use case. List every way execute can end (each return, each ?, the final value), and for each say which HTTP answer a client probably gets.

What to look for
An early return Err(Unauthenticated) when the rate limit is exhausted. ? after acquiring a connection and after the user lookup (database errors → 500). The let Some(user) = … else { … return Err(Unauthenticated) } for unknown email or wrong password (401). map_err(…)? and ok_or(…)? for crypto/time problems (500). And the final Ok(…) with the session. Notice that unknown email and wrong password take the same path, deliberately, so attackers can't tell which one was wrong.
