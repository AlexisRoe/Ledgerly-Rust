Testing

Unit tests next to the code

No Jest, no config file, no describe: a test is a function marked #[test], usually in a mod tests at the bottom of the file it tests, and cargo test finds it.

By the end of this lesson

You can read and write a unit test in Ledgerly's style, run one test by name, and know why tests may call private functions and unwrap().

Warm-up
What does #[cfg(test)] do?
Compiles the item only when building tests. (11, 60)
Why may tests use unwrap() in Ledgerly?
clippy.toml allows it in tests; a panic there is just a failing test. (5, 57)

Jest → Rust

  • The test name is the description, written as a sentence in snake_case. Grouping comes from nested mods, like describe blocks.
  • Assertions are macros: assert!(cond), assert_eq!(left, right), assert_ne!. On failure they print both values with Debug, plus an optional message: assert_eq!(a, b, "{from} + {action}").
  • .unwrap_err() asserts "this must be an error" (it panics on Ok). .unwrap() asserts success. For a specific error: assert_eq!(result, Err(…)), or assert!(matches!(result, Err(ExpenseError::NotDraft { .. }))).
  • Helpers (draft(), money(), clock()) are plain functions in the same test module, Ledgerly's version of fixtures.

Where the module lives, and why it sees private things

mod tests is a child of the module under test, so it can call private functions and read private fields (lesson 13). use super::* brings everything in. Larger test suites move into their own file, like web/tests.rs, declared with #[cfg(test)] mod tests; (Book 11.1).

Running them

Async tests use #[tokio::test] async fn … instead of #[test]. Domain tests don't need it, because the domain has no async.

Where the comparison breaks

No mocking framework, no jest.mock() of modules. You can't replace a function at runtime. Instead Ledgerly passes dependencies in as traits (&dyn Clock, Arc<dyn MembershipLookup>) and tests hand in test doubles (FixedClock, application/doubles.rs). Tests in one binary run in parallel threads by default, so tests must not depend on each other's state.

Try it
  1. Run cargo test -p ledgerly-expenses refused_edit and find the test in the output.
  2. Change "12.50" in its first assert_eq! to "12.51", run it again, and read the failure: left vs right, and the file and line. Then revert with git checkout -- crates/expenses.

Check yourself

What's the Rust for expect(a).toEqual(b)?

  • expect!(a, b)
  • assert_eq!(a, b)
  • a.should_equal(b)
  • test::equal(a, b)
assert_eq! needs PartialEq (for ==) and Debug (for the failure message).

Why can a test in mod tests call a private helper of the file?

  • Tests are compiled with privacy checks turned off
  • It's a child module; children see private items
  • use super::* makes private items public in tests
  • cfg(test) promotes every item to pub(crate) visibility automatically
Privacy is per module, and descendants see their ancestors' items.

How do you run only the tests whose names contain self_dealing in the expenses crate?

  • cargo test --grep self_dealing
  • cargo test -p ledgerly-expenses self_dealing
  • cargo test self_dealing.rs
  • just test self_dealing
A positional argument filters by test path substring.
