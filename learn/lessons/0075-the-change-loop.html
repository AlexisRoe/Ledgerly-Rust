Making changes

The change loop

You can read Ledgerly now. Changing it is a loop: edit, let the compiler talk, fix, test. This lesson sets up the loop and the safety net for the three exercises that follow.

By the end of this lesson

You can make a change on a practice branch, get fast feedback without Docker, read any compiler error top to bottom, and throw the change away cleanly.

Warm-up
Fastest command to check a change compiles?
cargo check (or just save: rust-analyzer runs it). (3, 6)
Which tests run without Docker?
Pure unit tests, such as the domain's: cargo test -p ledgerly-expenses domain. (67)

Before you start: a practice branch

The exercises change Ledgerly's behaviour, which in the real project only happens through Ledgerly-Java first (the contract, the schema and the behaviour are Java's). So they stay on a practice branch and are never pushed.

The loop

  1. Edit in VS Code. rust-analyzer underlines errors within a second or two of saving.
  2. Read the first error (cargo check -p ledgerly-expenses in a terminal shows them in full). Fix the first one only. Later errors are often consequences of it.
  3. Run the narrowest tests: cargo test -p ledgerly-expenses domain (seconds, no Docker). Widen later: the whole crate, then just test.
  4. Lint and format: cargo clippy -p ledgerly-expenses --all-targets -- -D warnings and cargo fmt.
  5. Before a real commit: just check (Docker), as CI does.

Reading a compiler error, top to bottom

  1. Headline: the error code and the rule broken. rustc --explain E0004 gives the long version.
  2. Location: --> file:line:column (click it in the VS Code terminal).
  3. Labels: ^^^ marks the problem, --- marks related places.
  4. note: gives context, and help: suggests a fix, often a literal diff (~ lines). Read the suggestion critically: here it proposes todo!(), which Ledgerly's lints forbid, and a wildcard, which would defeat the point. Write a real arm.
Where the comparison breaks

With tsc, a long list of errors often means many independent problems, and you can run the code anyway. Rust's errors cascade more (one wrong type causes several follow-ups) and nothing runs until they're gone, so fix from the top and re-check often. The upside of the strictness: once it compiles, the remaining failures are mostly logic, and the tests point straight at them.

Check yourself

You have 14 compiler errors after one change. What do you do first?

  • Fix them in any order, easiest first
  • Fix the first one, then check again
  • Revert, since 14 errors means a mistake
  • Add wildcard arms wherever the errors point
Later errors are often caused by the first. One fix can clear many.

The compiler's help: suggests adding todo!(). Should you?

  • Yes, the compiler's suggestions are always correct
  • No, it panics and Ledgerly's lints forbid it
  • Yes, but only inside the domain modules
  • No, because todo isn't valid Rust syntax
It's a placeholder to get compiling. In Ledgerly, write the real decision instead.
