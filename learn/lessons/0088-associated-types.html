Traits in depth

Associated types vs generic parameters

Why is it Iterator<Item = u32> but From<u32>? Both put a type inside a trait, with one real difference: how many times one type may implement the trait.

By the end of this lesson

You can read type Item, type Error and S::Item, and choose between an associated type and a type parameter when you design a trait.

Two ways to put a type in a trait

A countdown yields u32s, and only u32s; letting it implement Iterator<u32> and Iterator<String> would make for x in countdown ambiguous. So Item is an output of the impl. A type, though, can be built from many things, so From's type is an input chosen by the caller.

Rule of thumb: if, for a given implementing type, there's exactly one sensible answer, use an associated type. If callers should be able to choose, use a parameter (Book 20.2).

TypeScript's nearest idea

In Rust you'd write S::Item directly, and a generic function over sources needs only one parameter: fn drain_all<S: Source>(s: &mut S) -> Vec<S::Item>.

In Ledgerly: Item and Error

Item = … pins the associated type in a bound. TryFrom has both kinds: the source type is a parameter (a type can be tried from many sources), and the error is associated (for a given conversion, there is one error type).

Where the comparison breaks

TS interfaces can't say "one implementation per type" at all, because a value can satisfy any number of structural types. Rust's traits are implemented explicitly and at most once per (trait, type) pair. That's what makes "the" item type of a type a meaningful thing to ask for.

Check yourself

Why is Iterator's item an associated type, not a parameter?

  • Associated types are faster at run time
  • Each iterator yields exactly one kind of item
  • Trait parameters were added to Rust later
  • Parameters can't be used in return types
One answer per implementing type → associated type.

Can TeamId implement both From<Uuid> and From<[u8; 16]>?

  • No, a trait is implemented at most once
  • Yes, each parameter value is a distinct trait
  • Only if both impls live in one block
  • Only when the two impls are generic
From<Uuid> and From<[u8; 16]> are different traits.

You design a Parser trait whose parsers each produce one output type. Which shape?

  • trait Parser<Output> { fn parse(&self, s: &str) -> Output; }
  • trait Parser { type Output; fn parse(&self, s: &str) -> Self::Output; }
  • trait Parser { fn parse<O>(&self, s: &str) -> O; }
  • trait Parser { fn parse(&self, s: &str) -> Box<dyn Any>; }
One output per parser → associated type; callers write P::Output.
