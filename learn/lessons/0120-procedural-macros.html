Writing macros

Procedural macros, and when not to write one

#[derive(Serialize)], #[tokio::test], sqlx::query_as!, thiserror: the macros doing the heaviest lifting in Ledgerly aren't macro_rules!. They're Rust programs that run inside the compiler.

By the end of this lesson

You can name the three kinds of procedural macros, see what one generates with cargo expand, and judge when a macro is the wrong tool.

Three kinds

KindLooks likeIn Ledgerly
derive#[derive(Name)] on a struct/enum; adds items next to itSerialize, Deserialize, thiserror::Error
attribute#[name] on an item; replaces the item#[tokio::test], #[sqlx::test]
function-likename!(…), like macro_rules! but arbitrary codesqlx::query_as!

A procedural macro is a function from tokens to tokens, compiled into a separate crate with proc-macro = true and run by the compiler. Almost all use syn (parse tokens into a syntax tree) and quote (write tokens back) (Reference: procedural macros). Because it's real code, a proc macro can do anything at compile time.

In Ledgerly: a macro that talks to a database

At compile time, this macro sends the SQL to Postgres (or reads the cached answer in .sqlx/), learns the column types, and generates code that maps rows into ExpenseRow, failing the build if a column doesn't fit (lesson 69). No macro_rules! could do that.

Seeing the output

Reading the expansion of #[derive(Debug)] or #[tokio::test] once demystifies them: it's ordinary code you could have written. rust-analyzer can do the same for one macro call ("Expand macro recursively" in the command palette).

When not to write a macro

  • A function works: use the function. It type-checks at the definition, has better errors, and tools understand it.
  • A generic or trait works: use that. Ledgerly's display_as_text! exists only because three impls of a foreign trait can't share code through a generic (a blanket impl over "tuple structs with a String" isn't expressible).
  • Macros pay off for repeated items (impls, types, tests), variadic syntax, and compile-time checks. Write a proc macro only when you'd otherwise maintain a code generator; for an application, that's rare.
Where the comparison breaks

TS decorators run at run time, on values. Rust's attribute macros run at compile time, on syntax, and can rewrite the item entirely: #[tokio::test] async fn t() becomes a plain fn t() that builds a runtime and blocks on the body. Nothing of the macro exists at run time.

Check yourself

Which kind of macro is #[tokio::test]?

  • a derive macro
  • an attribute macro
  • a function-like macro
  • a macro_rules! macro
It takes the function it's attached to and replaces it.

Why can sqlx::query_as! check SQL but macro_rules! couldn't?

  • Because macro_rules! can't take string literals as input
  • It's real code the compiler runs, doing I/O
  • Because sqlx runs the query when the program starts
  • Because macro_rules! macros only expand at run time
Procedural macros are programs; declarative ones only rearrange tokens.

A helper formats a money amount the same way in three places. Macro or function?

  • A macro, because it avoids a function call
  • A function; nothing here needs a macro at all
  • A proc macro, so the format is checked
  • A macro, so it takes any argument type
Functions are inlined anyway when it helps. Reach for macros only when functions can't.
